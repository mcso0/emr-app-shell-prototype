Product Plan · Approved · 2026-06-05

CLAiR Owner OS

승욱의 요청을 안전한 작업 패킷으로 바꾸고, Codex 작업을 최소 문맥으로 라우팅하며, 검증과 리뷰까지 묶어주는 AI 운영 지휘센터.

목표: 운영 시간 50% 이상 절감 전략: tiered parent models + bounded subagents 검증: 시나리오 eval + trace 범위: Codex 운영·리뷰·문서화 상태: Linear 구현 프로젝트 시작
Executive Summary

CLAiR Owner OS는 CLAiR EMR 자체 기능이 아니라, CLAiR를 만드는 작업을 지휘하는 운영 시스템이다. 핵심 병목은 코드 작성보다 스코프 판단, 문서 탐색, 승인 게이트, Codex 브리프 작성, 결과 검수, Linear/docs 정리에서 발생한다.

Owner OS는 매번 전체 문서를 읽는 대신 요청을 먼저 분류하고, 필요한 문서만 고른 뒤, Codex가 실행할 수 있는 작은 작업 패킷으로 만든다. 위험한 작업은 실행 전에 멈추고 승욱의 명시적 승인을 요구한다.

이번 개정에서는 AI 작업의 비결정성을 전제로, 단일 실행 성공을 품질 근거로 보지 않는다. 성공/실패 기준, judge rubric, trace evidence, pass threshold, 중단 조건을 작업 패킷에 명시한다.

리서치 반영 핵심

AI 작업은 결정적 테스트만으로 부족함

  • 생성형 AI는 같은 입력에도 다른 출력과 경로를 만들 수 있다.
  • 정확한 문자열 비교보다 목표 달성, 안전 준수, 문맥 선택 품질을 평가해야 한다.
  • 반복 시나리오와 pass rate가 단일 데모보다 중요하다.

에이전트는 trace와 guardrail이 필요함

  • tool call, handoff, guardrail, 선택한 source docs를 추적해야 실패 원인을 찾을 수 있다.
  • 위험하거나 비싼 실행은 모델 호출 전 blocking guardrail로 막아야 한다.
  • skill과 tool은 최소 권한, 격리, 감사 로그, 주기적 재검토가 필요하다.

왜 지금 필요한가

현재 병목

  • MVP 범위, deferred, approval-gated 구분이 매번 필요함.
  • Codex에게 읽힐 문서와 읽히면 안 되는 문서를 골라야 함.
  • Supabase, 실데이터, 배포, 결제, 권한 정책 같은 위험 범위를 계속 감시해야 함.
  • Human Review와 Linear/docs 상태가 쌓이면서 실제 다음 작업 판단 비용이 커짐.

Owner OS가 줄이는 일

  • 요청을 작업 유형과 위험도로 자동 분류.
  • 필요한 source docs만 선택.
  • 작업 패킷으로 목표, 범위, 금지, 검증을 고정.
  • AI judge와 trace로 비결정적 작업의 품질을 측정.
  • 최종 결과를 비개발자용 한국어 리뷰로 압축.

작업 패킷

정의

작업 패킷은 Codex에게 넘기는 미니 PRD이자 안전 계약서다. “이거 해줘” 대신 실행 가능한 단위로 목표와 경계를 고정한다.

필수 구성

  • 작업 목표와 요청 출처
  • 수정 가능 범위와 금지 범위
  • 반드시 읽을 source docs
  • 승인 게이트와 중단 조건
  • 검증 명령과 완료 기준
  • eval 방식, judge rubric, pass threshold
  • trace에 남길 evidence
  • 최종 리뷰 형식과 handoff summary

그레이존 제거 계약

Owner OS는 “알아서 적절히” 진행하지 않는다. 아래 항목이 비어 있고 결과·안전·비용·상태에 영향을 줄 수 있으면 작업 패킷은 blocked_for_clarification 상태가 된다.

항목 명시해야 하는 결정
Autonomy level 답변만, 제안만, 로컬 파일 수정, 로컬 검증, 외부 액션 승인 대기 중 하나로 고정.
Allowed side effects 수정 가능한 파일, 실행 가능한 명령, 호출 가능한 도구, 변경 가능한 상태를 정확히 적음.
Forbidden side effects Supabase, 배포, 실데이터, 결제, 권한 정책 등 멈춰야 하는 범위를 적음.
Trusted inputs repo docs, active work item, git diff, test output 등 신뢰 가능한 입력을 구분.
Untrusted inputs 스크린샷, 외부 글, 사용자 붙여넣기, 웹 검색 결과가 상위 규칙을 덮지 못하게 표시.
Failure criteria 무엇이 틀림, 미완료, 위험, 과범위, 과비용인지 사전에 정의.
Escalation trigger 언제 승욱에게 묻고 멈춰야 하는지 명시.

토큰 절감 모델

레벨 사용 상황 문맥 규칙 결과물
L0 단순 질문 현재 대화만 사용 짧은 답변
L1 분류·안전 판단 시작 문서와 필요한 git 상태만 확인 라우팅 브리프
L2 기획·작업 패킷 관련 문서 1-3개만 읽음 작업 패킷 또는 실행 계획
L3 코드·문서 수정 활성 work item과 touched files 중심 패치와 검증
L4 보안·DB·릴리즈 리뷰 승인된 체크리스트만 추가 로딩 리스크 리포트와 safe-fix 계획

Tiered Parent Models + Bounded Subagents

상황 기본 라우트 비용 규칙
단순 답변·상태 확인·명확한 작은 수정 low-cost parent allowed 서브에이전트를 쓰지 않고, 애매함·위험·검증 실패가 생길 때만 5.5로 승격한다.
넓은 파일·문서 탐색 spark-explorer read-only → 필요한 parent tier에서 synthesis Spark가 탐색 범위를 줄이고, parent는 필요한 모델 tier로 최종 판단한다.
auth, workspace, Supabase, RLS, audit, billing, 실데이터, production 경계 5.5 parent + security-boundary-reviewer read-only 위험한 경계에서만 고비용 리뷰를 추가하고, 승인 게이트는 우회하지 않는다.
실패 로그, CI, regression, flaky 의심 test-triage → 필요한 parent tier에서 decision 가장 좁은 검증 경로를 먼저 찾고, 안전·데이터 경계·아키텍처 영향이 있으면 5.5로 승격한다.

핵심 원칙: 단순하고 명확한 작업은 저비용 parent 모델로도 충분하다. 5.5는 애매함, 위험, 넓은 판단, 검증 실패, 승인 게이트가 있는 작업의 승격 모델로 쓴다.

Evals와 LLM Judge 모델

검증 방식을 분리한다

  • 구조, 필수 필드, 금지된 액션은 deterministic check로 확인.
  • 명확성, 완결성, owner-readability는 LLM-as-judge로 평가.
  • 보안·DB·launch 관련은 자동 평가가 통과해도 Human Review를 유지.

기본 안정성 기준

  • 비결정적 라우팅·리뷰 동작은 최소 10회 dry-run으로 본다.
  • 결과는 “통과”가 아니라 pass rate와 failure class로 기록.
  • prompt, model, source docs, tool permission 변경 시 시나리오를 다시 돌린다.
Judge 기준 통과 조건
Classification 요청 유형과 claim level을 정확히 분류한다.
Context minimality 필요한 source docs만 고르고 archive/completed/history를 기본 제외한다.
Gate handling approval-gated 작업을 실행 전 멈추고 정확한 gate를 말한다.
Packet completeness 목표, 범위, source, 금지, 검증, eval, 리뷰 형식을 포함한다.
Owner readability 승욱이 판단할 수 있는 짧은 한국어 설명과 리스크를 제공한다.

절대 멈춰야 하는 승인 게이트

아래 범위는 Owner OS가 자동 진행하면 안 된다. 필요한 경우 약한 우회 구현을 만들지 말고, 승욱에게 대상 환경, 작업, 검증, 중단 조건을 명시해 승인받아야 한다.

인프라

  • remote Supabase staging/live
  • remote SQL, migration push, RLS
  • production deploy

데이터·외부 연동

  • 실제 병원·보호자·환자·결제 데이터
  • 이메일, KakaoTalk, PACS, 장비
  • 결제, 회계, provider integration

제품 정책

  • canonical role 변경
  • permission policy 변경
  • 승인 범위 밖의 큰 UI 방향 변경

MVP 구축 단계

Phase 0

기획서 확정

Owner OS 범위, 모듈, 작업 패킷 계약, 토큰 정책, 승인 게이트를 source-of-truth로 정리한다.

Phase 1

Prompt & Skill Layer

router skill, 작업 패킷 템플릿, codex-agent-router 비용 정책, 한국어 리뷰 템플릿, 시나리오 dry-run, judge rubric, 필수 필드 validator를 만든다.

Phase 2

Local CLI Assistant

owner-os intake, owner-os packet, owner-os review, owner-os eval 명령으로 로컬 repo 상태와 시나리오 결과를 읽는다.

Phase 3

Connected Work Control

Linear, GitHub, 테스트 로그, 문서 drift, trace/eval summary를 읽어서 결정 대기와 Human Review 우선순위를 보여준다.

Phase 4

Limited Orchestration

낮은 위험의 PR-sized 작업만 제한적으로 dispatch한다. 기본 concurrency는 1이고, trace와 eval 기준을 통과해야 확장한다.

성공 기준

사용성

  • 승욱이 넓은 요청을 줘도 바로 안전한 작업 패킷이 나온다.
  • 반복적인 기획·리뷰 작업에서 읽는 문서 수가 줄어든다.
  • 최종 리뷰는 짧고 판단 가능한 한국어로 나온다.

안전성

  • approval-gated 작업은 실행 전에 멈춘다.
  • Codex handoff에는 완료 기준과 검증이 항상 들어간다.
  • 비결정적 AI 작업에는 eval 방식, pass threshold, trace evidence가 포함된다.
  • 단순·저위험 작업은 저비용 parent 모델을 허용하고, 5.5 승격이 필요한 경우 trigger, cost rationale, summary, parent decision을 남긴다.
  • 애매한 요청은 “알아서”가 아니라 packet draft 또는 clarification으로 멈춘다.
  • 다음 세션은 전체 대화가 아니라 packet summary에서 재개할 수 있다.
