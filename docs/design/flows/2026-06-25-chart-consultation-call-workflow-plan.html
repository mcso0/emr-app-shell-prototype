진료/차트 호출-진료시작 업무 흐름 기획안

현재 진료 대기 환자를 선택했을 때 상단 CTA가 곧바로 차트 작성완료로 보이는 문제를 바로잡는다. 접수된 환자는 먼저 호출하기로 대기실 DID 호출을 받고, 환자가 진료실에 들어온 뒤 진료 시작 상태가 되어야 SOAP, 진단명, 오더 작성과 최종 차트 작성완료가 가능하다.

1. 결론

제품 결론

진료/차트 화면의 primary CTA는 encounter 상태가 아니라 consultation queue 상태까지 함께 보고 결정해야 한다. waiting 환자에게는 호출하기, called 환자에게는 진료 시작, in_progress/in_consultation 환자에게만 차트 작성완료를 보여준다.

기술 결론

기존 chart/completion API는 차트 완료와 수납 대기 전환을 담당하므로 호출 액션으로 재사용하면 안 된다. 별도 chart/consultation-flow 계열 API/RPC를 추가해 call, start, 이후 필요 시 recall을 분리한다.

2. 현재 문제

관찰 지점 현재 화면 문제 수정 방향
좌측 대기열 대기중 1, 초코 / 최도현 접수 카드 선택됨 환자는 아직 호출 전인데 중앙 차트 영역이 완료 가능한 상태처럼 보인다. 대기 상태는 호출 대기 업무로 표현한다.
상단 primary CTA 차트 작성완료 진료 시작 전 환자에게 completion 액션이 노출된다. 호출하기로 교체하고 확인 모달을 둔다.
차트 상태 차트 대기 차트 대기와 환자 호출 대기가 섞여 있다. 상태를 호출 대기, 호출됨, 진료중, 작성완료로 분리한다.
DB/API 의미 clair_complete_chart는 waiting도 ready_for_billing로 넘길 수 있음 대기 환자가 곧바로 수납 대기 흐름으로 넘어갈 수 있는 상태 전이 위험이 있다. completion은 in_consultation 또는 ordered 이후만 허용한다.

3. 목표 업무 흐름

1. 접수 완료

접수/예약 화면에서 보호자가 체크인하면 encounter가 생성되고, waiting_queue_entries.queue_type = consultation, status = waiting으로 진료 대기열에 올라간다.

2. 대기열 선택

담당 수의사는 진료/차트 화면 좌측 대기열에서 초코 / 최도현 접수 건을 선택한다. 이 시점의 CTA는 호출하기다.

3. 호출 확인

호출하기를 누르면 확인 모달이 뜬다. 권장 문구는 초코/최도현을 호출하시겠습니까?이다. 모달에는 담당 수의사, 접수 시각, 호출 대상, DID 표시 문구 preview를 함께 보여준다.

4. DID 호출

확인하면 내부 호출 이벤트가 저장되고 queue row가 called로 바뀐다. 실제 병원에서는 DID 대기실 모니터에 환자 호출 안내가 표시된다. 현 MVP에서는 실제 DID provider 호출을 하지 않고, 전송 이벤트/outbox 상태만 설계한다.

5. 진료 시작

환자가 들어오면 수의사는 진료 시작을 누른다. encounter.status는 in_consultation, queue row는 in_progress, started_at은 현재 시각으로 저장된다.

6. 차트 작성

진료중 상태에서 SOAP, 진단명, 오더 입력을 진행한다. 이 단계부터 기존 SOAP/diagnosis/order draft API가 정상 editing workflow가 된다.

7. 차트 작성완료

작성이 끝나면 차트 작성완료를 누른다. 기존 completion route가 차트 완료, consultation queue 종료, 수납 대기 handoff를 담당한다. 단, 더 이상 waiting 상태에서는 실행되지 않아야 한다.

7. DB / API 설계안

기존 필드로 즉시 활용 가능한 것

  • encounters.status: waiting, in_consultation, ordered, ready_for_billing
  • encounters.started_at: 실제 진료 시작 시각
  • waiting_queue_entries.status: waiting, called, in_progress, done
  • waiting_queue_entries.called_at: 호출 시각
  • waiting_queue_entries.finished_at: consultation queue 종료 시각

추가 권장 데이터

대상 필드/테이블 목적 우선순위
waiting_queue_entries called_by_user_id, started_by_user_id 누가 호출했고 누가 진료를 시작했는지 감사/운영 추적 P0
encounter_call_events 신규 이벤트/outbox 테이블 DID 표시 문구 snapshot, delivery status, retry 상태 저장 P0/P1
encounter_call_events room_id nullable 추후 진료실/공간 데이터 도입 대비 P1
audit_events chart.patient_called, chart.consultation_started 임상 workflow mutation 이력 P0

API shape

Route Method Body 역할
/api/workspaces/[workspaceId]/chart/live-queue GET query: date 현재처럼 진료 대기열을 읽되 queue status별 UI label을 충분히 내려준다.
/api/workspaces/[workspaceId]/chart/consultation-flow PATCH { encounterId, action: "call" } 호출 확인 후 queue를 called로 전환하고 call event를 기록한다.
/api/workspaces/[workspaceId]/chart/consultation-flow PATCH { encounterId, action: "start" } 환자 입실 후 진료 시작. encounter를 in_consultation, queue를 in_progress로 전환한다.
/api/workspaces/[workspaceId]/chart/completion PATCH { encounterId } 기존 차트 작성완료. 단, waiting/called 상태에서는 409로 차단한다.

RPC / server core 제안

  • src/features/chart/server-consultation-flow-core.ts 신규 추가
  • public.clair_call_consultation_queue(p_workspace_id, p_actor_user_id, p_encounter_id)
  • public.clair_start_consultation(p_workspace_id, p_actor_user_id, p_encounter_id)
  • 두 RPC 모두 workspace membership, encounter workspace scope, active queue row를 확인하고 row lock을 잡는다.
  • 상태 충돌은 409 stale_status 또는 409 encounter_unavailable로 반환한다.

8. 구현 범위 제안

PR 1: 상태 전이 foundation

  • DB migration/RPC 추가
  • server core + API route 추가
  • completion이 waiting을 완료하지 못하게 제한
  • server tests 추가

PR 2: 차트 UI 적용

  • CTA 상태표 적용
  • 호출 확인 모달 추가
  • 호출됨/진료중 상태 badge와 queue grouping
  • Playwright UI regression

PR 3: DID outbox 확장

  • call event/outbox persistence
  • DID adapter interface
  • 전송 실패/재시도 UI
  • 실제 provider 연동은 별도 승인
권장 순서: 먼저 PR 1과 PR 2를 하나의 작은 구현으로 묶을 수 있다. DID provider 실제 연동은 운영 비용, 보안, 장비 접근, 외부 side effect가 있으므로 별도 승인 범위로 분리한다.

9. 수용 기준

  • 초코 / 최도현이 waiting queue일 때 상단 primary CTA는 호출하기다.
  • 호출하기 클릭 시 초코/최도현을 호출하시겠습니까? 모달이 뜬다.
  • 모달 확인 후 queue row는 called, called_at은 현재 시각으로 저장된다.
  • 호출 후 primary CTA는 진료 시작으로 바뀐다.
  • 진료 시작 후 encounter는 in_consultation, queue row는 in_progress가 된다.
  • 진료중 상태에서만 차트 작성완료 CTA가 노출된다.
  • 대기 또는 호출됨 상태에서 completion API를 직접 호출하면 409로 차단된다.
  • 호출/start/completion 후 live queue와 chart context가 새로고침 없이 갱신된다.
  • 권한이 없는 사용자는 호출, 진료 시작, 작성완료 mutation을 실행할 수 없다.
  • 실제 DID provider 연동 완료를 주장하지 않는다. MVP에서는 내부 event/outbox 또는 local acknowledgement까지만 주장한다.

11. 리스크 / 확인 필요

제품 결정 필요

  • 호출 후 환자가 들어오지 않을 때 호출 취소 또는 재호출을 이번 범위에 넣을지 결정해야 한다.
  • 진료실/room 데이터가 아직 없으므로 DID 문구는 진료실명을 일반 문구로 처리한다.
  • SOAP 사전 작성 허용 여부를 결정해야 한다. 권장 기본값은 진료 시작 전 읽기 중심이다.

기술 리스크

  • 현재 작업 트리에 여러 파일 변경이 있어 구현 착수 전 branch/worktree 정리가 필요하다.
  • 기존 completion RPC가 waiting을 ready_for_billing으로 넘길 수 있으므로 반드시 서버 차단을 먼저 넣어야 한다.
  • 실제 DID 연동은 외부 장비/provider side effect라 별도 승인과 테스트 장비가 필요하다.
