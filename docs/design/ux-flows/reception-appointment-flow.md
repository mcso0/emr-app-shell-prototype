# Reception / Appointment UX Flow

## Purpose

이 문서는 접수/예약 화면에서 데스크 직원이 현장 방문, 예약 내원, 하루 대기열을 운영하는 실제 화면 흐름을 정의한다. 제품 기준은 `docs/product/features/reception-appointment-spec.md`를 따른다.

## Screen Areas

### Reception Side Panel

- 현재 대기/접수 환자를 빠르게 훑는 영역.
- 대기, 예약, 전체 같은 목록 유형을 전환한다.
- 기본 목록은 `전체`이며, `대기`와 `예약`은 선택 날짜 안의 필터로 동작한다.
- 캘린더 선택 날짜가 바뀌면 side panel 목록도 같은 날짜 기준으로 바뀐다.
- 날짜가 오늘이 아니면 선택 날짜 label과 `오늘로 돌아가기` action을 제공해 사용자가 오늘 대기열로 오해하지 않게 한다.
- 보호자명, 환자명, 전화번호, 방문 목적 검색을 지원한다.
- 예약확정, 접수완료, 진료대기, 노쇼, 취소 상태를 구분한다.
- 담당 수의사 지정/미지정이 목록에서 드러나야 한다.
- 대기 시간이 길어질수록 neutral, yellow, orange, red 단계로 긴급도를 드러낸다.

### Calendar Board

- 하루 예약과 접수 운영 밀도를 시간 기준으로 보여준다.
- day view가 MVP의 기본 운영 화면이다.
- week/month view는 밀도와 개요 확인용이며, 세부 조작은 day view를 우선한다.
- 담당 수의사별 lane 또는 filter로 예약/대기 분포를 확인한다.
- 기본 선택은 오늘 출근일인 수의사 전체다.
- 수의사 선택 옵션은 스케줄 board의 표시 대상만 바꾼다.
- 좌측 진료 대기열/환자 카드 선택 여부는 스케줄 board를 필터링하거나 선택 상태와 연결하지 않는다.
- 각 schedule card는 상태색 배경 위에 담당 수의사 accent bar를 더해 수의사 배정을 빠르게 구분한다.
- 동물 이름과 내원 목적을 보호자명/전화번호보다 높은 위계로 표시하고, 반복 목적은 작은 icon label을 병행한다.
- day view의 현재 시간 line에는 현재 시각 label을 함께 표시한다.
- 스케줄 운영 toolbar의 registration action은 `환자/보호자 등록`으로 단일화하고, 기존 환자 즉시 접수를 위한 primary `진료 접수`, `더보기`를 함께 배치한다.
- 빈 시간대는 클릭 또는 드래그로 접수 task 생성 진입점이 된다. Notion Calendar처럼 calendar grid에서 직접 시간대를 선택하지만, 설정 UI는 popover가 아니라 우측 Detail Drawer를 사용한다.
- 생성 시간은 15분 고정 슬롯만 허용한다: `HH:00`, `HH:15`, `HH:30`, `HH:45`.

### Detail Drawer

- 예약 또는 접수 항목을 선택했을 때 열리는 상세 확인 영역.
- 보호자/환자, 방문 목적, 예약/접수 시각, 담당 수의사, 상태, 메모를 확인한다.
- 상태에 따라 주요 액션을 하나만 강하게 노출한다.

### Registration Quality

- 향후 등록 진입점은 `docs/design/screens/reception/planning/unified-registration-entry.md`의 통합 등록 기획을 기준으로 단계적으로 검토한다.
- `환자/보호자 등록`은 등록 케이스 선택을 먼저 수행하고, 신규 보호자+환자 또는 기존 보호자+신규 환자 flow로 이어진다.
- 신규 동물 등록의 품종은 종별 후보를 autocomplete로 추천하되 직접 입력도 허용한다.
- 보호자 검색 후보는 입력 필드 하단에 상시 노출하지 않고, 검색 field focus/typing 시 popover list로 보여준다.
- 신규 동물 등록의 종 선택은 일반 동물병원에서 다루는 소동물 범주를 포함하고, 성별은 미상/수컷/암컷/중성화 수컷/중성화 암컷을 구분한다.
- 보호자 등록에서는 개인정보 수집 동의 서명 완료가 필요하며, 마케팅 수신 동의는 선택이다.
- 신규 동물 등록은 보호자 기본 정보 또는 기존 보호자 연결만 다루며 개인정보 동의 section을 노출하지 않는다.
- 전자서명은 MVP에서 `태블릿 서명 요청`과 `서명 완료 처리` 상태로 시뮬레이션한다.
- 보호자 휴대전화가 기존 보호자와 같으면 신규 생성은 막고 기존 보호자 상세 또는 기존 보호자 연결로 유도한다.
- 동물 등록은 나이와 생년월일 계산, 믹스견/믹스묘 제안, 마이크로칩 중복 차단, 동일 보호자 아래 동일 동물명 경고를 제공한다.

### Reception Form Drawer

- 현장 접수 또는 예약 접수 처리 시 사용하는 입력 영역.
- 현재 존재하는 reference image는 `docs/design/assets/reference-screens/reception/reception-form-drawer.png`뿐이다.
- 필드 밀도와 footer action hierarchy는 이 reference를 참고하되, pixel-perfect 기준으로 보지 않는다.

## Primary Flow 1: 현장 접수

1. 데스크 직원이 접수/예약 화면에 진입한다.
2. 사이드 패널 검색에서 보호자 또는 환자를 찾는다.
3. 환자를 선택하면 현재 예약/접수 맥락이 화면 상단 또는 drawer에서 확인된다.
4. 데스크 직원이 `진료 접수` 액션을 선택하거나, day calendar의 빈 시간대를 클릭/드래그한다.
5. 캘린더에서 시작한 경우 우측 drawer에 접수일, 담당 수의사, 진료시작시간, 소요 시간이 미리 채워진다. `진료 접수` 버튼에서 시작한 경우 시간은 기본값으로 시작한다.
6. 데스크 직원이 보호자/동물을 선택하고 방문 목적, 진료과, 담당 수의사, 소요 시간, 접수/예약 메모를 입력한다.
7. 담당 수의사는 미지정으로 둘 수 있다.
8. 생성 액션을 누르면 encounter가 생성되고 진료대기 상태로 표시된다.
9. 사이드 패널과 대기열에서 새 현장 접수 row가 확인된다.

## Primary Flow 1-A: 환자/보호자 등록 통합 경로

1. 데스크 직원이 `환자/보호자 등록`을 선택한다.
2. `환자/보호자 모두 신규 등록` 또는 `기존 보호자에 신규 환자 등록` 중 하나를 선택한다.
3. 신규 보호자 branch는 보호자 정보와 개인정보 동의를 입력한 뒤 환자 정보 입력으로 이어진다.
4. 기존 보호자 branch는 보호자를 검색/선택한 뒤 환자 정보 입력으로 이어진다.
5. 등록 정보 확인 단계에서 요약을 확인하고 `등록`을 누르면 session store에 commit한다.
6. 성공 toast에서 `환자 상세 보기` 또는 `진료 접수` 후속 액션을 선택할 수 있다.

### Required UI Feedback

- 생성 전 필수 필드가 비어 있으면 저장 액션을 막거나 명확한 field-level feedback을 제공한다.
- 최종 확인 전 취소된 draft는 store에 저장되지 않는다.
- dirty 상태로 닫기/취소하면 이탈 확인 dialog를 보여준다.
- 등록 완료 후 자동 접수로 이동하지 않는다.

## Primary Flow 2: 예약 환자 접수 처리

1. 데스크 직원이 캘린더 또는 예약 목록에서 예약확정 항목을 선택한다.
2. Detail Drawer에서 보호자/환자, 예약 시간, 방문 목적, 담당 수의사를 확인한다.
3. 필요하면 접수 처리 전에 담당 수의사나 방문 목적을 보정한다.
4. 접수 처리 액션을 선택한다.
5. appointment는 접수완료 상태가 되고 encounter가 생성된다.
6. 생성된 encounter는 진료대기 상태로 대기열에 표시된다.
7. 캘린더와 사이드 패널은 예약확정이 아니라 접수완료/진료대기 상태를 반영한다.

### Required UI Feedback

- 이미 접수완료된 예약에는 접수 처리 액션을 다시 노출하지 않는다.
- 접수 처리 후 담당 수의사 지정/미지정이 대기열에서 명확히 보인다.
- 같은 환자의 당일 중복 접수가 의심되면 확인이 필요하다.

## Primary Flow 3: 하루 캘린더와 대기열 운영

1. 데스크 직원은 day view에서 병원 내 시간대별 예약과 접수 현황을 확인한다.
2. 화면 진입 시 기본 날짜는 오늘이고, side panel 기본 탭은 `전체`다.
3. 날짜를 바꾸면 side panel도 선택 날짜의 접수/예약 records로 바뀐다.
4. 과거 날짜는 이력처럼 읽히고, 미래 날짜는 예약 중심으로 읽혀야 한다.
5. 기본적으로 선택 날짜 출근일인 수의사들이 선택되어 있고, 담당 수의사 selector로 표시할 수의사 schedule lane을 조정한다.
6. 좌측 진료 대기열의 환자 카드 선택은 환자/접수 상세 맥락을 여는 동작이며, 스케줄 표시 대상과 연결하지 않는다.
7. 데스크 직원은 수의사별 스케줄과 빈 시간대를 확인한 뒤 현장 접수 환자를 배정한다.
8. 미지정 대기 환자를 확인하고 필요 시 담당 수의사를 지정한다.
9. 접수완료/진료대기 환자를 진료팀이 확인할 수 있는 상태로 유지한다.
10. 진료 화면으로 이동해도 같은 encounter context가 보존된다.

### Required UI Feedback

- 예약확정과 진료대기는 색상, label, action으로 구분되어야 한다.
- 선택 날짜가 오늘이 아니면 오늘 대기열로 오해하지 않도록 날짜 label과 `오늘로 돌아가기` action을 명확히 노출한다.
- 미지정 담당의는 빈 값처럼 보이지 않고 의도된 상태로 보여야 한다.
- 미지정 schedule card는 gray accent를 사용한다.
- 예약확정 card의 `접수 처리` action은 card background와 충분히 대비되는 solid button으로 표시한다.
- 오늘 운영 흐름에서 취소/노쇼는 주요 대기보다 낮은 시각적 우선순위를 가진다.
- 좌측 환자 카드 선택 강조와 스케줄 card 강조는 별개의 상태로 다룬다.
- Existing task drag/drop schedule editing remains deferred until appointment mutation behavior is scoped. New session-only task creation by clicking or dragging empty time ranges is in scope for the calendar creation UX.

## Secondary Flow 4: 예약 생성/변경/취소

1. 데스크 직원은 빈 시간대 또는 예약 생성 액션을 선택한다.
2. 환자/보호자, 예약 시간, 방문 목적, 담당 수의사, 메모를 입력한다.
3. 저장하면 예약확정 상태가 된다.
4. 기존 예약 상세에서 시간, 담당 수의사, 방문 목적, 메모를 변경할 수 있다.
5. 예약 취소 시 취소 사유를 남긴다.
6. 취소된 예약은 운영 목록에서 낮은 우선순위로 유지되며 환자/보호자 이력에서 확인된다.

## Secondary Flow 5: 노쇼/지연/상태 관리

1. 예약 시간이 지났고 접수되지 않은 예약은 노쇼 후보가 된다.
2. MVP에서는 자동 확정이 아니라 데스크 직원의 수동 노쇼 처리를 기본으로 한다.
3. 노쇼 처리 액션은 예약확정 상태에서만 가능하다.
4. 노쇼 처리 후 예약은 노쇼 상태로 남고, 환자/보호자 이력에서 확인 가능해야 한다.

## Empty And Edge States

- 검색 결과 없음: 신규 환자 등록 또는 검색어 초기화로 이어진다.
- 오늘 예약 없음: 현장 접수와 예약 생성 액션을 우선 노출한다.
- 담당 수의사 없음: 미지정 상태로 접수 가능하지만 대기열에서 구분한다.
- 중복 접수 가능성: 같은 환자의 당일 active encounter가 있으면 확인한다.
- 중복 보호자 가능성: 같은 휴대전화 보호자가 있으면 새 보호자 생성은 차단한다.
- 취소/노쇼 항목: 기본 운영 흐름을 방해하지 않되 이력 접근은 가능해야 한다.

## Verification Ideas

- 현장 접수 후 새 진료대기 row가 보인다.
- 예약확정 항목을 접수 처리하면 접수완료와 진료대기 상태가 반영된다.
- 담당 수의사 미지정 접수가 가능하고 목록에서 미지정으로 보인다.
- 접수/예약 검색은 보호자명, 환자명, 방문 목적을 찾는다.
- 취소 또는 노쇼 항목은 접수 처리 액션을 노출하지 않는다.
