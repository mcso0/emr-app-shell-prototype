01

‘수정하기’의 범위

수정 진입점은 하나로 모으고, 저장 결과는 변경 내용에 따라 나눈다.

요구사항

선택한 확정 오더의 내용을 다시 편집

  • 선택 도구 모음에 수정 진입점을 제공한다.
  • 확정 전에 입력할 수 있었던 일수, 횟수, 용량, 단위와 청구 관련 값을 수정한다.
  • 작업 내용이 달라지면 작업 담당자에게 변경을 안내하고, 조제·처치 지시서에 변경 내용을 표시한다.
  • 진행 중 업무 수정은 기존 기록을 보존하고 작업을 대체한다. 담당자가 변경 내용을 확인한 뒤 이어서 작업한다.
  • 금액 관련 값만 바뀌면 조제·처치 담당자에게 안내하지 않는다.
  • 수납 요청 후·결제 전 청구 변경은 변경안으로 저장한다. 수납 담당자가 확인하기 전에는 기존 청구금액을 유지하고, 확인한 뒤 반영한다.
  • 조제·처치가 완료돼도 자동으로 수납에 보내지 않는다. 사용자가 ‘수납 요청’을 눌렀을 때만 수납 화면에 요청건을 생성한다.
기획 기준

수정 · 재요청 · 수납 요청

수정은 기존 오더의 내용을 변경하는 행위다. 작업 영향이 있을 때만 담당자의 확인과 후속 작업이 필요하다.

재요청은 기존 작업을 다시 수행하도록 요청하는 행위다. 상세값 변경 없는 반복 요청과 구분해 표시한다.

수납 요청은 사용자가 청구할 오더를 명시적으로 수납에 보내는 행위다. 수정 저장이나 조제·처치 완료에 자동 포함하지 않는다. 전달 시점 확정

1차 범위 확정: 조제·처치 개별 오더 및 세트 구성 항목을 한 오더씩 수정한다. 세부값 일괄 편집은 후속 확장한다. 약품 자체 교체와 마스터 가격 변경은 이번 수정 범위에 포함하지 않는다.

“안내하지 않는다”는 “기록하지 않는다”가 아니다. 모든 변경의 이전값·이후값·수정자·수정 시각을 남기되, 필요한 역할에게만 변경 안내를 표시한다. 제안
02

현재 코드에서 확인한 출발점

첨부 화면과 origin/main 소스를 대조했다. 현재 배포의 실제 저장·알림 전달은 실행하지 않았다.

영역origin/main에서 확인이번 기획의 차이
수정 진입점행 오른쪽 연필 버튼은 있다. 선택 도구 모음은 수납 청구·재요청·긴급을 제공한다.근거 S1선택 도구 모음에 수정 추가. 연필과 같은 편집 화면으로 연결.
작업 상태별 수정대기 상태는 현재 요청 수정. 진행·일시중지·완료 상태는 새 작업 회차로 재요청하는 경로가 있다. 이전 기록은 보존한다.근거 S1, S2진행 중 수정은 기록을 보존하고 작업을 대체한다. 완료 후에는 기존 코드의 수행기록 정정과 새 작업 재요청 경로를 구분해 사용한다.
변경 안내·이력세부값·지시·요청 회차 변경에 대한 담당자 알림, 지시서의 이전/이후값 이력 표시가 있다.근거 S3, S4업무·금액 변경 분류를 명확히 정의. 새 요청의 수신자 유지와 중복 안내 방지를 검증한다. 다른 사람이 업무를 수정하면 원 요청자에게도 안내하도록 확장한다.
최신 지시 확인총괄·범위별 지시사항의 버전 확인과 요청/완료 당시 기록이 있다. 이것만으로 처방 필드 변경까지 확인이 강제된다고 단정할 수 없다.근거 S5확정 정책에 따라 처방 필드 수정 버전도 담당자의 확인 대상으로 연결해야 한다. 최초 요청과 실제 변경을 구분하며, 현재 코드에 이미 연결됐다고 단정하지 않는다.
수납 전 금액 수정청구명·청구 수량·청구 반영 여부·할인/할증 등의 별도 저장 경로가 있다. 확인한 입력 계약에는 단가·과세 필드가 없다.근거 S6과세·단가까지 편집하려면 소유 규칙과 저장 계약을 추가 확인·확장해야 한다. 단순 버튼 추가만으로 끝나지 않는다.
수납 연결작업 완료 시 조건에 따라 수납 후보를 청구서에 연결하거나 수납 동기화를 호출하는 코드가 있다.근거 S7기획 확정
사용자가 ‘수납 요청’을 눌렀을 때만 수납에 보낸다. 기존 완료 자동 연결 경로는 구현 시 이 정책에 맞게 변경해야 한다. 앱에는 아직 반영하지 않았다.
수정 권한업무 수정은 order:update와 차트 접근 검사. 수납 전 수정은 chart:update와 billing:issue 검사. 청구서 수정은 현재 수납 담당자 조건도 검사한다.근거 S6, S9, S11기존 서버 권한을 유지한다. 담당 역할과 수정 권한을 동일하게 취급하지 않는다.
수정 사유업무 수정 사유는 3~500자 필수. 수납 전 할인·할증 사유는 후속 마이그레이션에서 선택 입력으로 변경됐다.근거 S6, S9확인된 기준을 유지한다. 단가·과세 통합 편집은 아직 없는 계약이므로 기존 할인 입력의 구현 완료 범위로 간주하지 않는다.
완료 기록 정정수행기록의 기록 정정 화면과 버전 이력이 있으며, 정정 사유를 받는다. 최초 수행결과 저장은 완료 처리와 연결된다.근거 S10기록 정정은 기존 이력을 보존한다. 다시 수행할 때만 새 작업을 요청한다. 진행 중 누적 수행량·남은 양은 별도 기록과 확인이 필요하다.
수납 요청 이후수납 전 수정은 청구서 연결 후 차단된다. 검토 보류된 미결제 청구서의 반전 경로가 있으며, 결제된 건은 환불 경로를 요구한다. 일반 변경안 승인 기능이 있다는 뜻은 아니다.근거 S6, S11결제 전 변경안은 수납 담당자가 확인한 뒤 반영하는 흐름을 추가한다. 결제 처리 중·완료 후 기존 금액을 직접 덮어쓰지 않는다. 실제 결제·환불 연동 완료는 미검증이다.
알림·일괄 편집일반 업무 변경 안내는 작업 담당자·주담당자 중심. 일괄 재요청·긴급 처리는 있으나 세부값 일괄 편집은 없다.근거 S3, S12다른 사람이 업무를 수정하면 원 요청자에게도 안내하고, 자기 수정 알림은 제외한다. 1차 세부값 수정은 단일 선택으로 제공한다.

주의: 해석 범위 — current-status에는 과거의 로컬 후보 설명과 후속 릴리스 설명이 함께 남아 있다. 이 문서는 확인된 코드와 확정한 기획 정책을 구분하며, 원격 DB 적용 상태를 보증하지 않는다.

03

무엇이 바뀌었는지로 판단한다

입력한 화면이나 버튼 이름이 아니라, 저장 전후 실제 차이를 서버가 분류한다. 아래 분류를 기획 기준으로 사용하며, 필드별 연결은 구현 시 검증한다.

변경 항목조제·처치 영향청구 영향저장 규칙
용량·용량 기준·횟수·일수변경 안내 + 이전/이후 비교수량·금액 재계산 여부 확인기존 계산 규칙 사용. 직접 지정한 조제량은 다시 확인.
처방 단위·조제 단위·조제 요청량업무에 쓰는 표시·수량이 달라지면 안내청구 기준에 따라 영향 가능단위 이름만 바꾸지 않음. 허용된 환산과 실제 물리량을 함께 검증.
경로·복용 시점·보관·스케줄·메모수행·포장·복약 안내에 쓰이면 안내금액 영향이 없을 수 있음지시서 적용 범위대로 비교. 단순 지시 문구 변경에 재조제를 강제하지 않음.
처치 방법·부위·투여량·일정·단계별 지시처치 담당자에게 안내기존 청구 규칙으로 영향 판단이미 수행한 부분과 앞으로 수행할 부분을 구분.
단가·과세·할인/할증안내 없음청구금액·세금 정보 변경수납 요청 전에는 변경 이력과 최신 금액 저장. 요청 후·결제 전에는 변경안을 저장하고 수납 담당자 확인 후 반영. 결제 처리 중·완료 후에는 기존 정정·환불 경계 유지.
청구명·청구 수량·청구 여부업무 표시와 완전히 분리된 값만 안내 없음청구 내용 변경“청구 수량”을 “조제 요청량”과 구별. 한 필드가 두 의미를 갖지 않게 함.
업무와 금액을 함께 수정업무 변경분만 안내금액 변경분만 수납에 반영업무 수정과 청구 변경안 생성은 한 번에 저장·실패 처리. 수납 요청 후·결제 전의 실제 청구금액 반영은 수납 담당자 확인 뒤 별도로 처리. 이 단계를 화면에서 구분한다.
변경 없음 / 표시만 같은 값없음없음저장 비활성. 불필요한 이력·알림·새 작업 생성 금지.
수행기록 정정과 새 작업 요청은 기존 경로를 구분해 사용하며 이전 기록을 보존한다. 약품/오더 항목 자체 교체와 보호자에게 이미 전달한 약의 변경은 이번 일반 수정 범위를 넘어서는 별도 흐름이다.

수정 버튼을 눌러 합성 데이터 편집 예시를 볼 수 있다. 나머지 항목은 배치 예시다. 실제 앱이나 서버와 연결되지 않는다.

01 · 수정 열기최신 오더·담당자·작업 상태·청구 상태를 함께 조회한다.

03 · 차이 검토바뀐 필드, 재계산 결과, 전달 대상과 작업 영향만 표시한다.

편집 화면

업무 정보와 청구 정보를 나눠 배치하되, 한 화면에서 편집한다. 권한이 없는 영역은 읽기 전용과 이유를 표시한다.

수납 요청 전에는 업무 변경을 수정 후 요청, 금액만 변경을 수정 저장으로 구분한다. 수납 요청 후·결제 전 청구 변경은 변경 확인 요청으로 표시한다. 저장 직전 바뀐 값과 수신 대상을 보여 준다.

코드 기준 유지: 업무 수정 사유는 3~500자 필수. 수납 전 할인·할증 사유는 선택 입력. 수행기록 정정은 별도 정정 사유를 받는다.

지시서·수납 화면

지시서에는 업무 내용 변경됨, 변경 항목의 이전값 → 최신값, 수정자·시각·사유를 표시한다.

수납 요청 후·결제 전에는 해당 수납건에 청구 변경 확인 대기와 기존값 → 변경안을 표시한다. 수납 담당자가 확인하면 청구금액에 반영하고 이력을 남긴다. 업무 안내 카드에 가격·할인 변경을 섞지 않는다.

알림을 읽거나 변경 카드를 접는 행위는 “최신 내용 확인”으로 간주하지 않는다. 실제 수정 이력이 있을 때만 “변경됨”을 표시한다.

담당자가 있는 경우

현재 작업 담당자에게 업무 변경 안내. 세트는 관련 구성 항목 담당자와 주담당자에게 보내되, 같은 사람은 한 번만 수신.

확정: 다른 사람이 업무 내용을 수정하면 원 요청자에게도 안내한다. 동일 수신자는 한 번만 받고, 자신이 수정한 건의 자기 알림은 제외한다.

담당자가 없는 경우

공용 작업 목록과 지시서에 변경 표시를 남긴다. 새로 맡는 담당자는 최신 내용을 확인한 뒤 작업한다.

모든 직원에게 개인 알림을 보내는 방식은 기본값으로 삼지 않는다. 긴급 건의 별도 전달 규칙은 추가 결정.

금액만 바뀐 경우

조제·처치 담당자의 읽지 않은 알림, 변경 배지, 작업 확인 상태를 건드리지 않는다. 작업 상태·담당자·수행 기록도 유지.

수납 요청 전에는 개인 알림 없이 기록만 저장한다. 요청 후·결제 전에는 수납 담당자에게 변경 확인을 요청하고, 확인 전까지 기존 청구금액을 유지한다.

06

진행 상태를 잃지 않는 수정

진행 중 수정과 수납 전달·반영 시점은 확정 정책이다. 완료 기록 정정과 권한은 확인된 코드 기준을 유지한다. 부분 수행 후 남은 작업량은 담당자가 확인하며 자동 차감 공식을 새로 만들지 않는다.

상태업무 정보 처리 기준금액 변경 처리 기준
확정 · 시작 전현재 요청의 최신값을 수정. 담당자 유지. 새 중복 작업을 만들지 않고 변경 확인 표시.수납 요청 전이면 청구값만 변경. 업무 상태·회차·담당자·완료 상태 유지.

수납 요청 후·결제 전에는 변경안을 저장하고 수납 담당자가 확인한 뒤 반영한다. 확인 전에는 기존 청구금액을 유지한다. 결제 처리 중·완료건의 금액은 차트에서 직접 덮어쓰지 않는다.
진행 중 · 일시중지확정 · 2026-11-03
기존 작업 기록을 보존하고 변경된 요청으로 작업을 대체한다. 담당자가 변경 내용을 확인한 뒤 이어서 작업한다. 확인 전에는 대체 작업을 진행하지 않으며, 구버전 작업으로 완료하지 않는다.
완료기존 코드 기준 유지
수행기록 정정은 정정 사유와 새 기록 버전을 남긴다. 실제로 다시 수행할 때만 재요청 경로로 새 작업을 만든다. 정정 때문에 완료 상태를 되돌리지 않는다.
반려 · 취소 · 차트 잠김일반 수정에서 자동 복원하지 않음. 반려 후 재요청 가능 조건, 취소 복원, 서명된 차트 정정 권한을 별도 확인.청구 상태와 권한에 따른 정정 경로 사용.
세트 일부 변경변경된 구성 항목만 새 확인/작업 대상. 변경하지 않은 완료 항목은 유지. 공통 지시 변경과 항목 재수행을 구분.세트 가격과 개별 항목 가격의 소유 규칙 유지. 구성 항목 수정으로 세트 전체가 중복 청구되지 않게 함.
부분 조제·부분 처치 처리 확정: 이미 수행한 부분을 별도로 기록·보존하고, 담당자가 수정된 내용과 남은 작업 범위를 확인한 뒤 이어서 작업한다. 기존 결과를 새 작업의 수행실적으로 복사하거나 남은 양을 임의로 자동 차감하지 않는다. 현재 수행결과 저장은 완료 처리와 연결되므로, 진행 중 수행분 기록과 작업 재개 흐름은 추가 구현이 필요하다.
07

확정 정책과 적용 기준

질문으로 남겼던 제품 방향은 확정했다. 기존 코드 유지 항목과 추가 구현이 필요한 정책을 구분한다. 앱 구현·배포를 승인하거나 완료한 기록은 아니다.

진행 중 업무 수정 확정

기존 기록을 보존하고 작업을 대체한다. 담당자는 변경 내용을 확인한 뒤 이어서 작업한다. 추가 작업으로 병행 생성하지 않는다.

수납으로 보내는 시점 확정

조제·처치가 완료돼도 자동으로 보내지 않는다. 사용자가 수납 요청을 눌렀을 때만 수납 화면에 요청건을 만든다.

차트 내부 청구 후보와 수납 요청건을 구분한다. 기존 완료 자동 연결 코드는 향후 구현에서 변경해야 한다.

수납 요청 후·결제 전 변경 확정

변경안 저장 → 수납건 확인 대기 → 수납 담당자 확인 → 청구금액 반영. 확인 전에는 기존 청구금액을 유지한다.

업무 변경으로 청구 수량·금액이 달라진 경우도 같은 기준이다. 업무 내용 확인은 조제·처치 담당자, 청구 변경 확인은 수납 담당자가 각각 맡는다. 기존 코드에 일반 변경안 승인 기능이 있다는 뜻은 아니며 추가 구현이 필요하다.

일부 수행한 상태에서 수정 제안 채택

이미 수행한 부분을 기록·보존한다. 담당자가 수정된 내용과 남은 작업 범위를 확인한 뒤 재개한다. 남은 양을 임의로 자동 계산하지 않는다.

진행 중 누적 수행량과 재개 시 확인 기록은 기존 완료 결과와 구분해 구현한다. 기록 보존 자체가 기존 조제물의 재사용 가능성을 뜻하지는 않는다.

원 요청자에게 변경 안내 제안 채택

다른 사람이 업무 내용을 수정하면 원 요청자에게도 안내한다. 작업 담당자·주담당자·원 요청자가 같은 사람이면 중복 안내하지 않는다. 자신이 수정한 건의 자기 알림은 제외한다.

금액만 바뀐 경우에는 이 업무 변경 알림을 보내지 않는다. 현재 알림 대상을 확장하는 구현이 필요하다.

1차 편집 범위 제안 채택

개별 오더 또는 세트 구성 항목을 한 오더씩 수정한다. 여러 오더의 세부값 일괄 편집은 후속 확장한다. 기존 일괄 재요청·긴급 처리와 구분한다.

코드 기준을 유지하는 항목: 업무·수납 수정 권한 분리, 업무 수정 사유 3~500자 필수, 수납 전 할인·할증 사유 선택, 수행기록 정정과 새 작업 재요청 분리, 결제된 청구서의 직접 금액 수정 제한. 실제 결제·환불 연동은 이번 조사에서 검증하지 않았다.
08

빠지면 안 되는 저장·동시 작업 규칙

아래는 구현 시 확인할 조건이다. 현재 모두 구현됐다는 의미가 아니다.

저장과 안내

  • 중복 클릭은 한 번의 수정·한 번의 알림으로 처리.
  • 저장 실패 시 입력을 보존. 성공 안내나 재요청을 먼저 표시하지 않음.
  • 업무 수정과 청구 변경안 생성은 함께 저장하거나 함께 실패한다. 수납 요청 후·결제 전 청구금액의 실제 반영은 수납 담당자 확인 뒤 별도로 처리하며, 확인 대기와 반영 완료를 구분한다.
  • 저장 성공 후 알림 실패는 “저장됨 · 전달 재시도 중”으로 구분. 동일 수정 이벤트로 재시도하고 중복 요청 금지.
  • 수정 후 청구 금액은 기존 계산·과세·할인 규칙으로 검증. 이 문서에서 새 계산식을 정의하지 않음.
  • 수납 담당자는 최신 변경안의 전후값을 확인한다. 확인 중 새 변경이 들어오면 이전 확인으로 최신 금액을 반영하지 않는다. 확인 대기 중 결제와의 동시 처리도 서버에서 검증한다.

다른 사용자가 동시에 작업할 때

  • 열어 둔 사이 오더·작업 상태·청구 상태가 바뀌면 최신 내용과 다시 비교.
  • 변경 확인은 사용자와 업무 버전에 묶음. 다음 변경이나 담당자 교체 후 이전 확인을 재사용하지 않음.
  • 기존 버전으로 완료 버튼을 누르면 서버에서 거절하고 최신 변경을 보여 줌.
  • 작업 대체 시 구버전 작업의 실행을 막고 담당자·지시서·청구 연결을 함께 검증.
  • 늦게 도착한 응답이 다른 오더의 편집 화면이나 최신 저장 결과를 덮어쓰지 않음.
09

기능 완료 판단 기준

구현에 착수하면 아래를 합성 데이터로 확인한다. 이 기획 단계에서는 실행하지 않았다.

01선택 도구 모음과 행 연필이 같은 수정 화면을 연다.
02업무값 수정은 지시서의 차이와 해당 담당자 안내에 반영된다.
03가격·과세·할인만 수정하면 업무 알림과 확인 상태가 변하지 않는다.
04조제·처치 완료와 금액 수정만으로 수납 요청건을 생성하거나 수납 화면에 보내지 않는다.
05사용자가 ‘수납 요청’을 눌렀을 때만 최신 청구값으로 전달한다. 중복 클릭과 요청 후 작업 완료가 중복 요청·청구를 만들지 않는다.
06수납 요청 후·결제 전 변경은 확인 대기로 표시된다. 수납 담당자 확인 전에는 기존 금액을 유지하고 확인한 변경안만 반영한다. 결제된 건은 기존 정정·환불 제한을 유지한다.
07세트의 변경하지 않은 완료 항목과 이전 수행 기록을 보존한다.
08진행 중 수정은 기존 기록을 보존하고 작업을 대체한다. 담당자가 변경 내용을 확인해야 이어서 작업할 수 있으며, 구버전으로 완료할 수 없다.
09다른 사람이 업무를 수정하면 원 요청자에게도 안내한다. 자기 알림과 중복 수신을 제외하고, 금액만 변경할 때 업무 알림을 보내지 않는다.
10중복 저장·저장 실패·알림 실패·연속 변경·늦은 응답을 처리한다.
11업무 수정과 청구 변경안 생성의 부분 저장·중복 알림을 막는다. 확인 대기·반영 완료를 구분하고, 오래된 변경안의 확인으로 최신 청구를 덮어쓰지 않는다.
12기존 업무·수납 권한과 수납 담당자 검사를 유지한다. 업무 수정 사유 3~500자와 할인·할증 사유 선택 입력을 검증한다.
13부분 수행분을 보존하고 담당자가 남은 작업 범위를 확인한 뒤 재개한다. 임의 자동 차감이나 기존 실적 복사를 하지 않는다.
14단일 선택 수정과 기존 일괄 재요청을 구분한다. 완료 기록 정정은 이력을 보존하고 재수행과 혼동하지 않는다.
