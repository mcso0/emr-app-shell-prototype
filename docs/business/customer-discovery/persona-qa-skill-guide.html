Project-local skill · v1

사용자 관점에서 기능을 검토하는 가장 짧은 방법

persona-qa는 CLAiR 화면과 업무 흐름을 7개 동물병원 프로토 페르소나의 목표와 Claim, 근거에 맞춰 살펴본다. 화면에서 확인한 사실과 AI의 추론을 나눈다. 알 수 없는 부분은 모르는 상태로 남긴다.

읽기 전용이 기본 Claim과 근거 연결 로컬·합성 데이터 우선 7개 호출명으로 바로 시작 외부 MCP 없음

Quick start

$persona-qa 서진 관점에서 검사 결과 검토 화면을 QA해줘.

이름은 페르소나를 짧게 부르기 위한 호출명이다. 실제 인물의 성별, 나이, 성격, 권한과는 관계없다.

과거 가이드 보관본

2026-08-01 작업 결과에서 복구한 자료야. 본문의 스킬과 페르소나는 당시 구성을 설명해. 2026-09-07 복구 시점에는 persona-qa 스킬, 프로토 페르소나 원본, Evidence 로그가 저장소에 없어서 해당 항목은 링크 없이 표시했어. 현재 설치 상태나 조사 근거를 뜻하지 않아.

01 · PURPOSE

이 스킬이 하는 일

특정 사용자를 흉내 내는 도구가 아니다. 지금 화면에서 확인한 사실과 조사 근거로 짚어낸 위험을 따로 보여줘, 다음 제품 판단에 바로 쓸 수 있게 한다.

1

관찰과 추론을 분리한다

화면에서 확인한 상태와 페르소나가 겪을 수 있는 어려움을 하나의 사실처럼 섞지 않는다.

2

Claim으로 근거를 추적한다

각 위험은 `PER-01-C01` 같은 Claim에 연결해 상태와 신뢰도, 한계를 함께 확인한다.

3

모르면 모른다고 남긴다

연결할 근거가 없으면 그럴듯한 이야기를 보태지 않는다. `미확인`으로 남기고 실제 사용자에게 확인할 질문으로 바꾼다.

이 스킬이 내놓은 결과는 사용자 조사 결과가 아니다. 제품 개선 가설로만 쓴다. Evidence 로그에는 비식별 인터뷰와 현장 관찰, 사용성 테스트, 추가 출처 검토 결과만 기록한다.

03 · WORKFLOW

스킬은 이렇게 검토한다

매번 페르소나 문서 전체를 읽지는 않는다. 필요한 카드와 Claim만 먼저 보고 근거의 한계까지 확인해야 할 때 Evidence 로그를 연다.

  1. 범위 확인검토할 화면과 경로, 업무, 바꾸지 말아야 할 범위를 정한다.
  2. 페르소나 선택호출명을 `PER-*` ID와 행동 역할에 맞춘다.
  3. Claim 연결관련된 주장과 상태, 신뢰도, Evidence만 가져온다.
  4. 화면 관찰화면에 보이는 상태와 해본 행동, 나온 결과를 기록한다.
  5. 위험 분리관찰한 사실, 페르소나 위험, 미확인 사항, 개선안을 나눈다.
  6. 검증 질문실제 사용자에게 묻거나 현장에서 확인할 질문을 남긴다.
기본

Review mode

화면과 문구, 프로토타입, 구현을 읽기 전용으로 살펴본다. 제품 상태는 바꾸지 않는다.

필요할 때

Compare mode

2~3명의 목표와 인계 조건을 나란히 보고 함께 필요한 것과 서로 충돌하는 지점을 가려낸다.

명시적으로 요청할 때만

Scenario mode

합성 데이터와 허용할 행동, 바꾸면 안 되는 상태, 중단 조건을 먼저 정한 뒤 제한된 범위에서 실행한다.

이렇게 요청하면 된다

길게 설명할 필요는 없다. 호출명과 살펴볼 화면이나 흐름, 확인하고 싶은 성공 조건을 함께 적으면 된다.

PQ-01 · PERSONA RISK 높음

검사 결과는 나왔지만 임상 확인 여부를 알 수 없다

관찰목록에는 결과 완료 시각만 보인다. 누가 확인했는지와 다음 행동 상태는 알 수 없다. ClaimPER-01-C01 · 지지됨 · 신뢰도 중간 영향서진은 아직 검토해야 할 결과와 이미 처리한 결과를 빠르게 가려내기 어렵다. 제안결과 생성과 임상 확인을 서로 다른 상태로 보여준다. 미확인실제 병원의 결과 확인 책임자와 승인 절차는 현장에서 검증해야 한다.
심각도는 차단 · 높음 · 중간 · 낮음 네 단계만 쓴다. 근거 없이 그럴듯해 보이는 페르소나·사용성·전환 점수는 만들지 않는다.
06 · GUARDRAILS

이 작업은 하지 않는다

페르소나는 행동을 이해하는 모델이지 권한표도, 가상의 직원도 아니다. 의료·개인정보·실서비스 경계를 넘는 즉시 검토를 멈춘다. 필요한 승인이나 안전한 환경부터 확인한다.

  • 실제 환자, 보호자, 직원 정보로 테스트하지 않는다.
  • 비밀번호, 토큰, 환경 변수 같은 비밀값을 읽거나 기록하지 않는다.
  • 저장, 삭제, 처방, 오더 확정, 결제, 권한 변경은 기본 동작으로 실행하지 않는다.
  • 페르소나 이름만 보고 성별, 나이, 성격, 경력, 권한을 추정하지 않는다.
  • AI가 만든 반응을 실제 사용자 발언이나 조사 Evidence로 남기지 않는다.
  • 비공개 화면을 외부 터널이나 서비스에 올려 검토하지 않는다.
  • 근거가 없는 부분을 그럴듯한 사용자 이야기로 메우지 않는다.
  • QA 결과만으로 제품 코드를 자동 수정하지 않는다.

08 · DESIGN REFERENCES

무엇을 참고하고 무엇을 뺐나

외부 도구를 그대로 설치하지 않았다. 쓸 만한 구조만 골라 CLAiR의 의료·Evidence 경계에 맞는 작은 프로젝트 로컬 스킬로 만들었다.

Hafermilch 설치 안 함 페르소나별 브라우저 여정과 결과를 구조화하는 방식만 참고했다. 자격증명을 전달하거나 역할극으로 평가하는 방식, 근거 없이 수치 점수를 매기는 방식은 가져오지 않았다.
Mimiq MCP 설치 안 함 페이지와 흐름, 문구를 사용자 관점별로 나눠 검토하는 호출 방식을 참고했다. 원격 MCP와 외부 터널, 가상 사용자의 독백·감정 서사는 가져오지 않았다.
PersonaCite 답할 때마다 근거를 찾아 연결한다. 출처가 없으면 답을 보류하는 원칙을 참고했다. 논문 속 시스템을 설치한 것은 아니다. 대신 프로젝트의 Claim·Evidence 구조로 원칙을 구현했다.
CLAiR persona-qa 로컬 Markdown에서 Claim 상태와 Evidence 신뢰도를 읽어 실제 화면에서 확인한 내용과 함께 본다. 기본은 읽기 전용이다. 실제 사용자 조사와 합성 QA도 섞지 않는다.
