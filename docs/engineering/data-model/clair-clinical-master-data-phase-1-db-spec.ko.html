CLAiR 임상 마스터 데이터
1단계 DB 상세 명세

Airtable에서 작성한 임상 마스터를 검증해 PostgreSQL에 배포하고, 병원별 오더 카탈로그로 복사한 뒤, 차트의 개별 오더와 Order Set이 업무 전달·수납까지 실제 동작하도록 만드는 최소 DB 구조다.

1. 1단계에서 증명할 것

→

→
차트 적용
→
업무·수납
  1. 같은 릴리즈를 다시 적용해도 마스터와 병원 복사본이 중복되지 않는다.
  2. 병원 2개가 같은 릴리즈를 받되 서로의 데이터를 읽거나 수정할 수 없다.
  3. 미수정 복사본은 자동 업데이트되고, 수정 복사본은 행 전체 업데이트 검토를 받는다.
  4. 병원 자체 오더는 CLAiR 업데이트와 분리된다.
  5. 개별 오더가 차트 확정·업무 전달·수납까지 동작한다.
  6. Order Set이 차트 선택·펼치기·진료별 수정·확정·업무 전달·수납까지 실제 동작한다.
  7. 마스터·병원 가격·세트 revision이 바뀌어도 과거 기록은 바뀌지 않는다.
초기 데이터의 임상적 완성도는 1단계 완료 조건이 아니다. 합성 데이터로 시스템은 검증할 수 있지만, 검토되지 않은 값을 수의학적으로 검증된 권고처럼 사용자에게 보여주면 안 된다.

2. 범위와 제외 범위

이번에 명세하는 것

  • 마스터 ID·이름·출처·릴리즈·revision·검토 기록
  • X/T/A, CG, NT, 분류 경로와 개별 표준 오더
  • 개·고양이와 검증 fixture에 필요한 단위·검체·결과 유형
  • 검사항목·검사 패널·오더-검사 연결
  • 병원 복사본·자동 업데이트·행 전체 검토
  • Order Set 불변 revision·고정 자식 revision·구간 가격
  • 차트 적용 스냅샷·RLS·감사·검증

이번에 만들지 않는 것

  • VetSCT·LOINC·ATCvet 등 대량 가져오기
  • CLAiR 추천 가격과 실제 투약 권고
  • 사용자용 임상 정상범위
  • 약품·백신·영상·진단명 전체 상세 마스터
  • 수정 행의 필드별 자동 병합
  • 3계층 이상 세트와 차트의 프리셋 저장
  • service_*와 호환 필드의 즉시 삭제
  • 원격 migration·실병원 데이터·운영 배포

3. 현재 DB에서 출발하는 지점

현재 구조현재 상태1단계 처리
order_catalog_items병원 오더, 가격, 경로, 수정 상태가 있음. 가격은 0 기본값·필수값유일한 병원 오더 원본으로 유지하고 마스터 계보·분류 경로·revision·미설정 가격을 추가
order_sets한 행을 직접 수정하고 문자열 버전을 사용안정적인 세트 ID만 맡기고 현재 불변 revision을 가리키게 변경
order_set_items개별 오더만 직접 참조revision 1로 이관한 뒤 새 작성 원본에서 제외
orders개별·세트·세트 자식 행과 JSON 스냅샷 기반이 있음그 구조를 재사용하고 조회 가능한 직접 계보 컬럼을 추가
service_*기존 진료·수가 카탈로그와 과거 FK가 남아 있음호환 전용. 새 이중 작성 금지, 삭제는 나중에 별도 승인
차트 검색개별 오더와 활성 세트를 검색함검증된 현재 세트 revision만 반환
차트 확정세트는 unsupported_order_type으로 거부1단계 1B에서 신뢰할 수 있는 펼치기·확정으로 교체
기존 테이블을 한 번에 교체하지 않는다. 새 구조를 옆에 추가하고, 읽기·쓰기 경계를 순서대로 옮긴다.

4. 물리 구조 원칙

영역확정 규칙
CLAiR 마스터비공개 master schema와 UUID PK. 브라우저 직접 권한 없음
병원 카탈로그현재 public 테이블과 text ID를 유지해 광범위한 ID 이관을 피함
마스터 식별변경·재사용하지 않는 master_key. 이름으로 생성하지 않음
A코드UUID와 분리된 서버 자동 생성 A000001
revision서버가 부여하는 양의 정수
릴리즈UUID + 자동 숫자 release_no. 사람이 semantic version을 입력하지 않음
상태현재 저장소 방식에 맞춘 text + check. PostgreSQL enum은 추가하지 않음
가격KRW 정수. NULL은 미설정, 0은 의도적 무료
이름중복 가능. ID·키·코드만 유일하며 유사 이름은 경고·검토
1단계에서 초안·검토·반려 작업 상태는 Airtable에 있고, PostgreSQL master에는 검증된 배포·폐기 상태와 불변 검토 증거를 저장한다.

컬럼군내용
부모 세트·부모 revision어떤 부모 정의가 영향을 받는지 표시
자식 세트·기존/새 revision현재 고정값과 반영 가능한 새 값 비교
상태대기·수락·무시·무효화

해결자·시각병원 관리자 감사

저장 규칙

  1. 병원 관리자가 전체 정의와 예상 현재 revision을 제출한다.
  2. 서버가 같은 트랜잭션에서 자식 오더와 자식 revision을 다시 읽는다.
  3. 병원 경계·사용 상태·가격·깊이·순환·중복·최소 선택 오더를 검증한다.
  4. 새 불변 revision과 구성 행을 insert한다.
  5. 활성 요청이 유효하면 현재 revision 포인터와 호환 projection을 함께 바꾼다.
  6. 비었거나 invalid이면 명시적인 사용 중지 확인 후 비활성으로만 저장하고 활성 revision을 대체하지 않는다.
  7. 자식 변경은 부모를 자동 변경하지 않고 검토를 만든다.
  8. 수락하면 새 부모 revision을 만드는 트랜잭션으로 처리한다.

  • 서버가 활성 병원 오더를 다시 읽음
  • 이름·수량·가격·과세·단위·A/X/T/CG/NT·업무 경로를 snapshot
  • 마스터와 병원 revision을 직접 기록
  • 이후 live catalog join 없이 과거 표시·수납 가능

  • 부모 행: row_type=set, order_type=set, 업무 없음
  • 선택된 개별 오더만 set_child 행 생성
  • 중첩 세트 경로는 child snapshot 안에 보존
  • 부모 snapshot에 전체 펼치기·사용자 변경·가격 계산을 보존

11. 배포와 병원 동기화

검증된 마스터 배포

  1. Airtable 검토 export를 읽는다.
  2. 이름을 정규화하고 fingerprint를 계산한다.
  3. 중복 ID·코드, 잘못된 관계, held NT, projection 불일치, 검토 없는 임상 주장을 거부한다.
  4. 같은 fingerprint의 성공 릴리즈가 있으면 재사용한다.
  5. 하나의 트랜잭션에서 현재 구조화 행, 증가한 revision, 불변 version, 검토 이벤트를 쓴다.
  6. 릴리즈를 published로 바꾸고 병원 동기화를 실행한다.

Airtable은 런타임에서 조회하지 않는다.

12. 보안과 RLS

비공개 master

  • 브라우저 Data API 비노출
  • authenticated 직접 mutation 권한 없음
  • 고정 search path의 검토된 서버/private 함수만 사용
  • 임의 테이블명·SQL을 받는 범용 definer 함수 금지

병원 데이터

  • 읽기: 활성 같은 병원 멤버십
  • 오더·세트 관리: service_catalog:manage, 1단계 hospital admin
  • 차트 적용: 기존 차트 권한 + 신뢰할 수 있는 서버 경계
  • 다른 병원 참조: FK·RLS·서버 검증 모두 거부

UPDATE RLS에는 USING과 WITH CHECK를 모두 적용하고, 삭제 권한은 일반 앱 역할에 주지 않는다.

15. 필수 검증 항목

Schema·마스터

  • 현재 local schema에서 migration 성공
  • 잘못된 상태·가격·revision·자식·구간 거부
  • 같은 fingerprint 릴리즈 중복 없음
  • 중복 코드는 실패, 중복 이름은 경고 가능
  • release 2에서 미수정 자동 업데이트·수정 행 검토

보안

  • 브라우저의 master 직접 접근 거부
  • 비로그인·비활성·다른 병원 접근 거부
  • 일반 직원의 카탈로그·세트 관리 거부
  • 클라이언트 가격·snapshot·펼치기 결과 거부

개별·검사 오더

  • 청구 오더의 가격 null 활성화 거부
  • 명시적 0원 무료 허용
  • 확정 시 최신 병원 행 재조회·snapshot
  • 패널 결과 여러 개지만 오더·청구 행 하나

Order Set

  • 부모→자식 세트→개별 오더 성공
  • 3계층·순환·다른 병원·중복 원자 오더 실패
  • 진료 수정이 프리셋에 역반영되지 않음
  • 세 가격 방식 이중 청구 없음
  • 자식 revision 2가 부모의 고정 revision 1을 변경하지 않음
  • 새 부모 revision 이후에도 과거 snapshot 유지
