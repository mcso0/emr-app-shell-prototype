3. 승욱과 확정한 결정

주제확정 방향

데이터 계층CLAiR 공통 마스터 → 병원별 복사본 → 진료 시점 고정 기록.

새 CLAiR 항목사용 대기로 자동 추가하고 사용자에게 알린 뒤 병원이 활성화한다.
폐기자동 삭제하지 않고 대체 항목과 함께 알리며 병원이 전환한다.
긴급 안전 조치예외적으로 신규 사용만 즉시 차단할 수 있으나 이유·승인·감사를 필수로 남긴다.
대상 동물개·고양이 우선. 기타 반려동물은 컬럼 추가 없이 확장 가능하게 한다.
식별자CLAiR 내부 ID가 기준. VetSCT·LOINC·ATCvet 등은 선택적 매핑이다.
이름국문 필수, 영문 선택, 동의어·약어·과거 이름 다중 지원.
승인초안→검토→배포→폐기 흐름. 임상값은 수의학 전문가 검토가 필요하다.
초기 데이터기존 Airtable 데이터는 없다. 먼저 비권위 구조·합성 데이터로 시스템을 검증하고, 임상 주장은 검증된 출처와 임상 검토를 갖춘 뒤 추가한다.
PDF 코드A 행위 구분, X/T 분류, CG 화면 그룹, NT 업무 전달을 분리한다. A는 오더의 필수 의미이지만 오더 ID나 오더 세트를 대체하지 않는다.
A 분리·통합임상 행위·오더 유형·임상 목적·측정 또는 수행 대상이 같을 때만 같은 A를 사용한다. 이름·가격·포장·제공 구성 차이만으로는 A를 나누지 않는다.
A코드 형식DB 기본키는 UUID, 업무용 코드는 자동 생성한 A000001 형식으로 분리한다. 코드는 변경·재사용하지 않고 서비스에는 검토된 이름을 우선 표시한다.
병원 자체 오더의 A1단계에서는 기존 A 또는 유형별 기타/미분류 A를 선택한다. 새 A 배포 후에도 자동 변경하지 않고 병원이 확인해 다시 연결한다.
Order Set 구성병원 소유로 관리한다. 1단계에서는 부모 세트 → 자식 세트 → 개별 오더의 최대 2개 세트 계층만 허용하고, 개별 오더로 펼친 결과의 순환·중복을 거부한다.
Order Set 구성원 상태구성원이 없거나 병원에서 사용 중지되면 구성 검토 상태로 바꾸고 신규 적용을 막는다. 일반 CLAiR 폐기는 경고만 하고 활성 병원 복사본을 강제 중지하지 않으며, 긴급 안전 차단은 즉시 신규 적용을 막는다. 과거 기록은 바꾸지 않는다.
Order Set 가격진료용 선택 묶음이면서 병원 선택에 따라 패키지 가격도 가질 수 있다. 기존의 포함 오더 합산·세트 고정금액·구간별 금액을 유지하고 가격 방식에 따라 하위 청구 기본값을 자동 설정한다. 1단계에는 별도 패키지 테이블을 추가하지 않는다.
차트 적용본 수정차트에는 해당 진료가 소유하는 적용 복사본을 만든다. 의료진은 확정 전 개별 오더 선택·추가와 허용된 수량을 바꿀 수 있지만 병원관리의 Order Set 프리셋 원본에는 절대 역반영하지 않는다. 1단계에는 필수·잠금 구성원을 만들지 않는다.
차트에서 프리셋 만들기1단계에서는 차트 적용본을 새 프리셋으로 저장하지 않는다. 재사용 프리셋의 생성·복제·revision은 병원관리에서만 수행하며, 반복 요구가 확인되면 나중에 관리자 검토용 후보 제안을 추가할 수 있다.
빈 Order Set구성 오더 없이 기본 정보만 저장할 수 있지만 기존 사용 여부를 자동으로 끈다. 별도 초안 관리 기능은 만들지 않으며, 유효한 개별 오더가 하나 이상 있고 구성·가격 검증을 통과한 뒤에만 활성화하고 차트에 노출한다.
1단계 Order Set 완료 기준차트에서 유효한 세트를 선택·펼치기·진료별 수정·확정하고, 스냅샷·업무 전달·수납까지 실제 동작해야 1단계가 완료된다. 같은 1단계 안에서 개별 오더 기반을 먼저 안정화한다.
Order Set revision안정적인 세트 ID와 변경 불가능한 revision을 분리한다. 유효한 관리자 수정은 미래 적용용 새 revision을 만들고 과거 적용 기록은 사용한 revision을 그대로 보존한다.
중첩 세트 업데이트부모는 검토한 자식 세트 revision을 고정 참조한다. 자식 변경은 부모를 자동 변경하지 않고 업데이트 검토를 만들며, 관리자가 반영하면 새 부모 revision을 만든다.
Order Set 삭제세트와 revision은 일반적으로 삭제하지 않는다. 비어 있거나 잘못된 작업은 명시적으로 사용 중지한 상태로만 저장하고 검증을 통과하기 전에는 활성화하지 않는다.
병원 오더 원본order_catalog_items를 미래의 유일한 병원 오더 원본으로 사용한다. service_*는 호환·이전용이며 별도 작성 원본으로 운영하지 않는다.
마스터 DB 물리 구조비공개 master schema에 공통 ID·상태 registry인 master.master_records와 유형별 1:1 상세 테이블을 둔다. 병원 복사본은 현재 앱 schema에 둔다.
수정 복사본 병합수정 필드 목록은 비교에 쓰되, 1단계 자동 병합은 행 단위로 보수적으로 처리한다. 수정된 행은 일부 필드도 자동 반영하지 않고 전체 업데이트를 검토하게 한다.
revision·릴리즈레코드 revision은 정수, 릴리즈 ID는 시스템 자동 생성값으로 관리한다. Airtable에서 직접 입력하지 않고 검증된 서버 배포기가 부여한다.
중복 판단ID·키·코드만 강한 유일성을 적용한다. 이름 중복은 허용하며 유사 이름은 경고·검토 대상으로 표시하고 자동 병합하지 않는다.
초기 A 목록1단계 검증 오더에 실제 필요한 A와 사용 유형별 기타/미분류 A만 만든다.
1단계 가격CLAiR 권위 가격은 제공하지 않는다. 병원이 가격을 정하고, 미설정과 명시적 0원·무료를 구분한다. 청구 오더는 가격 미설정 상태로 활성화할 수 없다.
Lab Panel검사 패널은 하나의 개별 검사 오더가 생성할 결과 항목 묶음이다. 패널 구성 검사는 별도 차트·청구 오더가 아니며, 독립 오더 묶음은 Order Set이 담당한다.
정상범위구조와 검증기는 만들 수 있지만 출처·임상 검토가 없는 정상범위는 사용자에게 배포하지 않는다. 합성값은 숨겨진 시스템 테스트에서만 사용한다.
초기 데이터 목적먼저 새 마스터 복사·업데이트·오더·세트·스냅샷·업무·수납 동작을 검증한다. 수의학적 정확성은 다음 우선순위이며 미검토값을 임상 검증값처럼 표시하지 않는다.
1인 운영구조·합성 검증 데이터는 한 명의 CLAiR 운영자가 작성·검토·배포할 수 있지만 행위자·시각·출처·사유를 남긴다. 임상 주장은 실제 수의사 검토 없이는 검토 완료로 표시하지 않는다.
유형별 상세공통 오더와 약품·검사·영상 상세를 분리하고 중요한 값은 구조화한다.
병원 항목 제안후보 제출은 가능하지만 자동 승격하지 않는다. 승인 시 새로운 CLAiR ID를 만든다.

5. 설계 원칙

  1. 이름은 바뀔 수 있지만 CLAiR ID는 재사용하거나 의미를 바꾸지 않는다.
  2. CLAiR 원본, 병원 복사본, 진료 기록은 서로 다른 소유자와 수명주기를 갖는다.
  3. 마스터 변경이 과거 기록을 바꾸지 않는다.
  4. 일반적인 삭제 대신 사용 중지·폐기·대체 관계를 사용한다.
  5. 임상 분류, 화면 그룹, 업무 전달, 수납 규칙을 하나의 코드에 섞지 않는다.
  6. 검사 단위·정상범위·투여경로 같은 중요 값은 구조화한다.
  7. 동물별 규칙은 관계로 표현하고 종마다 컬럼을 추가하지 않는다.
  8. 외부 표준은 CLAiR ID에 연결하는 버전형 매핑으로 사용한다.
  9. 임상 의미·용법·정상범위·케어가이드는 전문가 검토 없이 배포하지 않는다.
  10. 작고 검토 가능한 릴리즈로 확장한다.
  11. 병원 경계는 UI가 아니라 서버와 DB 권한으로 보호한다.
  12. 이 문서만으로 기존 테이블을 삭제·이름 변경·원격 적용하지 않는다.
  13. 같은 의미를 사람이 두 필드에서 각각 수정하지 않는다. 호환 필드는 한 원본에서 자동 생성한다.
  14. CLAiR 마스터는 정규화하고, 병원 복사본과 진료 스냅샷만 출처를 남긴 채 의도적으로 중복 저장한다.

6. 3개 데이터 계층

① CLAiR canonical master

  • CLAiR 중앙 소유
  • 초안·검토 데이터 비공개
  • 배포된 버전만 병원 제공
  • 안정적인 내부 ID와 버전 이력

② Workspace catalog

  • 한 병원 workspace 소유
  • 병원 표시명·가격·사용 여부
  • 내부 지시·장비 매핑·병원별 프리셋
  • CLAiR 복사본 또는 병원 자체 항목
  • 병원 소유 Order Set과 최대 2개 세트 계층
  • 1단계에는 오더별 CG·NT 예외 없음
  • 맞는 A가 없으면 유형별 기타/미분류 A 사용

③ Applied snapshot

  • 진료·오더·처방·결과·수납 소유
  • 당시 이름·가격·단위·업무 전달 보존
  • 마스터 변경 후에도 독립적으로 읽힘
  • 원본 ID·버전은 추적용

PDF에 있는 내용과 없는 내용

PDF는 A ⊂ T ⊂ X, 오더와 A의 연결, 행위 구분으로 오더 유형을 식별하는 규칙, CG의 차트 표시 역할, NT의 다음 업무 역할을 설명한다. 유형별 부가정보 연결은 별도이며 필요하지 않은 오더에는 없을 수 있다. 코드 유일성·허용 조합·버전은 정하지 않았으므로 CLAiR 구조에서 추가로 검증한다.

Airtable에서는 Code Dictionary로 X/T/A/CG/NT 초안을 관리하고, Classification Paths에서 허용 조합을 만든다. Airtable 룩업은 편집·검토용일 뿐이며, 배포기가 참조를 검증해 PostgreSQL의 정규화된 ID로 저장한다. 서비스는 Airtable을 직접 조회하지 않는다.

행위 구분 A

  • 배포된 모든 마스터 오더는 분류 경로를 통해 활성 행위 구분 하나로 연결된다.
  • 하나의 행위 구분을 여러 정확한 마스터 오더가 공유할 수 있다. A는 “무슨 행위인가”, 오더 ID는 “정확히 어느 상품·항목인가”를 답한다.
  • 오더 세트는 병원이 여러 오더를 묶은 별도 구성이고 A를 부여하지 않는다.
  • A코드는 UUID와 분리된 자동 생성 A000001 형식이며 변경·재사용하지 않는다. 서비스에는 코드보다 검토된 국문명·영문명·별칭을 사용해 표시·검색·필터·분석한다.
  • 오더 유형은 A에서 한 번만 정한다. 현재 categoryGroup은 여기에서 자동 생성하며 PDF의 CG와 섞지 않는다.
  • A는 T 하나에, T는 X 하나에 속한다. T·X 이름을 A에 다시 입력하지 않고 관계로 해석한다.
  • 임상 행위·오더 유형·임상 목적·측정 또는 수행 대상이 같을 때만 같은 A를 공유한다. 표시명·가격·포장·제공 구성만 다르면 A를 나누지 않고, 분석물·시술·대상·목적이 다르면 별도 A로 나눈다.
  • 병원 자체 오더는 기존 A를 선택한다. 맞는 A가 없으면 유형별 기타/미분류 A로 우선 사용하고 신규 A 후보를 제안할 수 있다. 새 A가 배포되면 알림과 수동 재연결 선택을 제공하며 자동 변경하지 않는다.
  • 유형별 부가정보는 정확한 오더에 선택적으로 연결한다. 임상병리 유형이어도 세포검사·검체 채취처럼 부가정보가 없을 수 있다.
  • 1단계에서는 A마다 활성 분류 경로 하나만 허용하고, 실제 예외가 생길 때까지 오더별 CG·NT 예외를 만들지 않는다.

공통 오더에 들어가는 정보

  • 표준 ID와 행위 구분·오더 유형을 해석하는 검증된 분류 경로 한 개
  • 기본 업무 전달과 Task 생성 여부
  • 기본 판매 단위와 수납 반영 여부
  • 일반 케어가이드·내부 지시 연결
  • 행위 유형에 맞는 선택적 부가정보 연결

1단계에는 CLAiR의 권위 있는 기본·추천 가격을 제공하지 않는다. 병원 가격이 실제 운영의 기준이고, 과거 수납은 적용 스냅샷이 기준이다. 목표 구조는 가격 미설정과 명시적 0원·무료를 구분하며, 청구 대상 오더는 병원이 가격을 의도적으로 정하기 전에는 활성화할 수 없다.

A는 오더 ID를 대체하지 않는다. canonical 오더는 분류 경로를 통해 A를 한 번만 참조하고, 서비스 읽기값과 병원 복사본은 출처를 남긴 채 코드·이름을 자동 생성할 수 있다.

병원 Order Set 구성

PDF에는 개별 오더 항목은 있지만 Order Set 테이블, 세트 중첩 관계, 펼치기 규칙은 없다. 따라서 Order Set은 CLAiR canonical 마스터가 아니라 병원 workspace가 소유하는 별도 구성으로 둔다.
목표 테이블역할

  • 세트 구성원은 같은 workspace의 개별 order_catalog_items 또는 자식 Order Set 하나를 참조할 수 있다.
  • 1단계는 부모 세트 → 자식 세트 → 개별 오더까지만 허용한다. 세 번째 세트 계층은 허용하지 않는다.
  • 적용 전 허용된 구조를 재귀적으로 펼쳐 개별 오더를 만든다.
  • 자기 자신 참조, 순환 참조, 다른 workspace 참조, 펼친 결과의 같은 개별 오더 중복을 거부한다. 자동으로 중복 제거하지 않는다.
  • 세트는 자체 workspace ID·사용 상태·구성 revision을 갖지만 A 행위 구분이나 A코드를 갖지 않는다.
  • 병원관리에서 유효하게 수정할 때마다 미래 적용용 새 revision을 만든다. 안정적인 세트 ID는 최신 활성 revision을 가리키고 과거 revision과 적용 스냅샷은 변경하지 않는다.
  • 부모 revision은 검토한 자식 세트 revision을 고정 참조한다. 자식 revision이 바뀌면 부모 업데이트 검토를 알리지만 자동 반영하지 않으며, 관리자가 갱신하면 새 부모 revision을 만든다.
  • 세트와 revision은 일반적으로 삭제하지 않는다. 비어 있거나 유효하지 않은 수정은 명시적인 사용 중지 확인 후 비활성 상태로만 저장하며 현재 활성 revision을 대체하거나 차트에 노출할 수 없다.
  • 적용 시 원본 세트 ID·revision·부모-자식 계층과 펼쳐진 개별 오더 스냅샷을 보존한다.
  • 마스터나 병원 오더가 나중에 바뀌어도 이미 적용한 세트 기록은 바뀌지 않는다.
  • 구성원을 찾을 수 없거나 병원에서 사용 중지했다면 세트를 needs_composition_review로 바꾸고, 구성을 고칠 때까지 신규 적용을 막는다.
  • CLAiR 원본의 일반 폐기는 경고를 표시하되 병원 복사본이 활성 상태라면 자동 중지하지 않는다. 병원이 기존 폐기 전환 정책에 따라 전환 시점을 정한다.
  • 긴급 안전 차단은 병원 사용 상태보다 우선하며 해당 오더가 포함된 모든 세트의 신규 적용을 즉시 막는다. 모든 경우에 과거 적용 기록은 그대로 읽을 수 있다.
  • 세트는 우선 진료용 선택 묶음이지만 병원이 원하면 청구 가능한 패키지로도 사용한다. 1단계는 현재 구조의 included_order_sum, set_fixed_price, range_price 세 방식을 유지한다.
  • 포함 오더 합산은 청구 대상으로 표시한 개별 오더만 합산하고 부모 세트 금액을 추가하지 않는다.
  • 세트 고정금액은 병원이 정한 세트 금액을 청구한다. 하위 오더 청구는 기본 해제하고 명시적으로 선택한 추가 항목만 더한다.
  • 구간별 금액은 적용 시점 문맥에서 병원이 정의한 구간 금액을 선택한다. 하위 오더는 고정금액과 동일하게 명시적 추가 항목만 더한다.
  • 고정·구간 가격은 세트 과세를 사용한다. 포함 오더 합산은 각 오더의 과세를 유지하고 서로 섞이면 수정 가능한 세트 과세값 대신 혼합으로 자동 표시한다.
  • 적용 시 가격 방식, 세트·구간 금액, 하위 단가·수량·청구 여부·과세, 최종 금액을 모두 스냅샷으로 보존한다.
  • 관리 화면은 가격 계산 방식을 사용하고, 청구서 세트명 표시·케어가이드 전달·하위 금액 반영을 서로 다른 의미로 표시한다. 가격 방식에 따른 기본값은 자동 설정해 이중 청구를 막는다.
  • 1단계에는 별도 패키지 마스터나 테이블을 만들지 않는다. 환불·금액 배분·회계·정산의 별도 요구가 실제로 생길 때 재검토한다.
  • 차트에서 세트를 선택하면 해당 진료가 소유하는 적용 복사본을 만들고, 확정 전 펼쳐진 개별 오더를 보여준다. 차트는 병원관리의 프리셋이나 구성 행을 직접 수정하지 않는다.
  • 적용본은 각 구성원의 defaultSelected, defaultQuantity, 수량 출처를 초기값으로 사용한다. 의료진은 개별 오더를 선택·해제·추가하고 해당 오더가 허용하는 수량을 조정할 수 있다.
  • 1단계에는 필수·잠금 구성원을 만들지 않는다. 개별 오더를 최소 한 개 선택해야 하며 실제 선택과 수량을 스냅샷에 저장한다.
  • 포함 오더 합산은 선택·수량 변경에 따라 다시 계산한다. 고정·구간 가격은 정해진 세트 금액을 유지하고 명시적인 추가 청구 오더만 총액을 바꾼다.
  • 차트 적용본의 변경은 프리셋에 자동 저장·학습·역반영하지 않는다. 프리셋을 바꾸려면 병원관리에서 별도로 편집하고 새 구성 revision을 만들어 이후 적용분에만 사용한다.
  • 1단계 차트에는 새 프리셋으로 저장을 제공하지 않는다. 재사용 세트의 생성·복제·수정은 병원관리에서만 수행해 관리 권한·검증·변경 이력을 한곳에 둔다.
  • 반복되는 요구가 실제로 확인되면 차트에서 관리자 검토용 프리셋 후보를 제안할 수 있지만, 차트가 직접 프리셋을 배포하거나 바꾸지는 않는다.
  • 병원관리에서는 구성원을 추가하기 전에도 세트 기본 정보를 저장할 수 있지만 기존 사용 여부를 끈 상태로 저장한다. 1단계에는 별도 초안 상태나 초안 관리 흐름을 추가하지 않는다.
  • 새 빈 세트는 기본적으로 사용할 수 없고 차트 검색·적용에 나타나지 않는다. 펼친 결과에 유효하고 선택 가능한 개별 오더가 하나 이상 있으며 구성·가격 검증을 모두 통과해야 활성화할 수 있다.
  • 1단계는 차트에서 활성 세트를 실제 선택하고, 진료 소유 적용본으로 펼쳐 수정·확정한 뒤 스냅샷·업무 전달·수납까지 처리할 수 있어야 완료된다. 같은 1단계 안에서 1A 개별 오더 기반을 먼저 만들고 1B에서 세트 런타임을 연결한다.
  • 현재 런타임과 DB는 직접 child_order_id만 지원한다. 2계층 세트는 별도 migration과 서비스 도입 작업이 필요하며 이 문서 변경만으로 구현된 것은 아니다.

15. 병원 복사·수정 모델

현재 public.order_catalog_items는 병원별 오더 카탈로그의 기반으로 유지한다. 목표 구조는 즉시 이름을 바꾸는 것이 아니라 출처·수정·업데이트 의미를 보강한다.

필드의미
origin_typeclair_master 또는 workspace_custom
source_master_record_idCLAiR 원본. 병원 자체 항목은 없음
source_master_revision현재 복사본이 반영한 원본 버전
initial_imported_revision처음 복사한 버전
last_auto_merged_revision마지막 자동 병합 버전
customization_stateunmodified·customized·detached
customized_fields병원이 수정한 필드 목록
merge_status최신·업데이트 있음·충돌·원본 폐기·분리
availability_status사용 대기·사용·일시 중지·비활성

1단계 병합은 행 단위로 보수적으로 처리한다. customized_fields는 차이를 설명할 수 있지만, customization_state = customized인 행은 일부 필드도 자동 병합하지 않고 전체를 보존한 채 업데이트 검토를 만든다. 필드별 자동 병합은 충돌 동작과 화면을 검증한 뒤 추가한다.

업데이트 검토와 알림

  • workspace_master_updates: 병원별 새 항목·변경·폐기·대체·긴급조치 상태
  • workspace_master_update_diffs: 원본·현재 병원값·새 값 비교
  • 기존 notification_events: 사용자가 업데이트 검토 화면으로 들어가는 알림

알림이 필요한 경우는 새 항목, 업데이트 있음, 충돌, 폐기·대체, 긴급 안전 차단이다.

  2. 안정적인 원본 ID로 병원 복사본을 찾는다.
  3. 새 항목은 사용 대기로 한 번만 복사하고 알린다.
  4. 병원이 수정하지 않은 복사본은 안전하게 자동 업데이트한다.
  5. 병원이 수정한 복사본은 행 전체를 보존하고 비교·선택 상태로 둔다. 필드별 자동 병합은 하지 않는다.
  6. 병원 자체 항목은 무시한다.
  7. 같은 릴리즈를 다시 실행해도 중복되지 않아야 한다.

18.1 필드별 원본·자동생성·병원수정·스냅샷

아래 표는 현재 서비스 필드, PDF 코드, 앞으로 만들 마스터 필드, 병원 수정값이 서로 같은 값을 따로 관리하지 않도록 기준을 정한 것이다.

의미 현재 CLAiR 필드 마스터 원본 병원 복사 시 자동 생성 병원 수정 진료 시점 스냅샷 상태·무결성 규칙
표준 오더 ID standardOrderId master.orders의 안정적인 키·ID 출처 필드와 현재 호환 필드에 같은 원본 ID를 복사 마스터 복사본은 불가. 병원 자체 항목은 별도 로컬 ID 생성 마스터 ID·버전과 병원 카탈로그 ID 확정. 한 ID를 다른 의미에 재사용하지 않음
병원 복사본 ID id, workspaceId 없음 복사하거나 병원이 만들 때 한 번 생성 불가 병원 카탈로그 ID 확정. 마스터 복사본은 workspace + source master 조합당 하나
Order Set ID·구성 order_sets, order_set_items 1단계 canonical 원본 없음. 병원 소유 canonical 복사 없음. 같은 workspace의 세트·오더 참조와 구성 revision 계산 최대 2개 세트 계층 안에서 가능 세트 ID·revision·부모-자식 계층·펼쳐진 개별 오더 확정 목표. 순환·3번째 세트 계층·다른 workspace·개별 오더 중복을 거부. 구성원 누락·병원 사용 중지는 구성 검토, 긴급 안전 차단은 신규 사용 차단. 현재 저장 구조는 migration 전까지 1단계
Order Set 가격·청구 amountBasis, setPriceKrw, 세트·하위 청구/수량/단가 필드 없음. 병원 패키지 가격은 CLAiR 마스터 소유가 아님 가격 방식별 청구 기본값과 화면 총액·과세 요약 계산 가능. 병원이 방식·금액/구간·하위 청구·해당 과세를 결정 방식, 세트/구간 금액, 하위 단가·수량·청구·과세, 최종 금액 확정. 합산은 선택 하위만, 고정·구간은 세트와 명시적 추가 하위만 청구. 혼합 과세는 자동 계산. 1단계 별도 패키지 테이블 없음
차트 적용 Order Set 선택 defaultSelected, defaultQuantity, quantitySource, 차트 적용 행 병원 프리셋은 초기값만 제공 진료 소유의 작업 복사본으로 펼침 해당 진료에서만 선택·개별 오더 추가·허용 수량 변경 가능 실제 오더·수량·원본 세트/revision·변경 결과 확정. 개별 오더 최소 하나 필요. 1단계 필수·잠금과 차트의 새 프리셋 저장 없음. 적용 변경은 프리셋을 생성·수정하지 않고 프리셋 생성·복제·revision은 병원관리에서만 수행
오더 유형 categoryGroup의 ServiceItemType master.clinical_actions.item_type 현재 categoryGroup을 자동 생성 필드 직접 수정 불가. 병원 자체 항목은 유효한 행위 구분·경로 선택 적용된 유형 코드·이름 확정된 호환 필드. PDF의 CG가 아니며, 부가정보가 있으면 이 유형과 일치해야 함
X 분류 전용 필드 없음. 현재 categoryLabel 의미는 혼재 선택된 A의 T 부모를 통해 해석한 X 부모 A → T → X 관계로 코드·이름을 해석하고 필요한 호환 표시값 생성 1단계 오더별 예외 없음. 병원 자체 항목은 유효한 경로 선택 X 코드·이름 확정. 코드와 이름을 따로 수정하지 않음
T 분류 tCode, tCodeLabel 선택된 A의 T 부모 A → T 관계에서 두 필드를 함께 생성 1단계 오더별 예외 없음 T 코드·이름 확정. Code Dictionary가 이름의 유일한 원본
A 행위 구분 없음 선택된 분류 경로의 필수 master.clinical_actions 참조 별도 행위 참조와 읽기용 코드·이름을 단계적으로 추가. categoryGroup·tCode 재사용 금지 마스터 복사본 직접 수정 불가. 병원 자체 항목은 기존 A 또는 유형별 기타/미분류 경로 선택 적용한 A 코드·검토된 이름 확정. 병원은 canonical A를 만들지 않으며 새 A가 배포돼도 병원 확인 없이 자동 재연결하지 않음
CG 화면 그룹 전용 필드 없음 선택된 classification_path의 CG 차트가 도입할 때 CG 전용 읽기값 생성. categoryGroup 재사용 금지 1단계 오더별 예외 없음 적용된 CG 코드·이름 초기 8종 확정. 전체·수납은 CG가 아님

정규화·무결성 통과 조건

  1. X/T/A/CG/NT 코드는 코드 종류 + 코드 조합으로 중복될 수 없고 다른 의미로 재사용하지 않는다.
  2. A는 오더 유형 하나와 T 부모 하나를 갖고, T는 X 부모 하나를 갖는다. T·X 이름을 A에 수정 가능한 값으로 복사하지 않는다.
  3. 분류 경로는 A·CG·NT의 ID를 참조한다. 해석된 X/T/A/CG/NT 조합은 중복될 수 없고, 1단계에서는 A마다 활성 경로 하나만 허용한다.
  4. 배포된 오더는 유효한 분류 경로 하나만 갖는다. 여러 오더가 같은 A·경로를 공유할 수 있지만 오더 세트에는 A를 부여하지 않는다.
  5. 없는 코드, 사용 중지·폐기·보류 코드를 참조한 경로는 배포할 수 없다. 입원 NT는 연동 전까지 활성 경로에서 금지한다.
  6. 오더 유형, 선택적 유형별 상세, NT, 수납 정책의 조합을 배포 전에 검사한다. 유형이 맞더라도 부가정보가 불필요하면 빈 상세 레코드를 만들지 않는다.
  7. 자동 생성 필드가 원본과 다르면 배포나 병원 복사를 거부한다.
  8. 마스터 복사본은 workspace + source master 조합당 하나다. 재실행은 새 행을 만들지 않는다.
  9. 마스터 원본과 병원 수정값을 비교할 수 있게 분리한다. 수정된 병원값을 자동 업데이트로 덮지 않는다.
  10. 배포된 revision과 진료 스냅샷은 변경하지 않는다.
  11. Airtable은 사람이 보기 쉬운 편집·검토 화면이고, 검증된 배포기만 ID·버전·자동생성값·릴리즈를 쓴다.
  12. 유형별 기타/미분류 A는 정상적인 임시 분류로 사용하되 검토 대상으로 보이고, 새 A가 생겨도 자동 변경하지 않는다.
  13. Order Set은 같은 workspace 안에서 최대 2개 세트 계층만 가지며 순환 없이 사용 가능한 개별 오더로 펼쳐져야 한다. 같은 개별 오더가 두 번 나오면 자동 제거하지 않고 거부한다.
  14. 구성원이 없거나 병원에서 사용 중지되면 구성을 다시 확인할 때까지 세트 적용을 막는다. 일반 원본 폐기는 활성 병원 복사본을 강제 중지하지 않지만 긴급 안전 차단은 포함 세트의 신규 사용을 즉시 막으며 과거 기록은 바꾸지 않는다.
  15. Order Set 적용에는 하나의 가격 계산 원본만 존재한다. 합산 방식은 세트 금액을 함께 청구할 수 없고, 고정·구간 방식은 명시적 추가 항목이 아닌 하위 오더를 함께 청구할 수 없다. 과세와 최종 금액은 선택한 방식과 스냅샷 입력값에서 계산한다.
  16. 차트의 Order Set 수정은 진료 소유 적용본에서만 수행한다. 개별 오더 최소 하나를 포함해 유효성을 확인하고 실제 선택·수량·가격을 스냅샷한 뒤 확정하며, 병원 프리셋이나 구성 revision은 바꿀 수 없다.
  17. 1단계 차트는 Order Set 프리셋을 생성·복제·배포·수정할 수 없다. 모든 재사용 프리셋 변경은 병원관리 권한과 감사 경계를 통과한다.
  18. 빈 Order Set은 기존 사용 여부를 끈 상태로만 저장할 수 있다. 유효한 개별 오더가 하나 이상 있고 구성·가격 검증을 통과해야 활성화할 수 있으며, 비활성 세트는 차트에서 검색하거나 적용할 수 없다.
  19. 유효한 Order Set 수정은 새 변경 불가능한 revision을 만든다. 안정적인 세트 ID는 이후 적용에 사용할 활성 revision을 가리키고 이전 revision과 진료 스냅샷은 변경하지 않는다.
  20. 부모 revision은 특정 자식 세트 revision을 참조한다. 자식 업데이트는 부모 검토를 만들고 자동 전파하지 않으며, 수락하면 새 부모 revision을 만든다.
  21. order_catalog_items가 미래의 유일한 병원 오더 작성 원본이다. service_*는 매핑된 호환값 또는 이전 입력일 뿐 별도 카탈로그로 작성할 수 없다.
  22. 기술 ID·안정 키·코드는 유일하다. 표시명·수납명·국문·영문·별칭·과거 이름은 유일하지 않으며 유사 이름은 경고·검토만 만들고 자동으로 같은 ID로 합치지 않는다.
  23. 병원 가격은 미설정과 명시적 0원·무료를 구분한다. 가격이 없는 청구 오더는 활성화할 수 없고 0원은 병원이 의도적으로 저장했을 때만 유효하다.
  24. 검사 패널은 한 개별 검사 오더 안의 결과 항목으로만 펼친다. 별도 차트 오더·청구 행을 만들지 않으며 독립 오더 조합은 Order Set으로 만든다.
  25. 수정된 병원 행은 1단계 동기화에서 전체를 보존한다. 필드 차이는 보여줄 수 있지만 병원이 검토를 수락하기 전에는 일부 필드도 자동 병합하지 않는다.
이 문서가 생겼다는 이유만으로 현재 테이블을 이름 변경·삭제·소유권 변경하지 않는다. 영역별 도입 계획과 검증을 거친다.

19. 단계별 구현 순서

0

아키텍처와 데이터 거버넌스

목표 구조 승인, 역할 정의, 출처·중복 규칙, 필드 원본 매핑 유지, 검증 오더에 필요한 A와 유형별 기타/미분류 A만 준비, 작은 검증 데이터셋.

1A

개별 오더 기반

ID·이름·버전·출처·외부 코드·릴리즈·검토, 종·단위·검체·결과 유형, 확정된 A와 오더 역할 분리, 표준 개별 오더, 병원 복사·업데이트·알림, 개별 오더 CRUD·차트 검색·확정 스냅샷·업무 전달·수납.

임상병리와 실제 Order Set 런타임

2

성분·제품·구성·오더 프로필·검토된 종별 기본값·백신 차수와 처방 스냅샷 연결.

3

영상·기타검사

modality·신체부위·검사 정의·선택지·병원 장비와 전달 설정. 파일·수동 흐름부터 시작.

표준 진단·분류·동의어·케어가이드, 자유입력 호환, 품종과 기타 반려동물 확대.

5

상호운용성과 다지점 운영

승인된 외부 표준, FHIR/LOINC/VetSCT/ATCvet/UCUM/DICOM 운영, 실제 요구가 확인된 조직·지점 공유, CSV·품질 보고·충돌 해결.

20. 초기 데이터 구축 원칙

기존 Airtable 원본은 없다. 따라서 초기 마스터는 이전이 아니라 새로 검토해 만드는 데이터다.

  • 첫 우선순위는 마스터 복사·업데이트·오더·Order Set·스냅샷·업무 전달·수납 구조가 실제 동작하는지 검증하는 것이다. 임상 정확성과 범위 확장은 다음 데이터 구축 우선순위다.
  • 개별 오더 20–40개, 해당 오더에 필요한 A와 유형별 기타/미분류 A, 검사 패널 2개, 중첩 세트 1개를 포함한 Order Set 3–5개로 제한한다.
  • 병원 2개를 사용한다. 한 병원은 원본을 유지하고 다른 병원은 일부를 수정한다. 마스터 릴리즈 2개로 복사·재실행·자동 업데이트·알림·수정 행 검토를 확인한다.
  • 동물은 개·고양이로 제한하고 외부 용어 대량 가져오기, 실제 투약 권고, 임상적으로 맞다고 주장하는 정상범위는 포함하지 않는다.
  • 제품 검증에는 합성·데모 안전 데이터를 사용하고 비권위 데이터임을 표시한다. 숨겨진 fixture는 검증기를 시험할 수 있지만 사용자 화면에서 임상 정답처럼 보이면 안 된다.
  • 임상 주장에는 출처와 검토자를 기록한다.
  • PDF 예시값은 구조 참고용이며 검증된 사실로 취급하지 않는다.
  • 병원 자체 항목은 자동으로 CLAiR 표준이 되지 않는다.
  • 병원이 후보를 제출하면 검토 후 새로운 CLAiR ID를 만들 수 있다.
  • 승인된 표준이 생겨도 병원은 기존 자체 항목을 언제 전환할지 선택한다.

21. 보안·권한 원칙

  • CLAiR 원본과 검토 테이블은 기본적으로 Data API에 노출하지 않는다.
  • service-role·secret 자격증명을 브라우저에 노출하지 않는다.
  • 초안·검토·배포·동기화·폐기·긴급조치는 서버가 소유한다.
  • 병원 복사본·업데이트 검토·장비 매핑에는 workspace RLS를 적용한다.
  • 보호된 읽기는 활성 멤버십, 변경은 승인된 관리 권한을 요구한다.
  • 비로그인·멤버십 없음·비활성·다른 병원·일반 직원·관리자·CLAiR 운영자 경로를 검증한다.
  • UPDATE 정책에는 기존 행 조건과 변경 후 행 조건을 모두 적용한다.
  • 감사 로그에는 ID·버전·변경 필드·사유·결과만 남기고 개인정보·원문 차트·비밀값을 제외한다.
  • 1인 팀의 1단계에는 작성자·검토자·배포자 역할 UI를 따로 만들지 않는다. 한 운영자가 구조·합성 검증 데이터를 처리할 수 있지만 모든 단계의 행위자·시각·출처·사유를 남긴다.
  • 투약량·정상범위·케어가이드 등 임상 주장은 실제로 지명된 수의사가 검토했을 때만 임상 검토 완료로 표시한다. 실병원 배포 전까지 긴급 권한·대응 시간 운영은 보류한다.

22. 향후 구현 검증 시나리오

  1. 배포된 CLAiR 오더가 병원에 한 번만 사용 대기로 복사되고 알림이 생긴다.
  2. 초기화나 릴리즈 적용을 재시도해도 중복되지 않는다.
  3. 미수정 복사본은 안전하게 자동 업데이트된다.
  4. 수정된 복사본은 덮어쓰지 않고 업데이트 검토가 생긴다.
  5. 병원 자체 항목에는 CLAiR 자동 병합이 발생하지 않는다.
  6. 병원 후보는 검토·배포 전까지 표준으로 승격되지 않는다.
  7. 폐기 후에도 병원과 과거 기록이 남고 대체 항목이 보인다.
  8. 긴급 차단은 신규 사용만 막고 과거 기록을 보존한다.
  9. 이름·가격·단위·업무 전달 변경이 과거 진료 기록을 바꾸지 않는다.
  10. 다른 workspace의 읽기와 변경이 거부된다.
  11. 새 동물 종을 추가해도 모든 상세 테이블에 컬럼을 추가하지 않는다.
  12. 외부 코드 버전이 바뀌어도 CLAiR ID는 바뀌지 않는다.
  13. 정상범위는 문맥·단위·경계·출처·검토자 검증 후 배포된다.
  14. 국문·영문·동의어·약어·과거 이름과 병원 별칭을 구분해 검색한다.
  15. 배포된 분류 경로가 원본 T·NT와 다른 tCode·전달 위치·Task 여부를 만들 수 없다.
  16. 같은 마스터 릴리즈를 두 번 적용해도 병원-원본 행은 하나이고 병원 수정값은 보존된다.
  17. 여러 정확한 마스터 오더가 오더 ID를 공유하지 않으면서 같은 A를 공유할 수 있고, 각 오더는 A 하나로만 해석된다.
  18. 임상병리 유형 A라도 부가정보가 필요하지 않은 오더는 빈 상세 레코드 없이 배포할 수 있다.
  19. 서비스는 내부 코드를 주 표시명으로 노출하지 않고 검토된 행위 이름을 표시·검색·필터·스냅샷할 수 있다.
  20. 병원 자체 오더는 유형별 기타/미분류 A로도 사용할 수 있고, 새 canonical A가 생기면 알림과 수동 재연결 선택을 제공한다.
  21. 부모 Order Set은 자식 세트 한 계층을 거쳐 개별 오더로 펼쳐지고, 적용 기록에는 세트 revision과 계층이 보존된다.
  22. 순환 참조, 세 번째 세트 계층, 다른 workspace 구성원, 펼친 결과의 같은 개별 오더 중복은 적용 전에 거부된다.
  23. 구성원이 없거나 병원에서 사용 중지되면 구성 검토 상태가 되고 신규 적용이 막힌다. 일반 원본 폐기는 경고만 하며 긴급 안전 차단은 즉시 신규 사용을 막고, 과거 스냅샷은 유지된다.
  24. 세 가지 Order Set 가격 방식은 이중 청구 없이 설명 가능한 하나의 총액을 만들고, 계산 입력값과 과세 결과를 적용 스냅샷에 보존한다.
  25. 의료진은 한 진료의 펼쳐진 Order Set 선택과 허용 수량을 바꿀 수 있지만 원본 프리셋은 그대로 유지된다. 병원관리의 이후 프리셋 수정은 새 revision과 미래 적용분에만 영향을 준다.
  26. 차트에는 새 프리셋 저장 기능이 없고, 재사용 세트 생성·복제·revision은 적절한 관리 권한과 감사 기록을 갖춘 병원관리에서만 수행된다.
  27. 병원관리는 빈 Order Set의 기본 정보를 잃지 않고 저장할 수 있지만, 유효한 개별 오더와 활성화 검증을 갖추기 전까지 비활성 상태이고 차트 검색에 나타나지 않는다.
  28. 유효한 Order Set을 차트에서 선택·펼치고 진료 소유 적용본만 수정한 뒤 확정하면 변경 불가능한 오더 스냅샷, 후속 업무, 수납 후보가 생성되며 프리셋은 바뀌지 않는다.
  29. 자식 세트 새 revision을 배포해도 부모 revision은 바뀌지 않고 업데이트 검토가 생긴다. 관리자가 반영했을 때만 새 부모 revision을 만든다.
  30. 활성 Order Set 편집은 미래용 새 revision을 만들고 이미 적용한 진료는 정확히 이전 revision과 구성을 계속 읽는다.
  31. 수정된 병원 오더는 행 전체 업데이트 검토를 받고 명시적 수락 전까지 어떤 원본 필드도 일부 자동 병합되지 않는다.
  32. 오더 생성·확정은 order_catalog_items 한 원본을 추적하며 service_*가 별도 오더 버전을 만들 수 없다.
  33. 청구 오더의 가격 미설정은 활성화를 막고, 명시적 0원은 무료 의도로 감사·스냅샷에서 구분된다.
  34. 패널 연결 검사 오더는 여러 결과 입력칸을 만들지만 차트 오더와 청구 행은 하나다. 독립 오더는 Order Set으로만 묶는다.
  35. 병원 2개와 마스터 릴리즈 2개로 최초 복사·재실행·미수정 자동 업데이트·수정 행 검토·새 항목 알림·과거 스냅샷 보존을 확인한다.
  36. 합성 투약·정상범위·기타 임상 fixture는 사용자에게 임상 검토된 canonical 안내로 노출되거나 표시되지 않는다.
