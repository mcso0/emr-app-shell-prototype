요청 사항

DEN-18에서 확정한 역할·권한 요구사항을 바탕으로, 다음 구현에 들어가기 전 멤버십 데이터 모델, RLS 방향, 서버 보안 게이트, 감사 이벤트를 실제 현업 기준에 맞게 계획하는 작업이었습니다.

이번 작업은 구현 전 잠금 장치입니다. 실제 Supabase migration, RLS SQL, 서버 코드, 결제 연동, 이메일 발송은 아직 만들지 않았습니다.

결정 사항

1. 권한은 Supabase Auth가 아니라 앱 멤버십 테이블에서 판단

auth.users.id는 로그인 사용자 식별에만 쓰고, 워크스페이스 권한은 users, user_memberships, permission_policies에서 판단합니다.

2. 역할 중복은 허용하되 권한은 합집합으로 계산

user_memberships.roles를 배열로 두고, hospital_admin이 포함되면 전체 병원관리자 권한을 갖는 것으로 정했습니다.

3. 개인 프로필과 권한 source를 분리

사용자는 이름, 연락처, 아바타, 알림 선호를 수정할 수 있지만 역할·권한·멤버십 상태는 개인 프로필에서 바꿀 수 없습니다.

4. 마지막 병원관리자 보호는 서버에서 막아야 함

마지막 active hospital_admin을 제거하거나 강등하는 작업은 UI가 아니라 서버 transaction 또는 private RPC에서 차단해야 합니다.

테이블 계획

테이블 역할 주의점
workspaces 병원 운영 공간 생성자 created_by_user_id를 남겨 최초 관리자 흐름을 추적합니다.
workspace_subscriptions 구독/온보딩 상태 실제 결제 provider 연동은 후속 범위입니다.
users, user_profiles 앱 사용자와 개인 설정 프로필 데이터는 권한 source가 아닙니다.
user_memberships 워크스페이스 소속과 역할 roles text[]를 사용하고, active 멤버십만 접근 권한으로 인정합니다.
workspace_invitations 직원 초대 동일 워크스페이스·이메일의 pending 초대 중복을 막습니다.
permission_policies 역할별 권한 정책 role_permission_policies는 별도 테이블이 아니라 설명용 별칭으로 정리했습니다.

보안 기준

  • 사용자 수정 가능한 Supabase user_metadata는 권한 판단이나 RLS에 쓰지 않습니다.
  • Supabase Data API 노출 권한과 RLS는 별도 레이어로 관리해야 합니다.
  • RLS 정책은 TO authenticated를 명시하고, UPDATE에는 SELECT 정책도 같이 필요합니다.
  • View는 RLS를 우회할 수 있으므로 security_invoker 또는 비노출 schema 전략을 써야 합니다.
  • 서버 권한 resolver 없이 client UI gating만으로 보안 완료 처리하지 않습니다.
