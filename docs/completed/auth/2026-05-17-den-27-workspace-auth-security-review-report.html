대표 보고

승욱, 현재 구현은 MVP 프로토타입 단계에서는 방향이 맞다. 개인 프로필은 권한 원천으로 섞이지 않았고, 역할이 여러 개인 경우 권한을 합산하는 정책도 테스트로 확인된다. 다만 운영 제품으로 넘어가기 전에는 데모용 사용자 식별 헤더와 브라우저 저장소 기반 역할 변경을 반드시 서버 검증 흐름으로 교체해야 한다.

결론: 지금 당장 출시 가능한 보안 완성 상태는 아니지만, 위험한 부분이 어디인지 명확히 분리되어 있다. 다음 구현은 “Supabase 서버 세션 검증 → 역할 변경 API 연결 → DB 트랜잭션/RLS” 순서로 가는 것이 맞다.

Findings

심각도 상태/신뢰도 취약 지점 악용 시나리오 영향 보완 후속 이슈 제안
High Verified / High POST /api/workspaces/[workspaceId]/memberships/[membershipId]/roles가 현재 x-clair-demo-session-user-id 헤더를 actor identity로 사용한다. 실제 저장 기능이 붙은 뒤에도 이 헤더를 유지하면 호출자가 user-admin을 가장해 역할 변경 권한을 통과할 수 있다. 권한 상승, 구성원 역할 변경, 병원관리자 권한 탈취 가능성. 운영 경로에서는 Supabase server session으로 actor를 검증하고, 데모 헤더는 테스트/개발 환경에서만 허용한다. 05-03 Replace demo role-update identity header with verified Supabase server session
High Verified / High 병원구성원 역할 변경 UI는 아직 updateSessionWorkspaceMembershipRoles와 browser storage를 직접 사용한다. 브라우저 저장소를 조작하면 현재 세션 UI 상태의 역할/멤버십을 바꿀 수 있다. 프로토타입에서는 허용 가능한 데모 동작이지만, live persistence와 연결되면 안 된다. 관리 UI와 서버 권한 경계가 어긋나며, 운영자가 보안 완료로 오해할 위험. 역할 변경/비활성화 UI를 서버 라우트 또는 server action으로 연결하고, 서버 허용 후에만 클라이언트 상태를 갱신한다. 05-04 Route-backed role mutation UI handoff
Medium Verified / Medium 마지막 active hospital_admin 보호는 session helper와 server resolver 계약에는 있으나, 아직 DB transaction/RPC 보호는 없다. 라이브 DB에서 두 요청이 동시에 마지막 관리자 강등/비활성화를 시도하면, 단순 app-level 체크만으로는 race condition이 생길 수 있다. 워크스페이스가 관리자 없는 상태가 될 수 있음. live write 전 private RPC 또는 단일 서버 트랜잭션에서 row lock과 함께 마지막 관리자 보호를 강제한다. 05-05 DB transaction/RPC for last active hospital admin guard

확인된 안전 장치

  • 개인 프로필 저장소에는 role, role label, permission field가 저장되지 않는다.
  • 권한 판단은 개인 프로필이 아니라 workspace membership/role/resolver contract를 기준으로 한다.
  • 다중 역할은 additive union으로 계산되며, hospital_admin은 전체 권한을 갖는다.
  • technician과 front_desk는 chart:view는 가능하지만 chart:update는 없다.
  • 서버 역할 변경 enforcement module은 server-only이며 browser storage API를 사용하지 않는다.
