삭제가 아닌 보관으로, 구성원과 권한 이력을 안전하게 관리한다.

구성원 디렉터리의 정보 위계를 정리하고 구성원·권한 역할·직무의 lifecycle을 DB, API, 감사 로그, 관리 UI까지 연결했다.

로컬 구현 및 검증 완료 · 릴리스 승인 대기
3구성원 상태: 활성·비활성·보관됨
76관련 서버·migration·UI 검증 통과
1 transaction상태 변경과 감사 로그의 원자 처리

무엇이 달라졌나

  • 구성원 보관은 사유를 필수로 받고 기본 목록에서 제외하며, 복구 시 비활성으로 돌아온다.
  • 본인과 마지막 활성 소유자 조작, 비소유자의 소유자 조작을 서버와 DB에서 차단한다.
  • 역할 비활성화는 비보관 구성원과 대기 초대를 활성 대체 역할로 이동한다.
  • 직무 비활성화는 기존 구성원 이력을 유지하고 대기 초대만 대체 직무로 변경한다.
  • 역할·직무 화면은 서버 목록·생성·비활성·재활성 API를 사용한다.

UX 결과

  • 전체 / 초대 대기 / 비활성 / 보관됨 탭과 검색·직무·부서 필터를 유지했다.
  • 행 클릭과 키보드로 상세 Sheet를 열고, 상태에 맞는 작업만 더보기 메뉴에 노출한다.
  • 삭제·90일 영구 삭제 검토 문구를 제거하고 보관·복구 의미를 명확히 했다.
  • 로딩 Skeleton, 빈 상태, 서버 읽기 실패 안내, 데스크톱 테이블과 모바일 목록을 제공한다.

검증

  • 로컬 Supabase migration reset/replay 성공
  • 실제 PostgreSQL transaction probe로 보관·복구·역할·직무·감사 이벤트와 직접 mutation 차단 확인
  • 관련 Playwright 77건 중 74건 통과, 실패 3건 중 2건은 단독 재실행 통과
  • 잔여 1건은 로컬 DB reset 뒤 테스트 전용 workspace bootstrap 대기 timeout이며 변경 API·migration 집중 검증은 통과
  • TypeScript, 전체 ESLint, secret scan, docs check, production build 통과
  • 데스크톱 브라우저에서 구성원 디렉터리와 역할·직무 화면 확인

릴리스 전 확인

새 Next.js API는 새 Supabase RPC와 컬럼을 요구한다. 원격 migration과 애플리케이션 코드를 같은 릴리스 단위로 적용해야 하며, 원격 DB 적용 승인 없이 main production 배포를 진행하면 안 된다.
