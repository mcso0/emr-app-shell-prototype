Fixed staging billing DB/RPC replay 결과

승욱 승인 범위 안에서 clair-emr-staging / qmerxgzrwaaahpkhjqlc에 수납 hardening migration을 적용하고 synthetic billing replay를 실행했다. production, production DB, real data import, payment provider 연동은 실행하지 않았다.

결론

  • 통과: guardian ledger 조회, checkout session 생성, invoice 상태 전환, audit payload readback이 fixed staging에서 통과했다.
  • 통과: 완료/취소 건은 ledger에는 남고 checkout payable 합계에서는 제외되는 규칙이 staging RPC 결과로 확인됐다.
  • 주의: CLI db push --dry-run은 기존 remote migration history와 local filename 일부 불일치 때문에 사용할 수 없었다. 승인된 단일 migration은 Supabase connector migration API로 적용했다.

발견 및 조치

  • Replay 중 clair_prepare_billing_checkout_session에서 min(uuid)가 Postgres 17에 없어 실패하는 문제를 발견했다.
  • local migration 원본을 min(i.guardian_id::text)::uuid로 수정했다.
  • 이미 staging에 적용된 RPC에는 follow-up repair migration 20260601112352_den_381_billing_checkout_uuid_guardian_repair.sql을 추가 적용했다.

Advisors

  • Security advisor는 기존 staging 전반의 RLS Enabled No Policy, SECURITY DEFINER RPC 경고, 일부 function search_path 경고를 계속 보고했다.
  • 이번 새 billing tables도 RLS는 켜져 있지만 table-level direct access policy는 아직 없다. 현재 replay는 승인된 RPC 경로로만 검증했다.
  • Performance advisor는 새 billing FK 일부의 covering index 경고와 막 생성된 index의 unused 경고를 보고했다. unused index는 신규 생성 직후라 즉시 제거 대상은 아니다.

남은 판단

DEN-381의 목표였던 fixed staging synthetic replay는 통과했다. 다만 실제 fixed staging 화면까지 닫으려면 Vercel 보호를 통과할 수 있는 승인된 preview access가 필요하고, 화면이 새 guardian-checkout route를 호출하도록 연결하는 follow-up이 필요하다. table direct RLS policy 설계와 FK covering index 정리는 별도 RLS/performance hardening 이슈로 분리하는 편이 안전하다.
