DEN-287 / 2026-05-26 / Fulfillment Routing

확정 Order 후속 업무 라우팅 보고서

차트에서 workspace catalog 오더를 확정하면, 서버가 저장한 applied snapshot의 destination과 task 필요 여부를 기준으로 lab, imaging, dispensing, treatment 업무 queue에 fulfillment work item을 만들도록 연결했다. 같은 오더 확정을 다시 시도해도 같은 work item을 재사용한다.

Status: Human Review Inpatient queue: Follow-up Remote DB: Not applied

무엇이 바뀌었나

  • 차트 확정 결과의 appliedSnapshot을 fulfillment sync boundary로 전달한다.
  • 기존 mock orders fixture에 없는 catalog 기반 신규 확정 오더도 snapshot으로 안전한 virtual order를 만들어 queue에 넣는다.
  • work item id는 fulfill-{orderId} 형태로 유지해 같은 확정 재시도에서 중복 work item이 생기지 않게 했다.
  • fulfillment source snapshot에는 업무 수행에 필요한 최소한의 이름, 청구명, 가격 snapshot, 수량, 지시사항, destination, source preset id만 담는다.

라우팅 규칙

Catalog destination 이번 구현 비고
lab Lab queue work item 생성 검사 완료 후 수의사 확인 gate는 후속 billing 흐름에서 다룸
imaging Imaging queue work item 생성 PACS/device integration은 범위 밖
dispensing Dispensing queue work item 생성 재고/라벨 출력은 범위 밖
treatment Treatment queue work item 생성 처치/치료성 업무의 1차 queue
billing_only, chart_only Fulfillment work item 생성 안 함 청구 후보 생성은 별도 이슈 범위
taskRequired: false Fulfillment work item 생성 안 함 업무 queue가 필요 없는 catalog row
inpatient 이번 구현에서는 shared fulfillment queue로 라우팅하지 않음 현재 fulfillment queue type과 권한 모델이 입원 전용 queue를 아직 지원하지 않아 명시 follow-up으로 남김

보안 및 데이터 경계

  • client가 보낸 가격이나 이름이 아니라, DEN-286에서 서버가 저장한 applied snapshot을 fulfillment source로 사용한다.
  • source snapshot에는 SOAP 본문, secret, token, 외부 provider payload, 불필요한 개인정보를 넣지 않는다.
  • 이번 작업은 app/API/core와 local test만 수행했다. remote Supabase 적용, 원격 RLS replay, production deploy, 실데이터 import는 하지 않았다.

남은 범위

  • inpatient는 현재 fulfillment queue type과 권한 모델에 없어 후속 이슈로 분리해야 한다.
  • billing_only 오더의 차트 확정 즉시 billing candidate 생성은 별도 billing 이슈에서 처리해야 한다.
  • lab/imaging 결과가 차트로 돌아온 뒤 담당 수의사가 확인해야 billing이 진행되는 gate는 후속 workflow 이슈에서 구현해야 한다.
