DEN-370 보호자 수납 데이터 계약 DB/RPC Fit 보고서

현재 구조는 단일 진료/단일 청구서의 수납대기, 미납, 수납완료까지는 감당한다. 하지만 보호자 한 명의 여러 환자/여러 청구서를 하나의 checkout으로 묶고, 완료/취소 이력의 합산 제외와 상태 되돌리기를 실사용 DB 계약으로 고정하려면 후속 schema/RPC 설계가 필요하다.

이번 검수 결론

  • 유지 가능: Order 청구가 candidate-backed invoice_lines를 만들고, 해당 건을 수납대기로 보여주는 흐름.
  • 유지 가능: invoices.status, payment_state, unpaid_reason, payments로 단일 invoice 결제/미납을 저장하는 흐름.
  • 설계 필요: 수납이력 날짜 기준을 issued_at ?? created_at이 아니라 "수납으로 넘어온 시각"으로 명확히 고정하는 계약.
  • 설계 필요: 여러 invoice를 하나의 checkout/payment로 묶는 session, allocation, payer snapshot.
  • 설계 필요: 완료/취소 이력 상태 전환의 actor, reason, 이전/다음 상태, 결제 side-effect를 남기는 audited RPC.

현재 DB/RPC Fit

요구 현재 감당 범위 부족한 점 후속 이슈
차트 Order 청구가 수납대기 생성 clair_sync_billing_invoice_candidates가 workspace/encounter/order를 검증하고, draft invoice anchor를 만들며, invoice_lines를 upsert하고 합계를 재계산한다. 엄밀한 billing_requested_at 필드는 아직 없다. DEN-375
수납대기/미납/완료/취소 분류 invoices.status와 payment_state로 대기, 미납, 완료, 취소를 유추할 수 있다. 미납은 reason이 필요한 상태로 이미 제약이 있다. 분류 기준과 checkout 합산 포함 여부가 DB view/RPC로 고정되어 있지 않다. DEN-371, DEN-372
보호자 ledger 조회 guardians, patient_guardians, encounters, invoices 관계로 구현 가능하다. 현재 UI는 mock helper로 같은 의미를 계산한다. date/status/co-guardian/include-excluded 규칙을 제공하는 read model/RPC가 없다. DEN-372
여러 환자/여러 invoice 합산 checkout UI/store에서는 여러 invoice 선택과 합산 표시가 가능하다. DB에는 billing_checkout_sessions, 선택 invoice snapshot, payment_allocations, immutable payer snapshot이 없다. DEN-373, DEN-376, DEN-377
할인/할증 및 수납 메모 audit 현재 invoice_lines.discount_amount와 invoice 합계 필드는 있다. 조정 사유, actor, 적용 범위, 승인 여부를 독립 이벤트로 남기는 모델이 없다. DEN-373
완료/취소 이력 선택 및 합산 제외 UI는 완료/취소 이력을 선택해서 볼 수 있고 오른쪽 수납 합산에서 제외한다. 서버가 payable/excluded split을 authoritative result로 돌려주는 계약이 없다. DEN-371, DEN-378, DEN-379
완료/취소 상태 되돌리기 local-first store에서는 완료 -> 대기/미납/취소, 취소 -> 대기/미납/완료 전환을 표현한다. 실사용 DB에서는 결제 취소, 영수증, 감사 로그와 연결되므로 audited transition RPC가 필요하다. DEN-374, DEN-377, DEN-379
staging 검증 local/static 설계 검토와 synthetic UI regression까지 가능하다. remote migration push, RLS replay, fixed staging replay는 승욱 승인 게이트 이후에만 가능하다. DEN-380, DEN-381

화면이 필요로 하는 데이터 계약

  • activityAt: 수납이력 그룹 날짜. 권장 기준은 chart Order 청구로 수납 후보가 생성/갱신된 시각이다.
  • billingStatus: waiting, unpaid, paid, voided를 사용자 라벨과 분리해 내려주는 값.
  • isCheckoutPayable: 현재 checkout 금액에 포함되는지 여부. 완료/취소는 조회 가능하지만 false여야 한다.
  • amountBasis: 서버가 재계산한 subtotal, discount, surcharge, tax, paid, balance.
  • payerSnapshot: 결제 당시 보호자 이름/연락처/공동 보호자 context의 immutable snapshot.
  • transitionAudit: 상태 변경 actor, reason, source screen, previous/next state, amount/payment side-effect.

  5. DEN-376 이후: local migration, server core, UI data-backed 연결, invariant regression, staging 승인 게이트 순서로 진행한다.
