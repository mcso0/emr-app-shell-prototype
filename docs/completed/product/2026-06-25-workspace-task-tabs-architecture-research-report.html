Product / Engineering Research

CLAiR EMR 워크스페이스 탭 아키텍처 조사 보고서

데스크톱에서 여러 업무 화면을 앱 내부 워크스페이스 탭으로 유지하고, 여러 환자와 여러 모듈을 오가며 일할 수 있게 하는 기능을 어떻게 설계할지 조사했다. 모바일에서는 워크스페이스 탭을 제공하지 않는 전제로 작성했다.

작성일: 2026-06-25 · 대상 화면: 워크스페이스 상단 업무 탭

1. 한 줄 결론

큰 아키텍처 교체는 필요 없다. 현재 App Shell 탭을 워크스페이스 탭으로 제품화하되, 탭의 목적을 “새 업무 생성 메뉴”가 아니라 “여러 역할, 여러 환자, 여러 임상 화면을 동시에 열어두고 전환하는 작업 공간”으로 명확히 잡는 것이 맞다.

2. 목적 달성 매트릭스

이번 기능은 “새 업무를 시작하는 메뉴”가 아니라, 사용자가 이미 필요한 업무 화면들을 데스크톱에서 동시에 열어두고 전환하는 작업 방식이다. 따라서 설계도 아래 목적을 직접 달성하는 순서로 정렬한다.

승욱이 준 주요 목적 제품 요구사항으로 바꾸면 구현에서 반드시 필요한 것
역할이 하나로 고정되어 있지 않다. 한 사용자가 접수, 진료, 검사, 영상, 수납 화면을 동시에 열어둘 수 있어야 한다. 탭 identity를 모듈 단위로 닫지 말고, 여러 모듈 route를 병렬 보존한다.
수의사는 여러 환자를 동시에 진료할 수 있다. 같은 진료/차트 모듈 안에서도 서로 다른 환자 또는 encounter 탭을 허용한다. encounterId를 URL과 워크스페이스 탭 metadata의 기준값으로 둔다.
차트뿐 아니라 검사/영상 화면도 함께 띄워야 한다. 같은 환자의 차트, 임상검사, 영상검사, 수납 화면을 동시에 열 수 있어야 한다. surfaceType, surfaceId가 encounter 외에도 lab/imaging/invoice를 표현해야 한다.
다른 사용자도 여러 화면에서 다양한 업무를 수행한다. 워크스페이스 탭은 수의사 전용이 아니라 데스크톱 공통 shell 기능이다. feature UI가 아니라 src/shell 레이어에서 관리한다.
같은 화면/같은 업무를 다른 탭에서 열면 알려줘야 한다. 중복 접근은 차단하지 않고, 위험을 알린 뒤 사용자가 선택하게 한다. dedupeKey, 중복 접근 모달, “다시 해당 알림 보지 않기” 설정이 필요하다.

3. 제품 원칙

역할이 하나로 고정되지 않음

사용자는 접수, 진료, 검사, 수납 같은 여러 화면을 동시에 열어두고 상황을 보며 일할 수 있어야 한다. 탭은 업무 시작 메뉴가 아니라 화면과 맥락을 보존하는 장치다.

수의사는 여러 환자를 동시에 본다

한 수의사가 초코 차트, 구름 차트, 검사 결과, 영상 화면을 함께 열어두고 확인할 수 있어야 한다. 차트 화면만 대상으로 보면 요구사항이 좁아진다.

모든 사용자의 병렬 업무를 지원

접수, 테크니션, 수납 담당자도 여러 화면을 열어두고 다양한 업무를 수행한다. 워크스페이스 탭은 특정 직군 전용 기능이 아니라 데스크톱 공통 작업 방식이다.

4. 현재 레포 상태 요약

탭 UI

현재 탭은 src/shell과 src/stores/workspace-tabs-store.ts에서 관리한다. 탭별 route history, 뒤로/앞으로, 새 탭, 닫기, 마지막 탭 유지가 있다.

기반 있음

탭 저장

저장 위치는 브라우저 sessionStorage다. 새로고침 복원은 되지만 로그아웃 후 계정 기반 복원, 다른 기기 복원, 서버 감사 추적은 제품 기능으로 보장하기 어렵다.

제품화 필요

임상 DB

soap_notes, diagnoses, orders는 workspace_id와 encounter_id 중심이다. 진료, 검사, 수납이 같은 encounter 맥락을 공유하기에 기반은 적합하다.

대체로 적합

핵심 확인 포인트

항목 현재 상태 판단
업무 탭 최소 1개 유지 이미 구현됨 유지
탭별 route history 이미 구현됨 유지
로그아웃 후 같은 위치 복원 sessionStorage라 제품 보장 약함 계정 기반 저장소 필요
초코 차트와 구름 차트, 검사/영상 화면 동시 열기 encounterId URL이 있으면 가능하나 전역 store 의존이 남아 있음 워크스페이스 탭 identity를 source of truth로 정리
같은 SOAP 동시 편집 명시 정책 없음 버전 충돌 감지와 UI 안내 필요

5. 웹/레퍼런스 조사 결과

조사 기준은 “새 업무 생성 메뉴가 필요한가?”가 아니라 “여러 업무 화면을 어떻게 열어두고, 전환하고, 중복 접근을 다루는가?”다.

서비스 확인한 패턴 CLAiR에 적용할 판단
Linear Desktop Tabs에서 데스크톱 앱 탭을 브라우저식 작업 정리 수단으로 설명한다. 2026년 최신 changelog에서도 각 데스크톱 탭의 독립 history stack과 앱 재시작 후 유지되는 pinned tab을 강조한다. 워크스페이스 탭은 데스크톱 고밀도 업무용 기능으로 제한한다. 모바일 미제공 결정과 맞다. 특히 “탭마다 마지막 위치를 기억한다”는 요구는 독립 history stack과 서버 복원으로 구현해야 한다.
Salesforce Console Workspace API는 레코드를 workspace tab으로, 관련 레코드를 subtab으로 여는 모델을 제공한다. openTab, focusTab, getAllTabInfo 같은 조작 API가 있다. CLAiR도 “진료/차트 화면”이 아니라 “특정 encounter, lab result, imaging study, invoice”처럼 업무 객체 중심으로 탭을 식별해야 한다.
ServiceNow Workspace Service Operations Workspace는 incident 같은 record page가 여러 탭을 갖고, 공통 탭과 record-specific 탭을 구분한다. record 중심 구조만 참고한다. CLAiR에서는 plus 버튼을 새 업무 메뉴로 확장하지 않고, 현재 사용자가 열어둔 업무 화면과 맥락을 보존하는 shell 기능으로 유지한다.
Zendesk Agent Workspace ticket tabs로 여러 대화를 탭으로 관리하고, overflow와 reorder 같은 다중 탭 관리 패턴을 제공한다. 접수/진료/검사/수납 화면을 여러 개 열 때 overflow 정책이 필요하다. 탭명도 모듈명만이 아니라 환자/업무 맥락을 식별할 수 있어야 한다.
WAI-ARIA Tabs Tabs Pattern은 tablist, tab, tabpanel 역할과 키보드 이동 규칙을 제시한다. 워크스페이스 탭은 앱 shell 내 복잡한 탭이므로 접근성 패턴을 직접 검증해야 한다. 기존 커스텀 탭을 유지하더라도 ARIA/키보드 계약은 문서화하고 테스트해야 한다.

6. 추천 제품 정책

데스크톱 전용

워크스페이스 탭은 데스크톱에서만 제공한다. 모바일은 탭 기능을 제공하지 않는다. 모바일에서 여러 화면을 병렬로 띄우는 요구는 이번 범위 밖이다.

탭은 작업 공간이다

워크스페이스 탭은 새 업무를 만들기 위한 메뉴가 아니다. 사용자가 여러 모듈과 여러 환자 화면을 열어두고 전환하기 위한 작업 공간이다.

중복 접근은 알려준다

다른 워크스페이스 탭에서 이미 같은 화면과 같은 업무 객체를 보고 있다면, 새로 여는 사용자를 막기보다 “이미 열린 화면”이라는 사실과 데이터 손실 가능성을 알린다.

선택권을 준다

경고 모달에서 기존 탭으로 이동하거나, 그래도 현재 탭에서 계속 열 수 있게 한다. 사용자가 원하면 “다시 해당 알림 보지 않기”를 선택할 수 있다.

7.3 탭 세션 저장 테이블 초안

create table public.user_workspace_tab_sessions (
  user_id uuid not null references public.users(id) on delete cascade,
  workspace_id text not null references public.workspaces(id) on delete cascade,
  active_tab_id text,
  tabs jsonb not null default '[]'::jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  primary key (user_id, workspace_id)
);

이 테이블은 임상 데이터가 아니라 개인 작업환경 저장소다. 환자명, 보호자명 같은 표시용 개인정보를 저장하지 않고, route와 업무 객체 ID만 저장하는 편이 안전하다.

7.4 중복 접근 알림 정책

상황 알림 여부 추천 UI
다른 워크스페이스 탭에서 같은 모듈, 같은 업무 객체를 이미 보고 있음 알림 모달: “이미 다른 워크스페이스 탭에서 보고 있는 화면입니다.”
같은 환자지만 다른 모듈을 봄. 예: 차트 탭과 검사 탭 알림 없음 정상 허용. 병렬 업무 목적에 맞음
같은 모듈이지만 다른 환자/다른 encounter를 봄 알림 없음 정상 허용. 수의사가 여러 환자를 동시에 보는 핵심 시나리오
사용자가 “다시 해당 알림 보지 않기”를 선택함 사용자/브라우저 또는 계정 설정에 따라 생략 중복 접근은 허용하되 저장 충돌 감지는 계속 유지

8. 기술/외부 도구 선택지 평가

외부 도구의 역할은 워크스페이스 탭 목적을 보조하는 것이다. 탭 자체를 통째로 외부 라이브러리에 맡기기보다, 접근성, 모달, 복원, 중복 감지, 저장 충돌처럼 목적 달성에 필요한 부분만 검증된 기술을 조합하는 편이 현재 레포 구조와 잘 맞다.
기술 목적과 연결되는 지점 판단
WAI-ARIA Tabs 패턴 워크스페이스 탭을 키보드/스크린리더가 이해하는 탭 구조로 유지 필수 기준 현재 UI를 유지하되 접근성 계약으로 삼는다
Radix Dialog / Alert Dialog “이미 보고 있는 화면” 중복 접근 알림과 확인 액션 추천 기존 shadcn/Radix 계열과 맞으면 새 의존성 없이 적용 가능
React Aria Tabs 탭 접근성 구현을 더 강하게 위임하고 싶을 때 보류 현재 워크스페이스 탭은 히스토리/업무 identity가 핵심이라 전면 교체 이득이 작음
BroadcastChannel 같은 브라우저/동일 계정에서 중복 화면 접근, 저장 완료, 탭 변경을 가볍게 전파 추천 서버 없이 가볍게 적용 가능
Zustand persist 현재 Zustand 탭 store의 브라우저 내 임시 복원과 마이그레이션 보조 수단 로그아웃 후 복원은 서버 저장이 필요하므로 단독으로는 부족함
Supabase Realtime Presence 다른 사용자/기기에서 같은 환자 차트, 검사, 영상 화면을 보고 있음을 표시 2단계 추천 첫 구현 후 presence와 변경 알림에 적합
Postgres optimistic concurrency 같은 SOAP/진단/오더를 여러 탭에서 수정할 때 조용한 덮어쓰기 방지 필수 updated_at 또는 version 비교로 409 conflict를 반환
Web Locks API 같은 브라우저에서 하나의 탭만 특정 로컬 작업을 수행하도록 조정 제한적 임상 데이터 락이나 권한 보안으로 쓰면 안 됨
TanStack Router route/search param을 타입 안전하게 관리 지금은 보류 라우터 교체 비용이 크고, 현재 요구는 탭 identity 정리가 먼저임
Dexie / IndexedDB 오프라인 초안, 대량 로컬 캐시 보류 현재 요구는 탭 복원과 충돌 감지라 과함
Yjs / CRDT Google Docs처럼 여러 사람이 동시에 같은 문장을 편집 초기 비추천 EMR SOAP에는 복잡도와 검증 부담이 큼

9. 구현 순서 제안

  1. 기획 확정: 모바일 미제공, 명칭은 워크스페이스 탭, 목적은 여러 역할/여러 환자/여러 임상 화면 병렬 유지로 확정한다.
  2. 탭 identity 정리: 현재 탭에 surfaceType, surfaceId, dedupeKey를 추가한다.
  3. URL source of truth: 차트, 접수, 수납, 검사, 영상 화면의 선택값을 URL과 워크스페이스 탭 identity 중심으로 정리한다.
  4. 중복 접근 알림: 같은 화면/같은 업무 객체를 이미 다른 탭에서 보고 있으면 모달로 알리고, 기존 탭 이동 또는 현재 탭에서 계속 열기를 선택하게 한다.
  5. 계정 기반 복원: user_workspace_tab_sessions 테이블과 저장 API를 추가한다.
  6. 충돌 감지: SOAP 저장 API에 expectedUpdatedAt 또는 version을 추가하고 409 conflict UI를 만든다.
  7. 실시간 안내: 같은 브라우저는 BroadcastChannel, 사용자 간 presence는 Supabase Realtime로 단계적 도입한다.

10. 리스크와 보완 포인트

가장 큰 리스크는 탭 UI가 아니라 데이터 덮어쓰기다. 탭을 여러 개 열 수 있게 만드는 일은 쉽지만, 같은 SOAP를 여러 곳에서 수정할 때 마지막 저장이 앞선 저장을 조용히 덮어쓰면 임상 데이터 신뢰가 깨진다.
  • 탭 복원 테이블에는 환자명/보호자명 같은 표시용 개인정보를 저장하지 않는다.
  • 탭 저장 API도 workspace membership과 사용자 범위를 서버에서 검증해야 한다.
  • 같은 화면/같은 업무 객체 중복 접근은 막지 말고 알림 후 선택하게 한다.
  • “다시 해당 알림 보지 않기”를 선택해도 서버 저장 충돌 감지는 계속 유지한다.
  • 동시 편집은 하드 락보다 optimistic concurrency가 실무 UX에 더 적합하다.
  • 모바일은 이번 워크스페이스 탭 범위에서 제외한다.

11. 최종 추천

1차 구현은 “데스크톱 워크스페이스 탭 + 중복 접근 알림 + 계정 기반 복원 + 저장 충돌 감지”로 잡는 것이 좋다. 외부 탭 라이브러리 도입이나 CRDT 협업 편집은 지금 단계에서는 비용 대비 이점이 낮다.

DB는 기존 임상 테이블을 유지하고, 탭 복원을 위한 사용자별 설정 테이블만 추가한다. SOAP/진단 저장 쪽에는 updated_at 또는 별도 version을 이용한 충돌 감지 계약을 붙인다.
