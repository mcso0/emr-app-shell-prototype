DEN-340 DB/RPC Fit for Separated Billing State Report

2026-05-31 기준으로 현재 DB/RPC 구조가 업무 상태와 수납 상태 분리를 감당하는지 검수했다. 결론은 DEN-341 staging replay에는 새 migration 없이 충분하다는 것이다.

판정

질문 판정 근거
업무 상태와 수납 상태를 분리해 담을 수 있는가? 가능 orders.status, orders.work_status, orders.task_status, order_fulfillment_work_items.status와 orders.billing_candidate_status, invoices, invoice_lines가 분리되어 있다.
chart Order 청구가 업무 상태를 바꾸는가? 아니오 clair_save_chart_order_action(action = 'bill')는 billing_candidate_status와 billing_candidate_id만 전진시키고, order/work/fulfillment status는 변경하지 않는다.
invoice candidate sync가 실제 후보 라인을 만들 수 있는가? 가능 clair_sync_billing_invoice_candidates는 workspace, encounter, selected order scope를 검증하고, cancelled/non-billable row를 제외하며, draft invoice anchor와 invoice line을 생성 또는 갱신한다.
단일 transaction/RPC migration이 지금 필수인가? 필수 아님 현재 두 RPC 구조는 부분 실패 후 재시도가 가능하다. chart bill RPC가 먼저 성공해도 invoice sync RPC는 billing_candidate_status = 'candidate_created'를 허용하므로 같은 order를 다시 청구해 후보 라인을 복구할 수 있다.

Migration 판단

이번 DEN-340에서는 새 schema/RPC migration을 만들지 않는다. 현재 구조는 local-first MVP와 synthetic staging QA에서 필요한 분리 상태, idempotent 후보 생성, 서버 금액 snapshot 기반 동기화를 제공한다.

승인 게이트: 대표 검수 기준이 “chart bill action과 invoice candidate 생성이 반드시 하나의 DB transaction으로 함께 성공 또는 함께 실패해야 한다”로 올라가면 consolidated RPC migration을 별도 승인 후 진행한다.

승인 필요 시 제안할 RPC

  • 함수명: public.clair_bill_chart_orders_and_sync_invoice_candidates
  • 입력: p_workspace_id text, p_actor_user_id uuid, p_encounter_id uuid, p_order_ids uuid[]
  • 처리: workspace membership, encounter, selected order, cancellation, billing reflection validation 후 order billing candidate update, invoice anchor create/reuse, invoice line upsert, invoice total recalculation, order event insert를 한 function 안에서 수행한다.
  • 검증: migration static tests, rollback/retry server specs, invoice candidate specs, npx tsc --noEmit --pretty false, npm run security:secrets, 승인된 staging synthetic replay.

남은 위험

  • 두 RPC 사이에서 network/API 실패가 나면 잠시 candidate_created order와 미생성 invoice line이 공존할 수 있다. 다만 같은 chart bill action을 재시도하면 복구 가능한 상태다.
  • 여러 active draft/issued invoice가 같은 encounter에 동시에 존재하는 경우 sync는 최신 invoice를 선택한다. 현재 앱 경로에서는 일반적으로 하나의 anchor만 쓰지만, 미래 고급 invoice split 정책 전에는 이 점을 QA에서 관찰해야 한다.
  • remote RLS replay, production deploy, 실데이터 import, remote migration push는 이번 작업 범위 밖이며 실행하지 않았다.

DEN-341 준비

  • lab, imaging, dispensing, treatment 각각에서 requested, in_progress, re_requested, completed 상태의 Order 청구와 billing readback을 synthetic staging에서 확인한다.
  • 미완료 오더 확인 다이얼로그와 이미 candidate인 오더의 재청구 idempotency를 확인한다.
  • billing 화면에서 같은 encounter의 invoice candidate line, 금액, order trace가 보이는지 확인한다.
  • staging replay 중 단일 transaction이 없어서 생기는 실제 blocker가 관찰되면 consolidated RPC migration 승인 요청으로 멈춘다.
