DEN-279 / 2026-05-25 / CLAiR EMR Order Platform

Workspace Order Catalog Platform 기획 보고서

병원관리의 Order 관리는 임상병리 화면 하나가 아니라 CLAiR EMR 전체 업무 오더의 마스터 데이터가 되어야 한다. CLAiR는 기본 오더 프리셋을 제공하고, 각 병원은 자기 워크스페이스 안에서 오더를 수정, 삭제, 추가한다. 진료/차트에서 선택해 확정한 순간에는 환자와 진료 건에 묶인 실제 오더 snapshot이 생기고, 오더 성격에 따라 검사, 영상, 조제, 처치, 입원, 수납으로 이동한다.

2. 제품 모델

System order presets

CLAiR가 제공하는 표준 오더 템플릿이다. CBC, 심전도, 방사선, 예방접종, 수액, 처치, 입원료, 약품, 의료물품 같은 기본 후보를 담는다. 병원 운영 데이터가 아니라 복사 원본이다.

Workspace order catalog

실제 병원관리 화면에 보이는 병원별 오더 목록이다. 같은 프리셋에서 출발해도 병원마다 원내명, 청구명, 가격, 사용여부, 지시사항, 라우팅 destination이 달라질 수 있다.

Encounter orders

진료/차트에서 선택되고 확정된 환자별 실제 오더다. 이 레이어는 catalog를 참조하되, 확정 당시 이름과 가격, 청구명, 지시사항을 snapshot으로 저장해야 한다.

Fulfillment and billing

확정 오더 중 업무가 필요한 항목은 lab, imaging, dispensing, treatment, inpatient queue로 이동한다. 청구 가능한 항목은 서버가 보유한 금액 snapshot을 기준으로 billing candidate가 된다.

3. 현재 저장소 기준으로 확인한 사실

  • Project 07 문서에서는 order_catalog_items, order_sets, order_set_items, lab_test_items, order_catalog_lab_test_item_links를 병원관리 master data로 정의했다.
  • 기존 schema plan은 chart 적용 시 이름, 청구명, 가격, 세금, 판매 단위, 대상 동물, source preset id/version, metadata를 snapshot으로 복사해야 한다고 정리해 두었다.
  • 현재 route는 GET /api/workspaces/[workspaceId]/hospital-admin/order-catalog와 mode=chart-search를 제공하고, POST/PATCH mutation에는 permission과 rate limit이 걸려 있다.
  • 현재 core에는 create, update, pause mutation이 있다. 화면의 삭제 UX는 실제로는 과거 기록을 깨지 않는 비활성화 또는 soft delete 정책으로 정리하는 게 맞다.
  • Project 08 문서와 core는 chart-confirmed order가 fulfillment work item으로 이동하고, 완료 상태가 order lifecycle과 billing candidate로 반영되는 계약을 이미 갖고 있다.

4. 결정해야 하는 데이터 계약

객체 책임 핵심 필드 주의점
system_order_presets CLAiR 기본 프리셋 원본 preset id, version, category, standard name, default price, default routing, metadata 병원 수정본을 덮어쓰지 않는다.
workspace_order_catalog 병원별 실제 오더 마스터 workspace id, source preset, standard name, in-hospital name, billing name, aliases, status, price, target, destination workspace isolation과 admin permission이 필수다.
encounter_orders 환자/진료별 확정 오더 encounter id, catalog item id, applied snapshot, quantity, priority, status, requested by 나중에 catalog가 바뀌어도 과거 차트와 청구는 바뀌면 안 된다.
fulfillment_work_items 후속 부서 업무 항목 queue type, status, assignee, source snapshot, due time, completion reason 중복 생성 방지와 invalid transition 차단이 필요하다.
billing_candidates 수납 후보 항목 server-owned service item, amount snapshot, tax, billing status 클라이언트 제출 금액을 신뢰하면 안 된다.

5. 화면과 사용자 흐름

  1. 병원 생성 또는 초기 설정 시 CLAiR 기본 프리셋이 병원별 workspace catalog로 복사된다.
  2. 병원관리자는 Order 관리에서 전체 오더를 조회하고, 카테고리/하위 타입/사용여부/청구/업무유형으로 필터링한다.
  3. 상세 drawer에서 원내 Order명, 청구서명, 별칭, 전달 여부, 대상, 케어가이드, 원내 지시사항, 메모, 가격, 사용여부를 수정한다.
  4. 삭제 버튼은 실제 삭제보다 inactive, paused, archived 같은 안전 상태로 처리한다. 이미 사용된 오더는 historical snapshot만 남긴다.
  5. + Order는 현재 병원의 workspace catalog에 새 오더를 만든다. system preset에는 영향을 주지 않는다.
  6. 진료/차트에서는 현재 병원의 active catalog만 검색한다. 의사가 오더를 확정하면 encounter order snapshot이 생긴다.
  7. 확정된 오더는 destination과 task_required에 따라 후속 queue 또는 billing candidate로 이동한다.

6. CSO 보안·무결성 기획 보강

위협 위험 기획 기준
Spoofing 권한 없는 사용자가 병원 오더 가격이나 사용여부를 바꿀 수 있음 오더 CRUD는 service_catalog:manage, 차트 검색은 service_catalog:view로 분리한다.
Tampering catalog 수정이 과거 차트와 청구 금액을 바꿔 버림 확정 시 snapshot을 저장하고 billing amount는 서버 계산값만 사용한다.
Repudiation 누가 가격/청구명/사용여부를 바꿨는지 추적할 수 없음 create, update, pause, archive, restore, price change에 safe audit event를 남긴다.
Information disclosure 후속 queue snapshot에 SOAP 원문, 토큰, 외부 provider payload가 섞임 source snapshot은 표시와 업무 수행에 필요한 최소 안전 필드만 허용한다.
Elevation of privilege 다른 워크스페이스 catalog item id로 cross-workspace 접근 가능 모든 read/mutation은 workspace id, actor membership, item workspace ownership을 함께 검증한다.

이 보고서는 전문 보안 감사의 대체물이 아니다. 구현 전 기획 단계에서 공격 경로를 줄이기 위한 1차 보안 설계 기준이다. 민감 데이터, 결제, 실병원 운영 전에는 별도 보안 검토와 실제 RLS/server enforcement 검증이 필요하다.

8. 권장 작업 순서

  1. 먼저 DEN-280에서 기존 Project 07/08 코드와 문서의 재사용 범위를 확인한다.
  2. DEN-281에서 system preset과 workspace catalog의 데이터 계약을 고정한다.
  3. DEN-282에서 local-first seed/import boundary를 구현한다.
  4. Linear issue limit이 해소되면 생성 대기 이슈를 실제 Linear 이슈로 옮긴다.
  5. 그 다음 병원관리 drawer CRUD, 차트 검색/확정 snapshot, 후속 라우팅, 보안 QA 순서로 진행한다.

9. 이번 작업 범위에서 하지 않은 것

  • 앱 구현, UI 수정, DB schema 변경, migration 작성은 하지 않았다.
  • remote Supabase, staging migration, RLS replay, production deploy는 실행하지 않았다.
  • 실병원 오더 데이터, 실제 환자/보호자/결제/신원 데이터는 사용하지 않았다.
  • 의료적 추천, 처방 정확성, 법적/컴플라이언스 인증은 이 보고서의 보장 범위가 아니다.

10. 승욱이 나중에 확인·검수·제공해야 하는 질문

  1. 초기 CLAiR 기본 프리셋의 범위는 어디까지로 할까? 검사, 영상, 예방, 처치, 수술, 입원, 치료, 처방/조제/의료물품을 모두 1차에 넣을지 결정이 필요하다.
  2. 병원이 CLAiR 기본 프리셋 업데이트를 받을 때 자동 병합을 원하나, 아니면 비교 후 수동 가져오기를 원하나?
  3. 삭제 버튼의 제품 문구는 “삭제”로 유지할까, 아니면 실제 동작에 맞춰 “사용중지” 또는 “보관”으로 바꿀까?
  4. 가격 변경은 즉시 적용만으로 충분한가, 아니면 적용 시작일과 가격 이력이 필요할까?
  5. 오더 확정 후 lab/imaging/dispensing/treatment/inpatient/billing_only/chart_only destination 분류를 이 기준으로 확정해도 될까?
  6. technician이 후속 업무를 취소할 수 있게 할까, 아니면 chart로 반려만 가능하게 할까?
  7. lab/imaging 완료 후 billing으로 바로 갈 수 있는 항목과 수의사 review가 필요한 항목을 어떻게 나눌까?
  8. 오더 세트는 이번 프로젝트에서 차트 검색까지 포함할까, 아니면 개별 오더 안정화 후 별도 단계로 둘까?
  9. 병원관리에서 오더 수정 권한을 hospital_admin 전용으로 둘까, manager 또는 lead technician까지 열어둘까?
  10. 실제 병원 오더 목록 import는 MVP 이후로 미룰까, 아니면 CSV 템플릿 설계만 먼저 넣을까?
