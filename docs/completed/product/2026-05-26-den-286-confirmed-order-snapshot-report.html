차트 확정 Order Snapshot 저장 보고서

차트에서 workspace catalog 오더를 확정할 때 서버가 active catalog row를 다시 조회해 당시 이름, 청구명, 가격, 지시사항, destination을 applied snapshot으로 고정하도록 연결했다. 이후 병원관리에서 catalog 값을 바꿔도 이미 확정된 차트 오더 snapshot은 바뀌지 않는다.

Status: Human Review Fulfillment routing: Later issue Remote DB: Not applied

무엇이 바뀌었나

  • PATCH /chart/order-actions가 catalog selection 정보를 받을 수 있게 됐다.
  • 서버 core는 client가 보낸 이름이나 금액을 신뢰하지 않고, active workspace catalog search 결과에서 snapshot을 다시 만든다.
  • 확정 snapshot에는 표준 Order명, 원내 Order명, 청구명, 가격, 판매단위, 과세 포함 여부, 금액 기준, 대상, 케어가이드, 원내 지시사항, destination, task 필요 여부, 수량, line total이 들어간다.
  • paused catalog row는 확정 전에 거절된다.
  • order set 확정은 개별 오더 안정화 이후 범위라 이번에는 거절된다.
  • 차트 UI는 catalog에서 추가한 draft row를 확정할 때 source preset id와 수량을 함께 보내도록 연결됐다.

왜 중요한가

병원관리에서 나중에 오더 가격이나 이름을 바꿔도, 이미 과거에 진료한 기록과 청구 금액은 바뀌면 안 된다. 이번 작업은 그 경계를 차트 확정 시점에 만들었다. 즉, catalog는 미래 선택 후보이고, 확정된 encounter order는 당시 값을 가진 별도 기록이 된다.

보안 및 데이터 경계

  • client가 보낸 billing name이나 price를 snapshot 원천으로 사용하지 않는다.
  • server-side catalog gateway의 active chart-search 결과만 snapshot 원천으로 사용한다.
  • snapshot payload에는 SOAP 본문, token, provider payload, secret을 넣지 않는다.
  • remote Supabase 적용, 원격 RLS replay, production deploy, 실데이터 import는 수행하지 않았다.

제외한 것

  • 확정된 catalog order를 downstream fulfillment queue로 생성하는 작업은 후속 issue 범위다.
  • order set을 개별 child order snapshot으로 확장하는 작업은 별도 단계다.
  • billing candidate sync의 최종 화면 연결과 lab/imaging review gate는 후속 issue 범위다.
  • remote Supabase RPC replay와 live DB 적용은 하지 않았다.
