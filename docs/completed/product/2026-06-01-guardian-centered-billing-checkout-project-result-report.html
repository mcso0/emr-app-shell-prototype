보호자 중심 수납 Checkout 프로젝트 결과

이번 프로젝트는 수납 화면의 기준을 “환자 한 마리”에서 “보호자와 보호자 소유 환자들의 결제”로 바꾼 작업이다. 이제 차트에서 오더 청구를 하면 수납 화면에서 보호자 기준으로 수납대기 건을 확인하고, 필요한 청구 항목을 검토한 뒤 수납 진행, 미납 처리, 수납 완료를 처리하는 흐름이 정리됐다.

현재 Linear 상태

남은 실행 이슈는 없다. Blocked, Rework, Todo, In Progress 상태는 0건이다. 의미 있는 작업은 규칙상 Human Review에서 멈춰 승욱 검토를 기다린다.

무엇이 좋아졌나

  • 상단 정보가 환자 바이탈/품종 중심에서 보호자 연락처, 보호자 소유 환자, 수납대기/미납 요약 중심으로 바뀌었다.
  • 왼쪽 큐가 수납대기 / 미납 / 완료로 정리되어 데스크 담당자가 지금 처리할 건을 더 쉽게 찾을 수 있다.
  • 보호자 수납이력 영역에서 기간과 상태를 보고 여러 환자의 미수납/대기 건을 선택할 수 있는 구조가 생겼다.
  • 중앙 영역은 선택된 checkout 작업대가 되어 청구 항목과 추가 수납 항목을 함께 확인한다.
  • 오른쪽 수납 요약은 최종 결제금액, 결제수단, 할인/할증 사유, 수납 메모, 수납 CTA 중심으로 정리됐다.
  • 청구 확정이라는 헷갈리는 사용자 문구를 제거하고, 수납 담당자 관점의 수납 진행으로 바꿨다.
  • 미납 처리는 사유가 있어야 저장되도록 해서 “왜 미납인지” 기록이 남게 했다.

검증 결과

  • fixed staging에서 보호자 중심 수납 화면이 최신 build로 표시되는 것을 확인했다.
  • 수납 진행, 사유 필수 미납 처리, 수납 완료 흐름이 staging browser replay에서 통과했다.
  • 타입체크, focused Playwright, 서버 스펙, eslint, 문서 링크 검사, secret scan을 통과했다.
  • Staging URL: https://emr-app-shell-prototype-staging-mcso0s-projects.vercel.app

아직 범위 밖인 것

런칭 전 MVP 범위 밖

  • 실제 카드사/PG 결제, 영수증, 환불, 정산 연동은 아직 아니다.
  • production deploy, real data import, remote Supabase migration push, remote RLS replay는 하지 않았다.
  • 보호자 합산 결제를 완전한 회계 모델로 만들기 위한 checkout session/payment allocation DB 설계는 DEN-365에서 후속 승인 게이트로 정리했다.

승욱 리뷰 포인트

  • 보호자 정보바에 데스크 담당자가 실제로 필요한 정보가 충분한지
  • 수납대기/미납/완료 큐와 보호자 수납이력 선택 흐름이 직관적인지
  • 수납 진행, 미납 처리, 수납 완료 문구가 현장 업무 언어와 맞는지
