DEN-288 / 2026-05-26 / Billing Candidate Sync

청구 후보 Snapshot 동기화 보고서

차트에서 확정된 billable order snapshot과 fulfillment 완료 snapshot을 서버 소유 금액 기준으로 billing candidate에 반영하도록 연결했다. client가 보낸 금액이 아니라, DEN-286에서 고정한 applied snapshot 또는 fulfillment source snapshot을 기준으로 수량, 단가, line total을 만든다.

Status: Human Review Lab/Imaging: Vet review gate held Remote DB: Not applied

무엇이 바뀌었나

  • invoice candidate sync가 legacy order id뿐 아니라 optional order snapshot도 받을 수 있게 됐다.
  • billing_only catalog row는 차트 확정 시 바로 billing candidate를 만들 수 있다.
  • fulfillment 완료 시 dispensing과 treatment는 fulfillment source snapshot 기준으로 billing candidate를 만든다.
  • lab과 imaging은 업무 완료만으로 billing candidate를 만들지 않고, 담당 수의사 review gate 전 상태로 보류한다.
  • 비청구 row, returned/cancelled order, duplicate sync는 billing candidate로 잘못 올라가지 않게 막았다.

Billing Timing Policy

경로 청구 후보 생성 시점 이번 상태
billing_only 차트 확정 즉시 구현
dispensing fulfillment 완료 후 snapshot 기준 보강
treatment fulfillment 완료 후 snapshot 기준 보강
lab, imaging 결과가 차트로 돌아오고 담당 수의사가 확인한 뒤 업무 완료 시 자동 청구 차단
chart_only, 비청구 row 생성하지 않음 구현

DEN-287 남은 범위와의 관계

DEN-287 남은 항목 DEN-288에서의 처리
billing_only 즉시 billing candidate 해소됨
lab/imaging 담당 수의사 review gate 업무 완료 시 자동 청구는 차단했다. 실제 결과 review UI/상태는 후속 workflow 이슈가 필요하다.
inpatient queue 이번 이슈 범위 밖. 별도 follow-up으로 남는다.

보안 및 데이터 경계

  • billing amount는 client 입력값이 아니라 server-owned snapshot에서 가져온다.
  • catalog 가격이 나중에 바뀌어도 이미 생성된 candidate의 금액은 기존 snapshot 값을 유지한다.
  • remote Supabase 적용, 원격 RLS replay, production deploy, 실데이터 import, PG/payment provider 연동은 수행하지 않았다.
