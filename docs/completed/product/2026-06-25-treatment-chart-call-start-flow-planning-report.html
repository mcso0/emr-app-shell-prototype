진료/차트 접수 후 호출 및 진료 시작 흐름 기획안

접수된 환자가 진료 대기열에 올라온 뒤 수의사가 호출하고, 환자가 진료실에 들어온 후 명시적으로 진료를 시작하는 흐름으로 차트 화면의 CTA, 상태 전이, DB/API 경계를 재정리한다.

작성일: 2026-06-25 · 기준 화면: 청담점 진료/차트 화면

1. 결론

현재 우상단의 `차트 작성완료` CTA는 대기 환자에게 노출되면 안 된다. 접수 직후의 주 액션은 `호출하기`이고, 호출 후에는 `진료 시작`이 주 액션이어야 한다. `차트 작성완료`는 SOAP, 진단명, 오더 작성이 진행된 뒤 진료를 마무리하고 수납/오더 후속 흐름으로 넘길 때만 노출되는 종료 액션으로 분리한다.

제품 판단

접수 완료는 진료 완료가 아니라 진료 대기 상태다. 의사가 대기열에서 환자를 선택하고 호출한 뒤 진료 시작을 명시해야 차트 작성 맥락이 열린다.

UX 판단

상태별 CTA를 분리해야 사용자가 실수로 대기 환자를 수납 준비 상태로 넘기는 일을 막을 수 있다. 대기, 호출됨, 진료중, 수납대기 상태가 화면에서 즉시 구분되어야 한다.

개발 판단

기존 `encounters.status`, `encounters.started_at`, `waiting_queue_entries.status`, `waiting_queue_entries.called_at`를 우선 활용하고, DID 연동은 별도 호출 이벤트/outbox로 확장한다.

2. 현재 문제

구간 현재 화면/코드에서 보이는 상태 문제 수정 방향
대기열 초코 / 최도현 접수 건이 `대기중`으로 표시됨 정상. 접수 후 consultation queue에 올라와 있음 선택 시 차트 본문은 열되, 상태와 CTA는 대기 흐름을 따라야 함
우상단 CTA `차트 작성완료` 버튼이 즉시 노출됨 대기 환자를 진료 종료/수납 준비처럼 오해하게 함 `호출하기`로 교체하고 확인 모달을 거치게 함
서버 동작 현재 chart completion API/RPC는 `waiting`도 `ready_for_billing`으로 이동시킬 수 있음 접수 직후 CTA와 연결되면 상태가 한 번에 너무 멀리 이동함 completion은 `in_consultation` 이후에만 허용하거나 UI/API 양쪽에서 막음
차트 입력 SOAP/진단 저장이 `waiting -> in_consultation`을 암묵적으로 만들 수 있음 `진료 시작`이라는 명시 액션이 사라짐 대기/호출 상태에서는 입력을 읽기 전용 또는 시작 확인 후 허용

3. 목표 업무 흐름

1 접수 완료 encounter waiting · queue waiting
2 대기열 선택 환자/보호자/담당의 확인
3 호출하기 확인 모달 · DID 안내 이벤트
4 진료 시작 encounter in_consultation · queue in_progress
5 차트 작성 SOAP · 진단명 · 오더 · 작성완료

사용자 관점 시나리오

  1. 접수자가 초코/최도현 내원 건을 접수한다.
  2. 진료/차트 화면의 좌측 `진료 대기열`에 초코/최도현이 `대기중`으로 보인다.
  3. 담당 수의사가 대기열 카드를 선택한다.
  4. 우상단 주 CTA는 `호출하기`로 보인다.
  5. `호출하기`를 누르면 `초코 / 최도현을 호출하시겠습니까?` 확인 모달이 열린다.
  6. 확인하면 대기실 DID 화면에 호출 안내가 표시될 준비 상태가 기록된다.
  7. 차트 화면은 `호출됨` 상태로 바뀌고 주 CTA는 `진료 시작`으로 바뀐다.
  8. 환자가 진료실에 들어오면 수의사가 `진료 시작`을 누른다.
  9. 이후 SOAP, 진단명, 오더 입력이 본격적으로 활성화된다.
  10. 진료가 끝날 때만 `차트 작성완료`를 눌러 수납/후속 업무로 넘긴다.

4. 상태 모델

화면 상태 `encounters.status` `waiting_queue_entries.status` 주 CTA 차트 입력
대기 waiting waiting `호출하기` 읽기 전용 또는 입력 비활성. 환자 컨텍스트만 확인 가능
호출됨 waiting called `진료 시작` · 보조 `재호출` 기본은 비활성. 필요 시 `진료 시작 후 작성` 안내
진료중 in_consultation in_progress `차트 작성완료` 또는 `진료 마무리` SOAP, 진단명, 오더 입력 가능
오더 진행중 ordered in_progress 또는 done `차트 작성완료` 또는 오더별 후속 액션 입력/수정 가능. 오더 상태와 수납 후보 분리
수납대기 ready_for_billing done 상태 표시 · 수납 이동 작성완료 상태. 수정은 별도 amend/권한 정책 필요
완료 completed done 없음 또는 이력 보기 읽기 중심
중요한 구현 원칙 `queue status`는 운영 표시 상태이고, `encounter status`는 진료 업무의 기준 상태다. `called`는 환자를 부른 상태일 뿐 진료가 시작된 상태가 아니다.

5. UI 기획

5.1 상단 CTA 정책

선택/상태 Primary Secondary 마이크로카피
선택된 대기열 없음 비활성 `대기열 선택` 없음 진료 대기열에서 환자를 선택해 주세요.
대기 `호출하기` `차트 공유`는 유지 가능하나 낮은 우선순위 접수 완료 · 아직 호출 전
호출됨 `진료 시작` `재호출` 14:20 호출됨 · 환자가 들어오면 진료를 시작해 주세요.
진료중/오더 진행중 `차트 작성완료` `차트 공유` SOAP, 진단명, 오더를 확인한 뒤 작성완료하세요.
수납대기/완료 상태 표시 또는 수납 화면 이동 이력 보기 작성완료 상태. 수정은 별도 권한/사유가 필요합니다.

5.2 호출 확인 모달

Title: 초코 / 최도현을 호출하시겠습니까?

Description: 대기실 DID 화면에 "초코 보호자 최도현님, 진료실로 입장해 주세요." 안내가 표시됩니다.

Context: 담당 수의사 상담 원장 · 접수 14:15 · 진료실 미지정

Primary: 호출하기 · Secondary: 취소

현재는 진료실 데이터가 없으므로 `진료실 미지정`으로 표시하고, 추후 room/space 선택이 추가되면 모달 안에서 진료실을 선택하거나 담당 수의사의 기본 진료실을 자동 적용한다.

5.3 차트 본문 상태

  • `waiting`: 환자 정보, 접수 일시, 담당 수의사, 차트 상태만 확인. SOAP/진단/오더 입력은 비활성 또는 약한 disabled overlay.
  • `called`: 호출 결과 배너를 표시하고, `진료 시작` 전까지 입력은 막는다.
  • `in_consultation`: SOAP, 진단명 검색/저장, 오더 추가/수정/청구 기능을 활성화한다.
  • `ready_for_billing`: 작성완료 상태를 명확히 표시하고, 수납 화면으로 이어지는 후속 동선을 제공한다.

5.4 대기열 카드 상태

  • `대기중`: 기본 대기 카드. 점선/회색 상태 아이콘 유지 가능.
  • `호출됨`: 호출 시간과 호출 횟수를 카드 하단 메타로 노출. 예: `14:20 호출`.
  • `진료중`: 담당 수의사/진료 시작 시간 노출. 예: `14:23 시작`.
  • 에러 상태: 호출 저장 실패나 DID 전송 실패는 카드가 아니라 상단 inline alert로 먼저 설명한다.

6. DB/API 설계안

6.1 기존 데이터 모델 활용

기존 필드 활용 비고
encounters.status `waiting`, `in_consultation`, `ordered`, `ready_for_billing`, `completed`, `cancelled` 진료 업무의 기준 상태
encounters.started_at 수의사가 `진료 시작`을 누른 시각 호출 시각과 분리
waiting_queue_entries.status `waiting`, `called`, `in_progress`, `done`, `cancelled` 대기열 표시와 운영 상태
waiting_queue_entries.called_at `호출하기`를 확정한 시각 DID 이벤트 시간의 1차 기준
waiting_queue_entries.finished_at 진료 대기열이 끝난 시각 차트 작성완료 시점 또는 수납대기 전환 시점

6.2 신규 API 후보

API 목적 주요 전이 권한
POST /api/workspaces/[workspaceId]/chart/encounters/[encounterId]/call 환자 호출 확정 queue `waiting -> called`, `called_at = now()` chart:update 또는 담당/허용 수의사
POST /api/workspaces/[workspaceId]/chart/encounters/[encounterId]/start-consultation 환자가 들어온 뒤 진료 시작 encounter `waiting -> in_consultation`, queue `called -> in_progress`, `started_at = now()` chart:update 또는 담당/허용 수의사
PATCH /api/workspaces/[workspaceId]/chart/completion 진료 종료/차트 작성완료 encounter `in_consultation/ordered -> ready_for_billing`, queue `done`, billing queue 생성 chart:update

6.4 DID 호출 이벤트/outbox

지금 당장 실제 DID 장비 연동까지 완료했다고 주장하면 안 된다. 1차 구현은 호출 이벤트를 서버에 기록하고, DID 연동은 mock adapter 또는 outbox 상태로 남기는 것이 안전하다. 

consultation_call_events
- id uuid primary key
- workspace_id text
- encounter_id uuid
- queue_entry_id uuid
- actor_user_id uuid
- room_id text nullable
- message text
- delivery_target text check ('did_waiting_room')
- delivery_status text check ('queued', 'sent', 'failed', 'cancelled')
- provider_message_id text nullable
- idempotency_key text nullable
- created_at timestamptz

최소 1차 범위에서는 이 테이블 없이 `waiting_queue_entries.called_at` + audit event만으로도 UI 전이는 가능하다. 다만 DID 실패/재호출/전송 이력을 제품적으로 다루려면 이벤트 테이블을 두는 편이 낫다.

6.5 서버 검증 규칙

  • 호출은 active workspace membership과 chart update 권한을 요구한다.
  • 호출 대상 encounter는 같은 workspace이고 `cancelled/completed/ready_for_billing`이 아니어야 한다.
  • 호출은 consultation queue row가 있어야 한다. 없으면 `queue_entry_unavailable`로 실패한다.
  • `called` 상태에서 재호출은 허용하되, idempotency key 또는 call event로 중복 처리를 해야 한다.
  • `진료 시작`은 `waiting/called` queue에서만 허용한다. 이미 `in_progress`면 idempotent success로 처리 가능하다.
  • `차트 작성완료`는 `waiting/called` 상태에서 거부하거나 UI에서 노출하지 않는다.

9. QA 및 검증 기준

서버/API

  • `waiting` encounter 호출 시 queue가 `called`로 바뀌고 `called_at`이 기록된다.
  • `called` encounter 진료 시작 시 encounter가 `in_consultation`, queue가 `in_progress`가 된다.
  • `cancelled`, `completed`, `ready_for_billing` 대상 호출은 실패한다.
  • 권한 없는 actor는 401/403으로 거부된다.
  • 중복 호출은 안전하게 처리되고 호출 이력이 중복 폭증하지 않는다.

UI/E2E

  • 대기 카드 선택 시 `차트 작성완료`가 보이지 않고 `호출하기`가 보인다.
  • `호출하기` 클릭 시 초코/최도현 확인 모달이 열린다.
  • 호출 성공 후 버튼이 `진료 시작`으로 바뀐다.
  • 진료 시작 후 SOAP/진단/오더 입력이 가능하다.
  • 진료중 이후에만 `차트 작성완료`가 노출된다.

10. 리스크 / 확인 필요

리스크 이유 대응
기존 completion API의 과도한 전이 `waiting`도 `ready_for_billing`으로 갈 수 있음 server guard 추가. UI 숨김만으로 완료하지 않음
SOAP/진단 저장의 암묵적 진료 시작 현재 저장 RPC가 `waiting -> in_consultation`을 만들 수 있음 명시 `진료 시작`이 전이를 소유하도록 조정하거나 UI에서 입력을 막음
DID 실제 연동 범위 대기실 모니터 전송은 외부 장비/운영 사이드이펙트 1차는 mock/outbox. 실제 장비 전송은 별도 승인과 설정 필요
진료실 데이터 부재 호출 메시지에 room/space가 아직 없음 `진료실 미지정`으로 표시하고 추후 `spaces`/room assignment 추가
기존 테스트 기대값 기존 chart tests는 `차트 작성완료`가 초기 노출된다고 기대할 수 있음 테스트를 상태별 CTA 정책으로 재작성

11. 이번 보고서의 범위 밖

  • 실제 DID 장비 또는 대기실 모니터로 메시지를 전송하는 production 연동
  • 진료실/공간 관리 전체 설계와 스케줄링
  • 실제 고객/환자/보호자 데이터 사용
  • 원격 Supabase에 migration 적용 또는 production 배포
  • 최종 의료 기록 법적 서명/수정 정책 확정

12. 구현 전 결정해야 할 질문

  1. `호출하기` 권한은 담당 수의사만 가능한가, hospital admin도 가능한가?
  2. 호출 없이 바로 `진료 시작`을 허용할 운영 예외가 필요한가?
  3. 재호출 버튼은 몇 초/몇 분 제한이 필요한가?
  4. 진료실 데이터가 생기기 전 DID 문구는 `진료실로 입장해 주세요`로 충분한가?
  5. 대기/호출 상태에서 SOAP 임시 메모를 허용할지, 완전히 막을지 결정해야 한다.
