Executive decision

결론부터 말하면, TanStack을 공통 엔진으로 쓰는 게 맞다.

단, TanStack에 CLAiR의 디자인과 업무 로직을 모두 떠넘기는 구조는 피해야 한다. TanStack은 상태와 행·컬럼 모델을 계산하고, EmrDataTable은 고객관리 스타일과 표 렌더링을 책임진다. 검색, API 호출, 담당자 지정 같은 업무 동작은 각 기능에 남긴다.

Implementation snapshot

제안한 공통 렌더러와 주요 업무 표 전환을 반영했다.

별도 origin/main 작업공간에서 EmrDataTable<TData>을 TanStack table instance 기반의 공통 렌더러로 구현했다. 원래 혼합 WIP 작업공간은 보존했고, 이 보고서에는 구현 결과와 남은 승인 경계까지 반영했다.

구분 반영한 내용 확인 결과
Workspace 상단 헤더 EmrTableWorkspaceHeader는 EmrDataTable과 분리된 형제 컴포넌트로 유지 상단 제어와 표 렌더링의 책임이 섞이지 않음

Research findings

공식 문서와 현재 코드는 같은 방향을 가리킨다.

TanStack Table은 완성된 표 UI가 아니라 headless 상태 엔진이다. 제품이 마크업과 스타일을 소유해야 하므로, CLAiR의 고객관리 스타일을 공통 컴포넌트에 넣는 데 적합하다.

확인 항목 공식 문서의 핵심 CLAiR 적용 판단
Headless 구조 행·컬럼 모델과 상태 API를 제공하고 DOM·스타일은 제공하지 않는다. 고객관리 시각 규칙은 EmrDataTable이 직접 소유한다.
상태 제어 외부에서 필요한 상태만 선택적으로 controlled로 끌어올린다. rowSelection 등 업무에 쓰는 상태만 기능 영역에서 관리한다.
컬럼 고정 sticky CSS와 column pinning API로 단일 table 구현이 가능하다. 기존 단일 overflow와 getEmrPinnedColumnProps를 유지한다.
행 선택 안정된 getRowId로 선택 상태를 데이터 ID에 연결한다. 정렬·필터 이후에도 일괄 선택이 깨지지 않도록 화면별 ID를 지정한다.
컬럼 크기 React에서는 기본 onEnd가 안전하며 실시간 변경은 최적화가 필요하다. 측정된 요구가 생기기 전까지 onChange를 기본값으로 만들지 않는다.
가상화 Table 자체 기능이 아니며 TanStack Virtual 같은 별도 도구가 필요하다. 수천 행 문제가 측정되기 전에는 이번 범위에서 제외한다.

Before · After · Why

이름만 공통인 컴포넌트를 실제 공통 컴포넌트로 바꾼다.

Before After Why
emr-data-table.tsx가 Order·담당자·완료 처리에 결합 조제 전용 표는 OrderWorkTable로 이동 공유 계층에서 도메인 로직을 제거하고 이름과 책임을 맞춘다.
상단 헤더와 데이터 테이블을 화면마다 함께 조립 공유 EmrTableWorkspaceHeader와 EmrDataTable을 형제 컴포넌트로 구성 제목·건수·검색·필터와 thead·행·셀의 책임을 섞지 않는다.
고객관리만 TanStack 렌더링과 완성된 시각 규칙을 보유 공통 EmrDataTable<TData>이 렌더링과 스타일을 소유 한 곳의 스타일 변경이 모든 업무용 데이터 테이블에 이어진다.
화면마다 header·row·hover·selected 클래스를 반복 고객관리 기준 스타일을 데이터 테이블 범위의 token으로 이동 시각 회귀와 중복 CSS를 줄이고 일반 Table에는 영향 주지 않는다.
고정 경계와 행 아래 남는 viewport를 화면별 CSS·gradient로 보정 TanStack pinning 상태와 총 고정 폭을 공유 sticky·full-height 표면 계약에 전달 하나의 table·overflow owner를 유지하면서 마지막 행 아래까지 고정 영역을 끊김 없이 이어 간다.
공통화할수록 props와 wrapper가 늘어날 위험 공통 컴포넌트는 table instance를 받고 최소 확장점만 제공 정렬·필터·선택·업무 콜백이 거대한 props API로 번지는 것을 막는다.

Proposed architecture

세 계층으로 나누면 코드가 오히려 단순해진다.

핵심은 “무엇이 공통인가”를 스타일과 렌더링에 한정하는 것이다. 데이터 준비와 업무 동작까지 공통화하지 않는다.

먼저 용어와 화면 구성을 분리한다.

EmrTableWorkspaceHeader는 제목·건수·검색·필터·주요 액션을 맡는다. EmrDataTable의 header는 thead/th 컬럼 헤더를 뜻한다. 기능 화면은 두 컴포넌트와 feedback surface를 조립하며, workspace 상단 헤더를 EmrDataTable 내부 props로 넣지 않는다.

3 Table primitive

semantic table 요소와 density, min-width, overflow, sticky cell의 저수준 계약과 축별 overscrollAxes를 제공한다.

components/ui/table.tsx 
const table = useReactTable({
  data: rows,
  columns,
  getRowId: (row) => row.id,
  getCoreRowModel: getCoreRowModel(),
  getSortedRowModel: getSortedRowModel(),
  state: { sorting, rowSelection, columnPinning },
  onSortingChange: setSorting,
  onRowSelectionChange: setRowSelection,
});

return (
  <EmrDataTable
    aria-label="처방/오더 테이블"
    density={density}
    overscrollAxes="both"
    table={table}
  />
);
피해야 할 API

EmrDataTable이 data와 columns부터 sorting, filtering, pagination, pinning, visibility, sizing 콜백을 모두 직접 받는 구조는 만들지 않는다. 처음에는 간단해 보여도 화면이 늘수록 props가 끝없이 추가된다. 다만 overscrollAxes처럼 이미 저수준 Table이 소유한 layout 계약을 선택적으로 전달하는 것은 업무 props 확장과 구분한다.

두 모드 모두 하나의 table과 하나의 overflow container를 쓴다. 고정 영역과 스크롤 영역을 별도 table로 나누지 않아야 header와 body 높이, hover·selected 배경, focus ring이 어긋나지 않는다. 페이지 자체가 세로로 움직이는 표는 기본 horizontal overscroll 억제를 사용하고, 고객관리처럼 내부 viewport가 가로·세로 스크롤을 모두 소유하는 표는 overscrollAxes="both"를 사용한다.

Migration plan

한 번에 갈아엎지 않고, 실제 사용처로 계약을 검증한다.

  1. 이름 충돌 해소와 공통 기반

    기존 조제 전용 EmrDataTable을 src/features/dispensing 아래 OrderWorkTable로 옮기고, 새 공통 렌더러와 Storybook의 전체 스크롤형·고정 컬럼형 사례를 만들었다.

  2. 고객관리 기준선과 병원관리 고정 컬럼

    고객관리 메인·보관 목록의 렌더링을 공통 컴포넌트로 교체했다. 이어 병원관리 Order 하위 화면에 표 controller와 고정 컬럼 계약을 연결했다.

  3. 진료/차트와 조제/처치

    편집 셀, 일괄 선택, 담당자 지정, 완료 처리, 경고 추가 행을 기능 adapter와 공통 renderer 조합으로 유지했다.

  4. 나머지 업무 화면과 정리

    임상병리, 영상검사, 입원, 감사 로그, 구성원, 수납도 옮겼다. 사용처가 사라진 고객관리 header/cell helper와 feature 전용 표 반복 렌더링은 삭제했다.

문서 계약도 함께 바뀌어야 한다.

기존 설계 문서의 “다른 화면을 현재 EmrDataTable에 강제로 넣지 않는다”는 규칙은 조제 전용 컴포넌트를 전제로 한 내용이었다. 이제 component ownership 문서의 표 책임을 새 공통 계약으로 교체했고, 일반 Table과 업무용 EmrDataTable의 경계도 함께 기록했다.

구현 확인 상태

TypeScript·ESLint·문서 링크·secret scan·한국어 UX copy 검사를 통과했고, Storybook build와 Next production build도 완료했다. 고객관리·병원관리 pinned 회귀 8개, 차트 업무 회귀 6개, 정렬·필터 QA 4개, 임상 업무 대표 회귀와 1440·1280·1024px document overflow 검사를 확인했다. 조제·영상·구성원 일부 기존 화면 테스트는 표 전환 지점이 아닌 mock 인증·선택 상태 전제에서 실패해 별도 후속 항목으로 남겼다. merge·deploy와 Quick Tunnel 공유는 수행하지 않았다.

최종 제안

TanStack Table v8을 EmrDataTable의 상태·행·컬럼 엔진으로 채택한다. 일반 Table은 유지하고 업무용 데이터 그리드만 새 컴포넌트로 옮긴다. 이렇게 하면 고객관리 스타일을 한 곳에서 바꿨을 때 연결된 화면이 함께 바뀌면서도 고객·Order·검사·수납 로직은 각 기능 경계 안에 남는다.

이 문서는 2026-08-09 기준 별도 codex/emr-data-table-tanstack 작업공간의 구현·검증 상태를 반영한다. 원래 혼합 WIP 작업공간은 수정하지 않았으며, merge·deploy와 Quick Tunnel 공유는 범위에 포함하지 않았다.
문장 정리는 humanize-korean strict workflow로 검토했으며 기술 용어, 버전, 수치, 파일 경로와 공식 문서 URL을 보존했다.
