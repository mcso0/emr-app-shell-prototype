2026-06-02 · Product/Design planning · Global notification center

CLAiR 전역 알림 센터 PRD 브리핑

알림 센터는 홈의 내 업무를 대체하지 않는다. 앱 전역에서 사용자가 알아야 할 사건을 모아 보여주고, 처리 가능한 항목은 원본 업무 화면으로 깊게 연결하는 별도 채널이다.

v0 권장 방향은 상단/네비 알림 버튼에서 열리는 오른쪽 drawer형 알림 센터다. 업무 중 맥락을 잃지 않고 최신 알림을 훑고, 읽음/보관/원본 이동만 빠르게 처리하는 구조가 CLAiR의 조밀한 운영 화면과 가장 잘 맞는다.

권장 시안 A: drawer 구현 전 질문 필요 Mock/local-first 우선 Live push/provider 제외

1. 목적과 사용자 가치

문제

  • 진료, 검사, 조제, 수납, 접수 흐름이 분리되어 있어 사용자가 중요한 변화를 놓칠 수 있다.
  • 모든 신호를 홈에 올리면 홈이 업무 큐와 공지함이 섞인 화면이 된다.
  • 단순 toast만 있으면 나중에 다시 볼 수 없고, 중요한 업무 추적성이 떨어진다.

목표

  • 사용자별, 역할별로 관련 있는 알림을 시간순으로 모아 보여준다.
  • 알림이 실제 액션을 요구하면 원본 업무 화면으로 이동시킨다.
  • 읽음, 보관, 재확인, 필터를 통해 알림 과부하를 줄인다.

2. 내부 기준

기준 현재 문서 근거 알림 센터 적용
홈과 알림 분리 docs/product/features/home/home-command-entry-planning.md는 전역 notification을 앱 오른쪽 상단 알림 카드/drawer로 정의한다. 알림 센터는 전역 채널이다. 홈 내 업무에는 실제 담당 action만 올라간다.
밝고 조밀한 운영 UI docs/design/system/DESIGN.md는 조용하고 정확한 운영 워크스페이스, semantic status, 8px 안팎 radius를 기준으로 둔다. 대형 마케팅식 패널 대신 리스트, 필터, 원본 이동 액션 중심으로 설계한다.
Mock/live 경계 docs/engineering/current-status.md는 live push, remote Supabase, provider 연동을 승인 게이트로 둔다. v0 구현은 synthetic notification fixtures와 local-first read state까지만 안전하다.

3. 외부 서비스 조사 요약

서비스 관찰한 패턴 CLAiR에 가져올 점
Microsoft Teams Activity Feed 알림은 activity feed에서 triage하고, 관련 앱/탭으로 deep link한다. 중복 알림과 무관한 알림을 피하라고 권고한다. 보관 기간도 사용자에게 알려야 한다. 알림 title/preview/action target을 명확히 하고, 같은 사건의 중복 알림은 chain/update로 묶는다.
Linear 모든 알림은 Linear Inbox에 보이고, desktop/mobile/Slack/email은 채널별 보조 수단이다. email digest는 읽지 않은 inbox notification에 따라 지연 발송된다. CLAiR도 in-app inbox를 기준 채널로 두고, 외부 채널은 후속 provider 범위로 분리한다.
Notion Inbox 워크스페이스 업데이트를 Inbox에 모으고, unread/read/archive 필터와 page/comment thread 단위 묶음을 제공한다. 환자, encounter, order, device result 같은 원본 entity 단위 그룹핑을 제공한다.
GitHub Notifications Inbox에서 read/unread, saved, done, unsubscribe, custom filter로 triage한다. v0는 읽음/보관/전체 읽음, v1은 저장/숨김/구독 해제 성격의 preference로 확장한다.
ClickUp Inbox, email, browser/desktop, mobile 채널별로 Default/Focused/Mentions only/Custom 설정을 둔다. 역할별 기본 필터와 개인별 알림 preference를 분리한다.
Slack DM, thread reply, mention, keyword 중심으로 badge와 banner를 나누고, 비활성 상태에서 email/mobile로 보낸다. CLAiR에서는 담당자 지정, 오더 재요청, 긴급 전달, overdue 같은 강한 signal에 badge 숫자를 제한한다.
Asana Inbox Inbox에서 unread, mention, assigned task, sender 등으로 필터링하고, inbox 안에서 reply/archive/follow-up을 처리한다. 알림에서 바로 원본 화면으로 이동하되, 실제 임상/수납 final action은 원본 workflow에서 수행한다.

4. 알림 분류

분류 예시 기본 대상 v0 처리
Action required 긴급 전달, 재요청/재확인 요청, 담당 오더 확인 요청 담당자 또는 역할 큐 v0 구현 대상. 대표 event만 mock/local-first로 시작한다.
Workflow signal 대기 30분 초과, 검사/영상/조제/처치 완료, 장비 결과 전달, 입원 처치 지연 역할별 관련 사용자 v0 구현 대상. 대기 지연, 오더 완료 안내, 장비 결과 전달처럼 이미 화면 흐름이 있는 event부터 시작한다.
Mention / handoff 수의사가 테크니션에게 오더 재확인 요청, 영상 담당자가 재촬영 요청 요청받은 사용자 또는 역할 큐 v0에서는 오더 재요청/재확인 같은 제한된 handoff만 다룬다. 자유 멘션/댓글형 알림은 v1 이후.
Awareness only 공지, 설정 변경, 반복 상태 업데이트 관련 역할 또는 전체 v0에서는 drawer-only fixture로 분류만 잡는다. 공지 작성/발행/관리 기능은 v1 이후.
System/security 권한 변경, 로그인/워크스페이스 이상 상태 관리자, 해당 사용자 v0 알림 매트릭스에서는 제외한다. 보안 알림 시스템은 v1 이후 별도 PRD로 둔다.

이 표는 전체 알림 taxonomy다. v0 구현은 Action required와 Workflow signal 중심이며, Mention / handoff는 재요청/재확인처럼 오더에 연결된 handoff만 포함한다. 댓글형 멘션, 공지 발행 시스템, 보안 알림 정책 엔진은 v0 이후 별도 PRD/작업으로 둔다.

4-1. Badge Count Policy

high-signal, high severity unread 같은 표현은 구현 기준으로 쓰지 않는다. v0에서는 알림을 requires_action, priority, badge_count 세 값으로 판정한다.

구분 정의 badge 숫자 포함 예시
Badge-count notification 안 읽음이고, 현재 사용자 또는 현재 역할이 당일 업무 흐름에서 조치하지 않으면 지연/누락이 생기는 알림. 포함 담당 오더 긴급 전달, 재요청/재확인 요청, 결과 확인 요청, 보호자 대기 안내 필요
Drawer-only notification 사용자가 알아야 하지만 즉시 action owner가 아니거나, 참고/상태 변화 성격이 큰 알림. 제외 조제 완료 참고, 일반 공지, 병원 설정 변경, 다른 역할 큐의 낮은 우선순위 상태 변화
Muted/system notification 기록은 남기지만 기본 drawer 상단과 badge에 올리지 않는 낮은 우선순위 시스템 신호. 제외 백그라운드 sync 성공, 반복 상태 업데이트, 읽은 알림의 후속 중복 업데이트

v0 badge 계산식은 unread && badge_count === true이다. badge_count는 아래 event rule table에서만 결정한다. 화면 구현자가 임의로 severity label이나 카드 색상만 보고 badge 포함 여부를 추론하지 않는다.

severity color와 badge 포함 여부는 분리한다. 예를 들어 대기 안내는 clinical danger가 아니어도 데스크에게는 badge-count 대상이고, 병원 공지는 unread여도 기본 badge 숫자에는 들어가지 않는다.

v0 event 수신자 requires_action priority badge_count 판정 기준
오더 긴급 전달 오더 담당 수의사 또는 현재 책임자 true high true 오더 수행자나 담당자가 명시적으로 긴급 전달/빠른 확인 필요를 선택한 경우. 자동 abnormal 수치만으로는 생성하지 않는다.
오더 재요청/재확인 요청 요청받은 사용자 또는 역할 큐 true high true 수의사, 검사/영상/조제/입원 담당자가 특정 사용자/역할에게 재요청, 재확인, 보완 입력을 요청한 경우.
담당 오더 완료 안내 오더 담당자, 담당 수의사 true normal_action true 내가 담당자 또는 담당 수의사로 지정된 오더가 완료됐고, 아직 내가 확인하지 않은 경우.
검사/임상 결과 완료 담당 수의사 true normal_action true 검사 queue item이 완료됐고 담당 수의사 확인이 아직 없는 경우.
검사 장비 결과 전달 담당 수의사, 검사 담당자 true normal_action true EMR 연동 장비가 검사 결과를 보내왔고 담당자가 원본 결과와 연결된 오더를 확인해야 하는 경우.
영상 결과/판독 완료 담당 수의사, 영상 담당자 true normal_action true 영상 촬영 또는 판독 완료 후 담당 수의사 확인이 필요한 경우.
대기 30분 초과 데스크 true normal_action true 보호자 안내 또는 접수 상태 조정이 필요한 desk action으로 전환되는 경우.
조제/처치 완료 담당 수의사, 조제/처치 담당자, 수납 role false 기본 info false 기본 상태 공유 성격이면 drawer-only. 담당자 확인/재요청이 필요한 경우에만 별도 badge event로 승격한다.
수납 대기 전환 수납 role, 데스크 role false 기본 info false 오더가 수납 후보로 넘어간 상태 공유 알림. 금액 검증/차단 알림은 이 매트릭스에서 제외한다.
입원 처치/투약 지연 입원 담당자, 담당 수의사 true high true 예정 시간이 지난 입원 처치/투약 오더가 있고 담당자가 지정되어 있는 경우.

4-3. Event별 Alert/Toast UI 시안

Toast alert: 짧게 알려주고 사라지는 알림 검사 결과 도착, 장비 결과 전달, 영상 판독 완료, 조제 완료처럼 사용자가 바로 원본 화면으로 갈 수 있지만 현재 입력을 막지는 않는 event에 쓴다. 색상 배경은 쓰지 않는다.
Inline alert: 현재 workflow 안에 남는 알림 장비 결과 매칭 실패, 오더 저장 실패, 권한 차단, live read 실패처럼 사용자가 그 화면에서 문제를 이해하고 복구해야 하는 event에 쓴다.
Drawer-only: 화면을 방해하지 않는 알림 일반 공지, 반복 상태 변화, 사용자가 action owner가 아닌 참고 신호는 화면 alert를 띄우지 않고 알림 센터에만 쌓는다.
Action rule alert의 primary action은 항상 원본 업무 화면 이동이다. 임상 판단, 수납 확정, 처방 변경 같은 final action은 alert에서 바로 실행하지 않는다.
Stacking rule toast는 동시에 최대 3개만 노출한다. 4번째 이후는 queue에 대기시키고, 일반 toast가 닫히면 순서대로 노출한다.

Toast Stacking 정책

정책 v0 결정 동작
최대 노출 한 화면에 최대 3개 동시에 3개를 넘으면 새 toast는 내부 queue에 대기한다.
정렬 최신 toast가 위 새로운 긴급/확인 toast가 들어오면 stack 상단에 배치한다.
자동 닫힘 일반 toast는 자동 dismiss, 긴급 toast는 더 오래 유지 정확한 시간은 구현 시 sonner 설정과 맞추되, dismiss 후 queue의 다음 toast를 표시한다.
중복 toast 동일 dedupe_key는 기존 toast를 update/bump 같은 환자+오더 지연 알림이 반복되면 새 toast를 추가하지 않고 시간/문구만 갱신한다.

5. v0 기능 스펙

포함

  • 알림 버튼 badge: 전체 unread가 아니라 Badge-count notification 수.
  • 전역 알림 drawer/page: 전체, 안 읽음, 내 업무, 오더 유형 필터.
  • 시간순 그룹: 오늘, 어제, 이번 주, 이전.
  • 알림 row: 상태점, 업무 타입 badge, UX title, detail, source metadata, 상대 시간, read state, 원본 이동 action.
  • 원본 이동: 접수, 차트/오더, 검사, 영상, 조제/처치, 수납, 입원 deep link.
  • 읽음/안 읽음, 전체 읽음, 보관.
  • 현재 탭 원본 이동과 dirty state confirmation dialog.
  • 동일 환자+동일 오더 미확인 알림의 dedupe/update-bump 처리.
  • Toast 최대 노출 개수와 queue/auto-dismiss 관리 정책.
  • Mock/local-first seed data와 localStorage 기반 read/archive state.

제외

  • 실제 push notification, service worker, background sync.
  • 카카오 알림톡, SMS, email provider 전송.
  • remote Supabase migration/RLS/live validation.
  • 역할 큐 read/archive 상태의 클라이언트 간 실시간 동기화.
  • 알림 안에서 임상/수납 final action 직접 수행.
  • 실제 고객/환자 데이터 기반 발송.
  • 모바일 native notification 정책.

6. 데이터와 시스템 구조 제안

아래 구조는 PRD/설계 제안이다. 실제 DB migration, RLS, live Supabase 적용은 현재 프로젝트 guardrail상 별도 승인 후 진행해야 한다.

1. Domain event order urgent, order recheck requested, order completed, device result received
2. Rule resolver event_type, status, recipient, badge_count, toast_policy, dedupe key 계산
3. Notification workspace scoped immutable event record
4. Delivery/read state recipient별 read, archived, channel state
5. UI surfaces badge, drawer, full center, source deep link
테이블/객체 핵심 필드 설계 의도
notification_events id, workspace_id, event_type, severity, title, body, actor_user_id, source_type, source_id, deep_link, dedupe_key, created_at, updated_at, occurrence_count 알림 원본 사건. audit log와 다르게 사용자 알림 표시를 위한 product event다.
notification_recipients notification_id, recipient_user_id, recipient_role, read_at, archived_at, saved_at, delivered_in_app_at 같은 사건을 여러 사용자에게 보내되, 읽음/보관 상태는 recipient별로 분리한다.
notification_preferences user_id, workspace_id, channel, event_type, mode, quiet_hours 현재 개인 프로필의 알림 opt-in placeholder를 확장하는 별도 preference. 권한 source가 아니다.
notification_rules workspace_id, event_type, recipient_policy, default_severity, dedupe_window, retention_days 병원별 운영 정책. v0는 코드 상수/mock으로 시작하고, v1에서 관리 화면으로 이동한다.

v0 Local State / Dedupe 계약

항목 v0 결정 이유/제약
저장소 localStorage를 기본으로 사용한다. 새로고침 후에도 read/archive state가 유지되어 QA와 사용성 테스트 혼선을 줄인다.
역할 큐 동기화 v0에서는 브라우저/사용자 간 역할 큐 read/archive 동기화를 지원하지 않는다. A 데스크가 읽어도 B 데스크의 브라우저 badge는 그대로 남을 수 있다. 이는 mock/local-first 프로토타입의 의도된 제약이다.
dedupe key workspace_id + patient_id + encounter_id + order_id + event_type + recipient_scope를 기본 단위로 본다. 동일 환자+동일 오더의 미확인 알림이 반복 생성되어 목록을 밀어내는 문제를 막는다.
중복 신호 UI 미확인 상태의 동일 dedupe_key 알림은 새 row를 append하지 않고 기존 row를 update/bump한다. updated_at을 최신 시간으로 갱신해 상단으로 올리고, 필요하면 occurrence_count로 반복 신호를 표시한다.

7. UI/UX 원칙

조용한 badge

숫자는 “모든 알림”이 아니라 안 읽은 중요 알림 또는 사용자 조치 필요 항목 중심으로 제한한다.

원본 우선

알림은 context와 진입을 제공한다. 진료 완료, 결제 확정, 처방 변경 같은 final action은 원본 화면에서 한다. 원본 이동은 현재 탭 이동으로 통일하고, 저장되지 않은 변경사항이 있으면 이동 전 confirmation dialog를 띄운다.

그룹과 필터

시간순 timeline이 기본이고, 업무 종류/역할/읽음 상태 필터로 과부하를 줄인다.

11. 권장 결정

  1. v0는 시안 A drawer를 기본으로 한다. 알림 버튼을 누르면 오른쪽 drawer가 열리고, 현재 업무 context는 유지한다.
  2. drawer 안에서 모든 final action을 처리하지 않는다. 원본 화면 이동, 읽음, 보관, 전체 읽음만 기본으로 둔다.
  3. 원본 이동은 현재 탭 이동으로 통일한다. 저장되지 않은 변경사항이 있으면 이동 전에 confirmation dialog를 띄운다.
  4. badge 숫자는 제한한다. unread 전체가 아니라 “내가 놓치면 업무 지연이 생기는 알림”을 우선한다.
  5. v0 저장소는 localStorage로 확정한다. 역할 큐 read/archive는 클라이언트 간 동기화되지 않는 프로토타입 제약으로 명시한다.
  6. 시안 B는 v1 전체 보기로 남긴다. 검색, 대량 처리, 보관함, preference가 필요해질 때 확장한다.
  7. 시안 C는 Home My Work와의 경계가 정해진 뒤 도입한다. 업무 큐 역할을 하려면 홈 정책과 함께 다시 결정한다.

12. 승욱에게 확인할 질문

질문 결정이 필요한 이유 루멘 추천 기본값
알림 badge 숫자는 전체 안 읽음으로 할까, 내 action 필요 항목으로 할까? 전체 안 읽음은 금방 noisy해질 수 있고, action 중심은 업무성은 높지만 일부 참고 알림이 숨는다. 전체 unread가 아니라 Badge-count notification만 숫자 badge. 기준은 unread && requires_action && recipient_is_current_user_or_active_role.
알림 센터에서 “완료/처리” 버튼까지 허용할까? 알림 안에서 업무를 끝내면 원본 workflow audit/context가 약해질 수 있다. v0는 원본 이동만. 읽음/보관은 허용.
알림에서 원본 화면으로 이동할 때 현재 탭을 이동할까, 새 탭을 열까? 차트/오더 작성 중 이동하면 저장되지 않은 변경사항이 사라질 수 있다. 반대로 새 탭은 업무 context가 분산된다. 승욱 결정: 현재 탭 이동으로 통일. 단, dirty state가 있으면 “작업 중인 내용이 저장되지 않을 수 있습니다. 이동하시겠습니까?” confirmation dialog를 먼저 띄운다.
보관된 알림은 얼마 동안 보여줄까? 법적 audit과 product notification retention은 다르다. notification UI 보관함 30일, audit/event 기록은 별도 정책.
역할별 기본 수신 범위를 어떻게 둘까? 데스크, 수의사, 테크니션, 관리자마다 같은 사건의 의미가 다르다. 담당자 직접 알림 우선. 역할 큐 알림은 Badge-count notification 조건을 만족할 때만 badge에 포함하고, 나머지는 drawer-only로 둔다.
담당자가 없는 역할 큐 알림을 badge에 포함할까? 역할 큐까지 badge에 넣으면 누락은 줄지만 책임자가 모호한 알림이 많아질 수 있다. v0는 담당자 직접 알림을 badge 우선. 역할 큐는 긴급/지연처럼 action owner가 명확할 때만 badge에 포함.
카카오 알림톡/문자 발송 이력과 staff in-app 알림을 한 화면에 섞을까? 외부 보호자 메시지와 내부 업무 알림은 대상과 책임이 다르다. 분리. 이 문서는 staff in-app 알림만 다룬다.
최초 구현은 어느 화면에서 실제 deep link를 연결할까? 모든 모듈을 한 번에 연결하면 PR 범위가 커진다. 검사/임상 결과 완료, 오더 재요청/긴급 전달, 대기 지연 3개 사건으로 시작.
알림 설정 화면을 v0에 포함할까? 설정까지 넣으면 사용자 통제는 좋아지지만 범위가 커진다. v0는 read-only 기본 정책, v1에서 preference 설정.

v0 공통 정책

정책 기본안 리뷰 포인트
read 사용자가 알림 row를 열거나 읽음 처리를 누르면 read. read는 처리 완료가 아니다. 읽은 알림은 badge count에서 제외하고, 현재 리스트에는 유지하되 텍스트/상태점을 dimmed 처리한다. 읽음 스타일은 opacity 50-60% 범위에서 디자인 QA로 확정.
archive 보관을 누르면 현재 리스트에서 즉시 사라지고, 보관함/보관 필터에서만 다시 볼 수 있다. 업무 완료 의미가 아니다. toast secondary action은 나중에 보기, drawer row action은 보관으로 구분.
toast lifetime 일반 toast는 자동 dismiss. 긴급 toast는 사용자가 원본 이동/닫기 전까지 더 오래 유지한다. 동시에 최대 3개만 노출하고, 나머지는 queue에서 대기한다. 정확한 유지 시간은 구현 시 sonner 설정과 맞춰 확정.
badge count unread && badge_count === true. drawer-only/reference 알림은 숫자에 포함하지 않는다. 조제 완료를 badge에서 계속 제외할지.
storage v0는 synthetic fixtures + localStorage read/archive state. live Supabase/RLS는 별도 승인 전까지 제외. 새로고침 후에도 상태가 유지되지만, 다른 브라우저/사용자와 동기화되지는 않는다.
role queue local limit 역할 큐 알림도 v0에서는 현재 브라우저의 localStorage 상태만 반영한다. A 데스크가 읽거나 보관해도 B 데스크의 브라우저에는 안 읽은 badge가 남을 수 있다. QA/리서치에서 의도된 제약으로 안내한다.
source navigation 알림의 primary action은 현재 탭에서 원본 업무 화면으로 이동한다. 이동 전 현재 화면에 dirty state가 있으면 confirmation dialog를 띄운다. 확인 문구: 작업 중인 내용이 저장되지 않을 수 있습니다. 이동하시겠습니까?
dedupe/update 동일 환자+동일 오더+동일 event의 미확인 알림은 새 row를 append하지 않고 기존 row를 update/bump한다. 반복 신호는 updated_at, 상대 시간, 필요 시 occurrence_count만 갱신한다.
permission fallback 권한이 없거나 source entity가 없으면 원본 이동 대신 알림 상세 fallback과 이유를 보여준다. 권한 fallback에서 관리자 문의 CTA를 넣을지.

14. 구현 로드맵 초안

단계 범위 완료 기준
PR 1: Shell drawer prototype 알림 버튼 click, drawer UI, mock notification fixtures, read/archive localStorage state. top menu/nav rail에서 열림, 필터/읽음/보관 동작, 역할 큐 local-state 제약 안내, 기존 화면 유지.

PR 3: Notification generation rules mock/local-first domain event에서 notification 생성 규칙, dedupe/update-bump, toast stacking 연결. 검사/임상 결과 완료, 오더 긴급 전달, 오더 재요청, 대기 지연 같은 대표 사건이 자동 생성되고 중복 알림이 기존 row/toast로 갱신됨.
PR 4: Full center / settings proposal 전체 보기, 검색, 보관함, preference 화면의 후속 설계. 사용량과 승욱 결정에 따라 implementation scope 확정.

15. 리스크와 주의점

  • 알림은 audit log가 아니다. 사용자 알림 삭제/보관과 보안/임상 audit 보존을 분리해야 한다.
  • client-only role filtering은 보안 경계가 아니다. live 단계에서는 server/API/RLS recipient filtering이 필요하다.
  • v0의 역할 큐 read/archive는 localStorage 기반이라 사용자 간 동기화되지 않는다. 사용성 테스트에서는 이 제약을 사전에 안내해야 한다.
  • 원본 이동 전 dirty-state guard가 빠지면 차트/오더 작성 중 데이터 유실 위험이 생긴다. deep link 구현의 필수 완료 기준으로 둔다.
  • dedupe/update-bump가 없으면 동일 오더 지연/장비 결과 알림이 반복 row로 누적되어 drawer noise가 커진다.
  • 실제 push/provider를 먼저 붙이면 운영 정책이 불명확한 상태에서 noise가 커질 수 있다.
  • Home My Work와 알림 센터가 같은 “해야 할 일”을 서로 다르게 표시하면 신뢰가 떨어진다.
