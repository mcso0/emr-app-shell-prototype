핵심 결과

  • 상단 badge는 전체 unread가 아니라 unread && badge_count === true 기준으로 표시된다.
  • drawer header는 중요 알림 7개 · 안 읽음 9개로 badge-count와 unread를 분리해서 보여준다.
  • role queue read/archive는 현재 브라우저 localStorage 상태로 유지되며, 다른 사용자/브라우저와 동기화되지 않는다는 안내가 표시된다.
  • 알림 primary action은 현재 탭에서 원본 업무 화면으로 이동한다.
  • source entity가 없는 장비 결과는 drawer 안에서 fallback detail과 사유를 표시한다.
  • 읽음 처리된 badge-count 알림은 즉시 badge에서 제외된다. 검증 중 7 → 6 → 5로 감소했다.

수동 UI 검증

in-app Browser

Browser 플러그인으로 localhost, 127.0.0.1, [::1] loopback URL을 열었지만 모두 ERR_BLOCKED_BY_CLIENT로 차단되었다. 이 차단은 앱 코드 동작 실패가 아니라 해당 브라우저 surface의 로컬 HTTP 접근 차단으로 기록했다.

Playwright CLI

같은 로컬 앱을 Playwright CLI wrapper로 열어 실제 UI 흐름을 검증했다. 시각 screenshot 저장은 drawer 안정성 판정 대기에서 timeout이 발생해 사용하지 않았고, 대신 snapshot artifact를 산출물로 남겼다.

콘솔 관찰

Playwright CLI 콘솔에는 reception calendar/queue API의 401, 403가 기록되었다. 이는 현재 화면이 mock/local-first demo data fallback을 표시하는 기존 경계와 일치하며, 이번 알림 센터 v0 범위의 live Supabase, RLS, provider 발송, production 배포 범위로 확장하지 않았다.

제외 및 남은 검토

  • live push, service worker, provider 발송, Kakao/SMS/email 알림은 v0 제외 범위로 유지했다.
  • remote Supabase migration, RLS, live validation은 이번 프로젝트 범위로 확장하지 않았다.
  • 역할 큐 read/archive의 클라이언트 간 실시간 동기화는 의도적으로 제외했다.
  • Human Review 상태의 12개 이슈는 대표자 검토 후 필요 시 Done으로 이동하면 된다.
최종 판정: 구현과 검증 기준은 충족했다. 운영상 남은 단계는 Human Review 승인이다.
