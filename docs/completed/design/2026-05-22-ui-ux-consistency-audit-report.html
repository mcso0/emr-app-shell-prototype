서비스 전 화면의 UI 밀도, 컴포넌트 재사용, 토큰 활용, CTA/다이얼로그/폼 UX를 점검했다. 결론은 색상 토큰 기반은 갖춰져 있지만, 간격/폭/폰트/다이얼로그 규격이 화면별 임의값으로 많이 흩어져 있어 제품 신뢰감과 학습성이 낮아지는 상태다.

요청과 진행 방식

요청은 각 화면의 정돈되지 않은 UI/UX, 다이얼로그/폼/CTA의 일관성, 재사용 컴포넌트와 토큰 사용 여부, 사용자 안내/주의/경고/미리 알림 affordance 부족 지점을 찾고 개선 방법까지 제안하는 것이었다.

  • 브라우저 조작: 로그인, 접수/예약, 진료/차트, 검사, 영상, 조제, 병원관리, 수납, 입원, 고객관리 화면을 열고 CTA와 메뉴를 클릭했다.
  • 코드 확인: 토큰, 공통 컴포넌트, arbitrary Tailwind utility, 다이얼로그/드롭다운/토스트 사용 지점을 스캔했다.
  • 리서치 기준: NN/g 휴리스틱의 상태 가시성, 일관성, 오류 예방/복구와 Material Design의 오류/스낵바 기준, W3C Design Tokens 형식 개념을 적용했다.

제한: 요청된 in-app Browser 플러그인으로 로컬 URL을 열 때 ERR_BLOCKED_BY_CLIENT가 발생했다. 실제 화면 조작은 같은 로컬 앱을 Playwright로 실행해 진행했다.

대표 증거 화면

핵심 발견

High 1. 간격/폭/폰트 임의값이 과다하다

text-[13px], w-[116px], max-w-[460px] 같은 arbitrary utility가 UI 소스에 1,978회 발견됐다. 색상 토큰은 많이 쓰지만 실제 밀도와 구조는 화면별 하드코딩에 가깝다.

제안: --emr-density-*, --emr-table-col-*, --emr-dialog-*, --emr-font-* semantic token과 컴포넌트 variant로 이동한다.

High 2. 다이얼로그 규격이 통일되지 않았다

공통 Dialog, 확인 Dialog, 신규 등록 Dialog가 각각 다른 폭/헤더/푸터 규격을 직접 지정한다. 예: sm:max-w-sm, 420px, 460px, 680px.

제안: EmrDialogShell을 만들고 confirm, form, wide-form, destructive variant로 통제한다.

High 3. 오류 안내에 복구 행동이 없다

접수 화면의 서버 대기열/캘린더 실패, 수납의 청구 확정 실패가 표시되지만 원인, 재시도, fallback 상태, 담당자에게 전달할 정보가 부족하다.

제안: 패널 단위 EmrInlineAlert를 도입하고 다시 시도, 로컬 데모 데이터 사용 중, 권한 확인 필요를 함께 제공한다.

High 4. 재무/상태 변경 CTA의 확인 기준이 다르다

차트 작성완료는 확인 다이얼로그가 있지만, 청구 확정/수납 완료는 동일하게 중요한 상태 변경임에도 다른 흐름이다.

제안: CTA를 safe, state-changing, financial, destructive, unavailable로 분류하고, financial 이상은 preflight summary를 통일한다.

Medium 5. 메뉴/오버레이 닫힘 규칙이 약하다

모달이 열린 상태에서 상단 프로필 메뉴를 누르려 하면 overlay가 포인터를 막았다. 접수 카드 더보기는 클릭 가능하지만 메뉴가 눈에 띄게 열리지 않았다.

제안: RowActionMenu와 overlay manager를 공통화하고 route change, Escape, 외부 클릭 시 닫힘 규칙을 통합한다.

Medium 6. 상태 색상 의미가 모듈별로 흔들린다

고객관리의 purple tone이 warning 색으로 매핑되고, 접수 캘린더는 수의사 lane 색과 상태 색이 함께 강하게 쓰인다.

제안: EmrStatusBadge와 status-labels에 상태별 semantic tone을 중앙화하고 사람/부서 색은 severity 색과 분리한다.

Medium 7. 빈 슬롯 CTA가 너무 많이 반복된다

접수 캘린더에 “진료 접수 생성”이 빈 시간마다 반복되어 실제 예약 카드와 오류 배너보다 시각적 소음이 커진다.

제안: 기본 상태는 낮은 대비의 plus affordance만 두고 hover/focus 때 + 접수 텍스트를 보여준다.

Medium 8. mock/live 경계 안내가 화면마다 다르다

어떤 화면은 “연동 없이 저장”을 직접 보여주고, 어떤 화면은 toast로만 후속 연결을 말한다. 실제 사용자에게는 기능 신뢰 경계가 불명확하다.

제안: 헤더 또는 패널에 Demo, Local-first, Live read 실패, 외부 연동 미지원 상태 칩과 설명 popover를 둔다.

Polish 9. 테이블/패널 밀도 규칙이 제각각이다

고객관리, 병원관리, 수납, 조제의 테이블 폭과 row height가 각 모듈 내부 상수로 흩어져 있다.

제안: EmrDataTable에 density와 column preset을 추가해 compact, standard, financial로 재사용한다.

Polish 10. 도움말 affordance가 전역 아이콘에만 머문다

상단 도움말 아이콘은 있으나, 실수 비용이 큰 화면 안에서는 맥락형 도움/주의 문구가 부족하다.

제안: 수납, 권한, 환자 등록, 차트 완료 같은 흐름에 EmrHelpHint와 EmrPreflightNotice를 추가한다.

컴포넌트/토큰 감사 메모

영역 현재 상태 권장 방향
색상 raw hex/rgb는 토큰 파일 밖에서 거의 없음. --emr-*, --clair-* 사용률은 높다. 상태/위험/사람 식별 색을 semantic layer로 더 분리한다.
간격/크기 arbitrary utility가 많아 화면별 밀도가 흔들린다. spacing, control height, table width, dialog width token을 만든다.
다이얼로그 기본 Dialog와 EMR Confirm Dialog, 등록 Dialog가 따로 커스터마이징된다. dialog shell과 footer action pattern을 표준화한다.
메뉴 DropdownMenu 기반은 있으나 row action, profile menu, card menu의 affordance와 결과 안내가 다르다. RowActionMenu, MoreButton, disabled/unavailable item 패턴을 만든다.
오류/안내 toast, 작은 inline text, panel error가 혼재한다. persistent error는 inline alert/banner, 낮은 우선순위는 toast로 기준을 분리한다.

추천 실행 순서

  1. 1차: EmrInlineAlert, EmrDialogShell, CTA risk taxonomy를 먼저 만든다.
  2. 2차: 접수/수납/차트의 오류, 재무 CTA, 완료 CTA에 표준 컴포넌트를 적용한다.
  3. 3차: 테이블/패널 density token과 column preset을 도입해 고객관리, 병원관리, 수납부터 정리한다.
  4. 4차: mock/live 상태 칩과 맥락형 도움말을 주요 워크플로우 헤더에 추가한다.
  5. 5차: 시각 회귀 기준 스크린샷을 저장하고 Playwright로 주요 다이얼로그/CTA 흐름을 고정한다.
