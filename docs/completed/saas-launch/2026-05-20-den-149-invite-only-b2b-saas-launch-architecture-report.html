DEN-149 / SaaS Launch Foundation / 2026-05-20

초대 기반 B2B SaaS 런치 아키텍처 보고

CLAiR EMR의 런치 가입 흐름을 공개 회원가입이 아니라 승인된 병원만 들어오는 B2B 초대 모델로 고정했다. 핵심은 CLAiR 내부 승인, 최초 병원 관리자 초대, 병원 관리자 주도의 직원 초대, 그리고 서버 기준 membership/permission enforcement다.

Status: Architecture Decision Complete

핵심 결정

  • 공개 회원가입은 workspace, tenant, membership, EMR 사용 계정을 만들 수 없다.
  • CLAiR 운영자가 승인된 병원 tenant/workspace를 만들고 첫 hospital_admin 초대를 생성한다.
  • 이후 병원 관리자가 기존 invitation lifecycle을 재사용해 staff를 초대한다.
  • Supabase Auth는 identity/session을 맡고, 앱 DB는 workspace membership과 permission source를 맡는다.

행위자 구분

행위자역할권한 경계
CLAiR operator내부 운영자병원 tenant 승인과 최초 관리자 초대. 병원 관리자보다 강한 권한이므로 별도 guard와 audit이 필요하다.
Hospital admin병원 관리자자기 병원 workspace 안에서 staff 초대, 역할, 상태를 관리한다.
Staff member초대받은 실무자초대 수락 후 active membership과 역할에 따라 workspace를 사용한다.
Supabase Auth user로그인 identitysession과 password/OAuth/MFA/reset 기능을 담당하지만 권한 source는 아니다.

런치 플로우

  1. CLAiR가 병원 신청 또는 영업 검토를 통해 병원을 승인한다.
  2. CLAiR 운영자가 승인된 병원의 workspace를 생성하거나 승인한다.
  3. CLAiR 운영자가 첫 병원 관리자 초대를 만든다.
  4. 병원 관리자는 Supabase Auth로 로그인 또는 계정 생성을 완료하고 초대를 수락한다.
  5. 병원 관리자가 직원에게 역할이 포함된 초대를 보낸다.
  6. 직원은 초대 링크로 계정을 만들거나 기존 계정에 연결하고 active membership을 얻는다.
  7. workspace selector와 서버 route는 active membership과 permission resolver를 기준으로 접근을 허용한다.

첫 Vertical Slice 기준

  • CLAiR operator-only path로 한 병원 workspace를 승인/생성할 수 있다.
  • 첫 병원 관리자 초대가 공개 signup 없이 만들어진다.
  • 초대받은 관리자는 로그인 후 해당 workspace에만 진입한다.
  • 관리자는 staff를 역할과 함께 초대할 수 있고, staff는 valid invite를 수락해 active membership을 얻는다.
  • 만료, 취소, 중복, 이미 수락됨, 다른 workspace invite는 안전한 오류로 거절된다.
  • 마지막 active hospital_admin 보호가 유지된다.
  • remote Supabase, real email, production deploy, payment, role policy 변경은 별도 승인 전까지 막혀 있다.

공개 회원가입 제외 이유

EMR은 tenant와 임상 데이터 경계가 중요한 제품이다. 공개 signup이 workspace나 membership을 만들면 가짜 병원, 중복 tenant, 권한 혼선, support/billing 책임 불명확성, cross-tenant 데이터 사고 가능성이 커진다. 나중에 public form을 열더라도 request-access record만 만들고 active workspace는 만들지 않는 방향이 맞다.

검증

  • DEN-148 scope audit과 auth/workspace 기준 문서를 재확인했다.
  • 기존 Supabase Auth, workspace creation, invitation lifecycle, RLS, permission foundation을 재사용하는 구조로 정리했다.
  • 코드 구현, DB migration, remote Supabase, real email delivery, production deploy, real data access는 수행하지 않았다.
  • npm run docs:check로 문서 링크 무결성을 확인했다.
