DEN-187 Real Email Invite Dry-Run Blocked Report

Linear: DEN-187 03-01 Run real email invite dry-run with test recipients only

작성일: 2026-05-22

비개발자 요약

DEN-187의 목표는 실제 이메일 provider를 통해 test recipient에게만 초대 메일을 보내보는 것이다. 하지만 현재 앱 코드는 의도적으로 실제 이메일 발송과 공개 초대 링크 생성을 막아두고 있다. 그래서 지금 단계에서 발송을 진행하면 "검증"이 아니라 미확정 provider/secret/token 흐름을 즉석에서 만드는 작업이 된다.

결론은 Blocked다. 실제 발송 전에 provider, sender domain, test recipient, secret 저장 경로, 초대 링크/token 처리 방식을 먼저 승인해야 한다.

확인한 현재 상태

영역상태
Staff invitation route src/features/auth/server-workspace-invitation.ts가 성공 응답에서 emailDelivery: not_sent_approval_gated와 inviteLink: not_generated_approval_gated를 반환한다.
First admin invite route src/features/ops/server-tenant-workspace-action-core.ts도 emailDelivery: not_sent_approval_gated만 반환한다.
Email provider implementation Repo에서 SMTP/Resend 등 실제 provider 발송 구현을 확인하지 못했다.
Secret handling tracked source를 기준으로 secret 값을 읽거나 기록하지 않았다. .vercel/.env.production.local 파일 내용도 열지 않았다.
Approval gate docs/engineering/auth-security/auth-login/saas-launch-approval-gates.md의 G4 Email delivery가 별도 명시 승인을 요구한다.

발송 전 필요한 승인 항목

  • Provider name: 예를 들어 Supabase Auth email, Resend, SMTP 등.
  • Target environment: staging project와 Vercel Preview/Production 중 어디인지.
  • Allowed email types: first admin invite, staff invite, password reset/account verification 중 무엇인지.
  • Sender domain/from address와 DNS/authentication 상태.
  • Template copy 또는 template id.
  • Secret storage path: Vercel env, Supabase dashboard, provider dashboard 중 어디인지.
  • Approved test recipient list: 실제 받을 이메일 주소 목록.
  • Rate limit/abuse prevention과 bounce/failure handling 기준.
  • Invite link/token handling: raw token을 로그, Linear, docs, screenshot에 남기지 않는 방식.

Stop Conditions

  • 승인되지 않은 recipient로 발송될 가능성이 있으면 중단.
  • raw invite token, OTP, magic link, provider secret이 로그/문서/채팅에 노출되면 중단.
  • sender domain authentication이 실패하면 중단.
  • 잘못된 workspace/tenant로 연결되는 링크가 만들어지면 중단.
  • bounce/abuse anomaly가 있으면 추가 발송 중단.

추천 다음 결정

DEN-187을 계속하려면 승욱이 위 항목을 명시해서 승인해야 한다. provider가 아직 정해지지 않았다면 먼저 "real email provider setup and invite-link implementation"을 별도 이슈로 분리하는 것이 안전하다.
