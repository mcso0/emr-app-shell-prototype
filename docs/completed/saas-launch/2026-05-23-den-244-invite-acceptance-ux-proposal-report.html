초대 수락 계정 선택 UX 리서치 및 제안

현재 초대 이메일에서 링크를 열면 신규 계정을 만들어야 하는지, 기존 계정으로 로그인해야 하는지, 그리고 어떤 이메일로 인증해야 하는지 판단하기 어렵다. 이 보고서는 B2B SaaS 초대 UX 사례를 비교하고 CLAiR EMR에 맞는 초대 수락 플로우와 화면 시안을 제안한다.

Recommendation: Invite-first guided flow Signup: Email OTP first Output: Research + UX proposal Implementation not included

결론

CLAiR EMR에는 초대 정보를 먼저 확인시키고, 그 다음 “초대받은 이메일로 계속하기” 하나의 주 CTA로 가입/로그인을 자동 분기하는 흐름이 가장 적합하다. 사용자는 “신규 계정”과 “기존 계정”을 먼저 판단하지 않아도 되고, 시스템이 초대 이메일 기준으로 계정 존재 여부와 인증 상태를 판정한다.

화면에는 신규/기존 카드 두 개를 동등하게 보여주기보다, “초대받은 이메일로 계속”을 기본 행동으로 두고 보조 링크로 “이미 다른 계정으로 로그인 중인가요?”와 “초대 이메일을 바꾸고 싶어요” 같은 예외 처리를 제공하는 구조가 덜 헷갈린다.

가입 방식은 이메일 OTP 기반 passwordless 방식을 1순위로 추천한다. 초대받은 이메일로 6자리 인증 코드를 보내고, 코드 확인 후 계정이 없으면 생성하고 기존 계정이면 로그인한다. 매직링크는 보조 옵션으로 둘 수 있지만, 첫 MVP에서는 브라우저/메일앱 이동이 적은 OTP가 더 예측 가능하다.

현재 문제

사용자가 직접 판단해야 하는 선택지가 많다

“신규 계정으로 시작”과 “기존 계정에 연결”이 동등한 카드로 보이면 사용자는 자기 상태를 먼저 알아야 한다. 병원 직원 입장에서는 이미 계정이 있는지, 같은 이메일인지, 현재 로그인 세션이 맞는지 알기 어렵다.

표기 정보가 서로 다른 수준으로 섞인다

이메일에는 clair-demo, 수락 화면에는 병원 표시명, 역할은 vet 또는 수의사로 보일 수 있다. 초대 대상, 병원, 역할이 한 기준으로 정리되어야 한다.

로그인 후 복귀가 화면 구조 안에서 보장되어 보이지 않는다

초대 화면에서 로그인 화면으로 이동했다가 다시 초대 수락으로 돌아오는 이유와 다음 상태가 사용자의 머릿속에 남아야 한다. 단순 “로그인 필요”는 초대 맥락을 잃게 만든다.

예외 상태가 가입/로그인보다 먼저 안전하게 설명되어야 한다

만료, 취소, 이미 수락됨, 다른 이메일로 로그인 중 같은 상태는 계정 생성 전에 차단해야 한다. 그래야 잘못된 계정을 만들거나 다른 이메일의 초대를 claim하려는 혼란을 줄일 수 있다.

외부 사례 리서치 요약

서비스 관찰한 패턴 CLAiR에 가져올 점 주의할 점
Slack 이메일 기반 sign-in과 workspace 선택을 분리한다. 같은 이메일로 여러 workspace에 접근할 수 있다는 모델을 설명한다. 초대 이메일을 계정 식별의 첫 기준으로 두고, workspace entry는 별도 단계로 보여준다. workspace 개념이 강한 서비스라 잘못 설계하면 사용자가 새 workspace를 만드는 길로 빠질 수 있다.
Notion 초대받은 사람은 이메일 링크로 sign in 후 workspace에 join한다. 도메인 기반 자동 join도 제공한다. 초대 이메일, workspace, role을 먼저 확인시키고 sign in/join을 연결한다. CLAiR는 invite-only라 도메인 자동 가입은 현재 범위 밖이다.
Linear 초대 이메일에는 join steps가 포함되고, SAML/JIT/allowed domain 같은 계정 생성 방식을 workspace 정책에 맞춘다. 초대 수락 화면은 account method보다 workspace access policy를 먼저 설명해야 한다. CLAiR에는 아직 SSO/SCIM이 없으므로 복잡한 enterprise option은 숨긴다.
Figma 계정이 있어야 초대를 수락할 수 있고, 이메일 초대와 in-app notification을 함께 쓴다. 특히 올바른 계정으로 로그인해야 함을 경고한다. “현재 로그인 계정이 초대 이메일과 맞는지”를 수락 전 화면에서 명확히 검증한다. Figma식 account 선택은 다계정 사용자가 많을 때 유용하지만 EMR 초기 MVP에는 너무 복잡할 수 있다.
GitHub 이메일로 조직 초대를 보낼 경우, 초대 이메일이 개인 계정의 verified email과 일치해야 수락할 수 있다. CLAiR도 초대 이메일과 인증 이메일이 일치해야 멤버십을 활성화한다는 규칙을 전면에 둔다. 개발자 도구식 설명은 병원 직원에게 어렵다. UX 문구는 더 직접적이어야 한다.
Google Workspace 초대 수락 시 해당 이메일의 Google Account가 없으면 생성하도록 안내한다. 기존 계정 충돌도 별도 문제로 관리한다. 신규/기존 계정 선택을 사용자가 판단하게 하지 말고, 이메일 기준으로 시스템이 다음 행동을 안내한다. Google처럼 계정 체계가 큰 서비스가 아니므로 충돌 관리는 단순한 safe denial로 시작한다.

CLAiR EMR UX 원칙

1. 초대 이메일이 identity 기준이다

사용자는 초대받은 이메일로만 멤버십을 활성화할 수 있다. 다른 이메일 세션으로는 수락 버튼을 보여주지 말고 계정 전환 안내를 제공한다.

2. 병원 표시명과 역할명은 human label로 통일한다

사용자가 보는 화면에서는 CLAiR Medium Animal Hospital, 수의사처럼 사람이 이해하는 이름을 사용한다. 내부 id는 보조 정보로만 둔다.

3. 가입과 로그인은 수단이고, 목적은 워크스페이스 입장이다

CTA는 “계정 만들기”보다 “초대받은 이메일로 계속”이 우선이다. 계정 존재 여부는 다음 단계에서 자동 분기한다.

4. 로그인 후 돌아올 위치를 계속 보여준다

로그인/가입 화면 상단에는 “로그인 후 이 초대로 돌아와 병원 워크스페이스에 입장합니다”라는 context strip을 유지한다.

5. 예외 상태는 계정 행동 전에 차단한다

만료/취소/이미 수락된 초대는 로그인이나 계정 생성으로 보내기 전에 알려준다. 관리자가 재초대해야 하는 경우도 명시한다.

6. staging과 production 문구를 분리한다

이메일 본문과 모든 시안은 production tone을 기준으로 작성한다. staging 표기는 footer나 내부 QA evidence에만 제한하고, 사용자가 보는 핵심 문구에는 테스트 냄새를 남기지 않는다.

가입 방식 결정

추천: 이메일 OTP passwordless

초대받은 이메일로 6자리 인증 코드를 보내고, 사용자가 코드를 입력하면 같은 화면 맥락에서 가입 또는 로그인을 완료한다. 신규/기존 계정 판단은 시스템이 처리하고, 사용자는 “초대받은 이메일을 확인한다”는 한 가지 행동만 한다.

  • 신규 사용자와 기존 사용자를 같은 CTA로 처리한다.
  • 비밀번호 생성/재설정 부담을 MVP에서 줄인다.
  • 초대 이메일 소유 증명과 멤버십 활성화가 자연스럽게 연결된다.

보조: 매직링크

매직링크도 passwordless라 방향은 맞지만, 사용자가 초대 이메일 링크를 누른 뒤 다시 인증 이메일 링크를 눌러야 해서 브라우저 탭과 이메일 앱 전환이 늘어난다. 모바일이나 사내 SSO가 붙는 단계에서 보조 옵션으로 검토한다.

비추천: 첫 가입부터 비밀번호 생성

초대 수락 목적보다 “회원가입 폼 작성”이 앞서 보이고, 비밀번호 정책/재설정/실패 상태를 먼저 해결해야 한다. 병원 직원 초대 MVP에서는 passwordless 이후 선택적 비밀번호 설정으로 미루는 편이 낫다.

Supabase Auth의 이메일 OTP는 없는 사용자를 생성할 수 있으므로, CLAiR 구현에서는 반드시 유효한 pending invitation을 먼저 확인한 뒤 인증 코드를 보내야 한다. 또한 invite/auth route rate limit, generic response, safe redirect allow-list를 같이 적용해야 한다.

제안 플로우 3안

안 A. Account-first 선택형

현재 구조를 다듬어 신규 계정/기존 계정 카드를 명확히 나누는 방식이다. 빠르게 구현할 수 있지만 사용자가 자기 계정 상태를 판단해야 한다.

  • 장점: 기존 화면과 가장 유사, 구현 리스크 낮음
  • 단점: 핵심 혼란을 완전히 해결하지 못함
  • 추천도: 낮음

안 B. Invite-first guided flow

초대 정보를 먼저 확인하고 “초대받은 이메일로 계속” CTA 하나로 시작한다. 시스템이 가입/로그인 여부를 판정하고, 사용자는 병원 초대를 수락한다는 목적만 이해하면 된다.

  • 장점: 신규/기존 사용자 모두 덜 헷갈림
  • 단점: 계정 존재 조회/분기 copy 설계가 필요
  • 추천도: 높음

안 C. Email-verification-first

이메일 OTP 또는 magic link로 먼저 소유 확인을 하고, 확인 후 계정 생성/로그인을 이어가는 방식이다. 보안감은 좋지만 현재 MVP에는 auth 구현 범위가 커진다.

  • 장점: 초대 이메일 소유 증명이 가장 명확함
  • 단점: Supabase email/redirect gate와 실제 발송 의존
  • 추천도: 중기 후보

추천 플로우

추천안은 안 B. Invite-first guided flow다. 가입과 로그인을 첫 화면에서 나누지 않고, 초대받은 이메일을 중심으로 같은 CTA를 제공한다.
1. 이메일 병원명, 역할, 만료일, “초대 확인하기” CTA
2. 초대 확인 초대 유효성, 이메일, 병원, 역할을 human label로 표시
3. 인증 코드 입력 초대받은 이메일로 OTP 발송, 코드 확인
4. 인증 후 복귀 계정 생성 또는 기존 계정 로그인 후 초대 수락
5. 워크스페이스 입장 초대 수락 완료, 병원 workspace로 이동

CSO 관점 보안/남용 방지 기준

위험 사용자에게 보여줄 UX 구현 시 지켜야 할 경계
초대 토큰 노출 초대 상태와 병원명만 보여주고 token 값은 표시하지 않는다. token, OTP, magic link, provider error는 화면/로그/보고서에 남기지 않는다.
계정 존재 여부 유추 “이 이메일로 계속” 이후 가입/로그인을 안내하되, 외부인에게 계정 존재 여부를 직접 말하지 않는다. public route 응답은 generic category를 쓰고, Supabase Auth user existence를 노출하지 않는다.
다른 이메일로 초대 claim 현재 로그인 계정과 초대 이메일이 다르면 수락 버튼 대신 계정 전환 안내를 보여준다. server accept route에서 verified session email과 invitation email을 다시 비교한다.
open redirect 로그인 후 돌아갈 위치를 “이 초대 화면” 또는 “병원 워크스페이스”로만 설명한다. next는 내부 invite/workspace 경로 allow-list만 허용하고 외부 URL은 무시한다.
만료/취소 초대 재사용 계정 생성으로 보내기 전에 “새 초대가 필요함”을 먼저 알려준다. expired/canceled/accepted 상태는 membership mutation 전에 차단한다.
staging/production 혼동 핵심 본문은 production tone으로 유지하고, staging 표식은 QA 전용 footer/evidence에만 둔다. staging domain, test recipient, real send approval gate를 production claim과 분리한다.

결정 반영

가입 방식

MVP 추천안은 이메일 OTP 기반 passwordless다. 신규/기존 계정을 별도로 고르게 하지 않고, 초대받은 이메일로 인증 코드를 확인한 뒤 시스템이 계정 생성 또는 로그인을 처리한다.

문구 톤

이메일 본문과 모든 화면 시안은 production tone으로 정리한다. staging 표식은 실제 발송 gate와 QA evidence에서만 다루고, 사용자가 보는 핵심 플로우에는 노출하지 않는다.

검증 및 범위

  • 이번 작업은 리서치와 제안서 작성이며, 제품 UI 구현은 하지 않았다.
  • 실제 이메일 발송, Supabase Auth 정책, RLS/server permission policy, production/staging deploy는 범위 밖이다.
  • 로컬 source-of-truth로 기존 invite/account policy와 invite onboarding flow를 확인했다.
  • 외부 사례는 공식 문서 위주로 확인하고, CLAiR에 필요한 원칙으로 재해석했다.
