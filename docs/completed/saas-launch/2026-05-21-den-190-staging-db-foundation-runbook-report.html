비개발자 요약

staging Supabase 프로젝트는 정상 작동 중이지만 아직 CLAiR EMR 앱의 DB 기초 공사, RLS 정책, synthetic seed가 적용되지 않은 빈 프로젝트 상태다. 그래서 DEN-190은 실제 DB 변경을 실행하지 않고, 승욱이 승인하면 바로 실행자가 따라갈 수 있는 안전한 순서와 멈춤 조건을 정리했다.

DEN-186으로 넘어갈 수 있는가? env inventory와 secret handling checklist 범위는 가능하다. 다만 staging app smoke, demo bypass proof, route-backed auth smoke는 DB foundation과 RLS replay가 통과된 뒤가 안전하다.

실행 가능한 순서

  1. 승욱이 아래 migration/RLS/schema approval 문구를 승인한다.
  2. 실행자가 target이 qmerxgzrwaaahpkhjqlc인지 확인하고 production ref가 아니면 계속한다.
  3. 실행 전 npm run security:secrets, npm run docs:check, relevant SQL/RLS/static tests를 통과시킨다.
  4. CLI를 순차 실행한다. 전역 CLI가 없으면 npx supabase를 사용한다.
  5. supabase link --project-ref qmerxgzrwaaahpkhjqlc를 실행한다. 이 단계도 승인 범위에 포함되어야 한다.
  6. supabase db push --dry-run으로 적용 예정 migration 목록을 캡처하고 DEN-190 또는 follow-up에 남긴다.
  7. dry-run 결과가 repo migration 33개와 일치하고 unexpected remote drift가 없으면 실제 supabase db push를 별도 최종 확인 후 실행한다.
  8. 적용 후 MCP/read-only로 migration count, table count, function count, RLS enabled count, policy count, advisor 결과를 확인한다.
  9. public.rls_auto_enable() WARN이 남으면 revoke/repair 승인 전 seed/replay로 넘어가지 않는다.
  10. 승욱이 별도 seed approval을 승인한 뒤 synthetic seed 실행을 진행한다.
  11. seed 후 synthetic-only admin/member/non-member/foreign workspace denial replay를 수행한다.
  12. 결과를 Linear comment/document와 repo report로 남기고 blocker를 launch blocker/non-blocker로 분류한다.

Synthetic seed approval 조건

  • Seed는 supabase/seed.sql 기준으로 실행 범위를 고정한다.
  • 현재 seed는 workspace auth, reception, clinical/order/billing, customer profile fixture를 포함한다.
  • 실제 병원명, 보호자, 환자, 직원, 결제, 신원 데이터는 금지한다.
  • 승욱이 seed dataset이 중형 병원 staging rehearsal 목적에 충분한지 승인해야 한다.
  • DEN-191 synthetic medium hospital dataset contract가 확정되기 전에는 seed를 "기존 local fixture replay"로만 취급한다.
  • Seed 실행은 migration/RLS/advisor 검증 통과 후 별도 승인으로만 한다.

Stop condition

  • Target ref가 qmerxgzrwaaahpkhjqlc가 아니거나 production으로 보이면 즉시 중단한다.
  • dry-run 결과가 repo migration 33개와 다르거나 remote drift가 있으면 중단한다.
  • real clinic/customer/guardian/patient/staff/billing/identity data가 발견되면 중단한다.
  • secret/service role key/DB password가 chat, Linear, docs, git diff, logs에 노출될 위험이 있으면 중단한다.
  • RLS disabled table, missing policy, helper grant mismatch, cross-workspace leak, last-admin guard failure가 있으면 seed/replay를 중단한다.
  • public.rls_auto_enable() advisor WARN을 해소 또는 명시 수용하기 전에는 seed/replay로 넘어가지 않는다.
  • Email/deploy/payment/provider action이 필요해지는 순간 DEN-190 범위를 벗어나 중단한다.

Rollback/repair report 기준

  • Staging rollback은 기본적으로 forward-fix migration을 우선한다.
  • Backup/restore가 필요하면 실행 전에 승욱이 backup/restore owner와 허용 방식을 별도 승인해야 한다.
  • 부분 적용, failed migration, migration history mismatch가 있으면 supabase migration list와 remote read-only inventory를 캡처한다.
  • Repair가 필요한 경우 supabase migration repair 또는 direct SQL mutation은 별도 승인 전 실행하지 않는다.
  • Repair report에는 target ref, 적용된 migration, 실패 지점, 데이터 영향, RLS/advisor 상태, 다음 조치가 포함되어야 한다.

승욱 승인 문구

Migration/RLS/schema 적용 승인

DEN-190에서 Supabase staging project clair-emr-staging / qmerxgzrwaaahpkhjqlc에 repo supabase/migrations의 앱 DB foundation migration 33개를 Supabase CLI 방식으로 적용해도 된다. 허용 작업은 target 확인, CLI link, db push --dry-run, dry-run 결과 보고, 별도 최종 확인 후 db push, 그리고 MCP/read-only post-change verification까지다. production project 접근, real data 사용, secret/service role key 노출, email 발송, deploy 실행은 금지한다. seed 실행은 이 승인에 포함하지 않는다.

Synthetic seed 실행 승인

DEN-190에서 migration/RLS/schema 적용과 read-only verification이 통과된 뒤, supabase/seed.sql의 synthetic-only dataset을 staging에 적용해도 된다. 실제 clinic/customer/guardian/patient/staff/billing/identity data 사용은 금지하고, @clair.local, example.test, deterministic demo UUID 등 synthetic fixture만 허용한다. seed 후 admin/member/non-member/foreign workspace denial replay와 read-only 검증 결과를 Linear와 repo report에 남긴다.
