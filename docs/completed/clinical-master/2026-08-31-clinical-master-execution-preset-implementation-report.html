1. 최종 판단

요청한 구현과 대상 워크스페이스의 원격 데이터 반영은 완료됐다. 애플리케이션 코드 배포와 인증 UI smoke가 남아 있다.

  • 기존 510개 마스터 오더와 새로 정의한 12개 계통별 신체검사 오더를 합쳐 522개 오더 모두에 정확히 하나의 현재 실행 프리셋이 존재한다.
  • 최종 게시 입력은 689개 레코드 / 522개 오더이며, 고정 산출물 SHA-256은 1eeb5035d70d5f28035df49d1d32c3689ffe79a4bb28062e5606256802572e0c이다.
  • 마스터 프리셋은 워크스페이스 카탈로그로 복사되고, 병원은 복사본을 수정하거나 사용 중지할 수 있다.
  • 수정하지 않은 복사본은 새 마스터 개정에 자동 동기화되고, 수정한 복사본은 덮어쓰지 않고 검토 대상으로 남는다.
  • 차트에 오더를 추가하면 프리셋 세부값이 초안에 자동 입력된다. 안전하게 추론할 수 없는 필드는 수동 입력 또는 런타임 해석 대상으로 남는다.
  • 확정 시점의 유효 세부값은 오더 snapshot으로 고정되며, 이후 마스터·워크스페이스 변경이 과거 확정 기록을 바꾸지 않는다.
  • 전용 system_exam 타입은 차트에서 완료되며 처치·검사·조제 fulfillment queue로 전달되지 않는다.

publisher의 set-based 2단계 성능 보완과 current-main 상담/billing/Realtime 호환을 격리 DB에서 검증하고 독립 재심사한 뒤, 정확한 원격 후보를 적용했다. release no. 50의 689개 레코드·522개 오더 게시가 25.2초에 완료됐고 같은 입력 재호출은 10.85초에 idempotent하게 끝났다. 세 대상 워크스페이스는 모두 522개 프리셋 연결과 빈 기본값 0개를 만족한다. 조제 108개는 기존 병원 프로필이 master revision 1에 묶여 있어 새 revision 2로 강제 변경하지 않고 기존 프로필과 일치하는 프리셋을 보존한 채 검토 유예했으며, 나머지 414개는 현재 release를 채택했다. 외부 통제 워크스페이스의 catalog·update·lab·notification·audit 변화는 모두 0이다. 모든 프리셋은 synthetic_unreviewed, clinicalUseAllowed=false 계약을 유지하므로 이번 완료는 임상 승인이나 실제 진료 활성화를 의미하지 않는다.

2. 요청을 구현 계약으로 정리한 내용

요청의 핵심은 “마스터에 오더 이름만 두지 말고 세부 기본값까지 보유하고, 워크스페이스로 오더를 가져올 때 그 값도 함께 복사해 바로 사용할 수 있게 하라”였다. 이를 다음 계약으로 구현했다.

  1. 마스터는 모든 적용 대상 오더에 버전이 있는 실행 프리셋을 보유한다.
  2. 워크스페이스 채택 시 오더와 프리셋 세부값을 함께 복사한다.
  3. 워크스페이스 관리자는 복사본을 수정하거나 사용 중지할 수 있다.
  4. 사용자가 수정한 값은 다음 마스터 채택에서 자동으로 덮어쓰지 않는다.
  5. 차트 초안은 유효 프리셋 값을 자동 입력한다.
  6. 환자·담당자·장소처럼 마스터가 알 수 없는 값은 런타임 또는 워크스페이스에서 해석한다.
  7. 필수값이 비어 있으면 확정을 막고, 확정된 snapshot은 불변으로 보존한다.

5. 구현 내용

5.1 공통 마스터 프리셋

master.order_execution_presets와 current pointer를 추가했다. 각 버전은 다음을 보유한다.

  • preset identity와 revision
  • 대상 master order revision
  • clinical order type과 detail schema version
  • defaultDetailInputs
  • 필드별 정책
  • 출처·근거·생성 정보
  • 현재 publisher가 허용하는 synthetic_unreviewed 상태
  • clinicalUseAllowed
  • canonical content hash, source artifact hash, source release lineage

버전 행은 update/delete를 거부하고, unknown field·잘못된 enum·schema 불일치·hash 불일치·동일하거나 낮은 revision을 fail closed 처리한다. 임상 검토 ledger가 별도로 구현되기 전에는 payload가 스스로 clinically_reviewed로 승격할 수 없고 clinicalUseAllowed도 true가 될 수 없다.

5.2 필드 소유권과 값 해석 순서

유효값은 다음 순서로 결정한다.

  1. encounter/runtime context
  2. workspace override 또는 병원 운영 기본값
  3. CLAiR master execution preset
  4. chart schema default
  5. 안전하게 유도할 수 없는 값의 사용자 직접 입력

필드 정책은 preset_fixed, derived_from_profile, schema_default, workspace_resolved, runtime_resolved, required_manual, not_applicable로 고정했다. 예를 들어 영상 부위·자세는 마스터 기본값이 될 수 있지만 실제 장비, 외부기관, 병동·케이지, 가격은 워크스페이스 소유다. 담당 수의사는 actor가 아니라 해당 encounter의 주치의에서 해석한다.

5.3 게시·채택 transport

  • 기존 publisher payload의 executionPreset envelope를 검증하고 immutable master version으로 투영한다.
  • 689개 레코드를 payload 범위로 게시한다.
  • 정확히 허용된 워크스페이스에만 522개 카탈로그 행과 기본 세부값을 복사한다.
  • 같은 입력 재게시·재채택은 idempotent하다.
  • 기존 lab dependency가 이번 payload에서 생략되어도 최신 immutable revision pin을 잃지 않는다.
  • 임상병리검사 projection의 conflict counter는 실제 insert가 발생했을 때만 증가한다.
  • 기존 조제의 nested default와 새 generic default를 양방향 호환한다.

5.4 워크스페이스 수정·사용 중지·검토

  • 병원관리 오더 drawer에서 타입 스키마에 맞는 일반 세부 기본값을 확인·수정할 수 있다.
  • partial edit는 가격·조제·백신 metadata를 SQL null로 지우지 않는다.
  • 수정은 CAS revision을 요구하고 stale revision을 SQLSTATE 40001로 거부한다.
  • 사용 중지는 신규 차트 검색에서 제외하며 과거 snapshot은 유지한다.
  • 일반 오더의 pause 감사 이벤트는 order_catalog.paused / pause로 남는다.
  • 사용자가 수정한 행은 customized와 변경 필드를 기록한다. 이후 채택은 해당 값을 보존하고 workspace_master_updates 검토 행을 만든다.

5.5 차트 자동입력과 확정 snapshot

  • 개별 오더와 Order Set child 모두 workspace catalog의 유효 기본값을 초안에 복사한다.
  • 상담의 responsibleClinicianId는 현재 encounter 주치의로 서버와 UI 양쪽에서 해석한다. 주치의가 없으면 임의 actor를 넣지 않고 미완료 상태로 남긴다.
  • required field가 빠지거나 unknown field가 포함되면 확정을 막는다.
  • 확정 오더, fulfillment source snapshot, billing candidate는 당시 값을 보존한다.
  • system_exam은 destinationless chart-only 타입이며 fulfillment projection이 들어와도 서버가 버린다.

5.6 보안 경계

  • master preset 테이블은 RLS enabled이며 client role에 직접 공개하지 않는다.
  • private publisher/adopter/project/sync 함수의 anon, authenticated, service_role execute를 명시적으로 회수했다.
  • 차트 저장의 내부 base RPC도 직접 실행 권한을 회수하고 공개 wrapper만 authenticated가 호출한다.
  • catalog writer와 master-update resolver는 TypeScript 선검사나 역할 label에 의존하지 않고 DB에서 canonical service_catalog:manage 권한을 다시 확인한다.
  • 차트 runtime resolver 조회는 chart:update permission preflight가 통과한 뒤에만 실행한다.
  • security-definer 함수는 빈 search_path, workspace/actor permission, CAS, audit 경계를 유지한다. 324개 compatibility backfill도 정확한 candidate 집합만 변경·감사하고 재실행 시 감사 행을 늘리지 않는다.
  • current pointer는 동일 order의 preset identity를 임의로 새 ID/revision 1로 교체하지 못하며, source release와 activated release가 일치해야 한다.
  • 임의 임상 타입 mismatch는 거부하고, 확인된 legacy identity 두 종류만 좁게 호환했다.

원격 DB에는 publisher, adopter, ANALYZE, VACUUM, index 또는 설정 변경을 실행하지 않았다. 함수 source/catalog, relation/index 통계, 현재 lock과 EXPLAIN 예상 plan만 읽었다. 이 방법은 Supabase의 query optimization, database inspection, pg_stat_statements 지침을 기준으로 삼았다. writer를 실제 실행하는 EXPLAIN ANALYZE는 사용하지 않았다.

확인된 사실

  • 설치된 cumulative publisher의 line 605는 689개 owner loop 시작, line 606은 v_master_key := btrim(v_record->>'masterKey'), line 608은 master.master_records의 FOR UPDATE point lookup이다. line 606은 느린 btrim의 증거가 아니라 60초 제한이 반복문의 interrupt 지점에서 전달됐다는 뜻이며, 몇 번째 owner였는지는 오류 context만으로 알 수 없다.
  • 이 loop 전에 combined stage 689행 insert와 2,455행 update가 발생했고, order stage 522행, test stage 72행, panel stage 18행도 생성 시도가 기록됐다. 따라서 payload 전송·첫 validation만 하다가 멈춘 것이 아니라 lab dependency와 durable stage materialization을 지나 owner revision loop에 진입했다.
  • 현재 lock은 0, deadlock 누계는 0이었다. 실행 당시 lock_timeout=5s보다 statement_timeout=60s의 57014가 발생했으므로 장시간 blocking lock이 주원인일 가능성은 낮다.
  • combined stage는 총 3.9MB, order stage 1.4MB, master version table 1.2MB로 작았고 combined stage의 heap block은 read 70 대 hit 74,252였다. combined stage는 seq_scan=0, idx_scan=7,521이었다. 큰 table scan이나 disk I/O, 일반적인 bloat만으로 60초를 설명할 증거는 없다.
  • clinical_master_lab_relation_content의 예상 plan은 4개 release를 순회하면서 기존 (release_id, master_key) index를 사용했고 stage sequential scan을 하지 않았다. 따라서 master_key 단독 index를 추가하자는 가설은 현재 증거로 반증됐으며 새 migration에 넣지 않는다.
  • advisor의 current-preset composite FK, activated_in_release_id, published_by_user_id child-side index 경고는 이번 timeout 이후 단계이거나 parent update/delete 검사에 주로 영향을 준다. 이번 60초 원인으로 취급하지 않는다.
  • 원격은 track_functions=none, pg_stat_statements.track=top이라 실패한 함수의 nested statement별 시간을 사후 복원할 수 없다. 이 설정을 변경하거나 통계를 reset하지 않았으므로 정확히 어느 owner iteration이 가장 비쌌다는 주장도 하지 않는다.

로컬 3초 결과의 한계

기존 격리 rehearsal은 exact 689/522 payload의 기능, 원자성, 결과 count와 rollback을 강하게 증명하지만 원격 성능을 재현하는 benchmark는 아니다. 시작 stage/history/TOAST footprint, relation 통계, phase timer, raw run output와 환경 snapshot이 version control에 없고, retry도 첫 publish와 같은 transaction에서 실행됐다. 따라서 3초대 수치는 깨끗한 로컬 DB에서 candidate가 동작한다는 증거로만 유효하며 원격 60초 해결 증거로 다시 사용하지 않는다.

현재 원인 판단

가장 강한 설명은 작은 원격 relation에 대한 index/lock 문제가 아니라, 약 2MB JSON과 689개 owner를 PL/pgSQL에서 여러 차례 행 단위로 순회하면서 stage relation, latest version, snapshot 비교와 update를 반복하는 CPU·SPI 비용이다. 특히 line 606 loop는 이미 계산된 stage의 master_record_id, base_content, relation_content, effective_revision을 다시 payload와 helper에서 재구성한다. 이것은 현재 증거에 가장 잘 맞는 우선 구현 가설이지만, nested timing 부재 때문에 단일 원인으로 확정하지는 않는다.

새 performance candidate 구현 계획

  1. 재현 가능한 benchmark부터 보강한다. exact payload/file SHA, function definition SHA, PostgreSQL 설정, relation/TOAST 크기와 table stats를 각 run의 JSON/TSV 증거로 남긴다. 기능 rehearsal과 성능 run을 분리하고, baseline과 candidate를 동일 fresh snapshot에서 ABBA 순서로 최소 3회 비교한다. retry는 commit 뒤 새 transaction/connection에서 검증한다.

7.1 독립 보안 재심사

독립 hard-gate 리뷰는 최초 MUST-FIX로 live lineage, required-field completeness, preset identity, DB writer permission·backfill audit, synthetic self-promotion 문제를 지적했다. 이를 수정한 뒤 마지막으로 master-update resolver의 canonical permission 우회 가능성까지 추가 발견해 보완했다.

기존 기능 후보의 최종 재심사 결론은 APPROVE이며 P0/P1은 0건이다. 첫 524 뒤 승인된 minified 동일 payload 재시도도 완전 rollback됐다. 재배치 전 성능 candidate의 별도 재심사는 exact file SHA 범위에서 High 0 / Medium 0 / Low 0, LOCAL APPROVE였고 관련 publisher spec도 독립 재실행에서 24/24 통과했다.

current-main 재배치 뒤 독립 hard gate는 처음에 High 0 / Medium 2 / Low 1, LOCAL BLOCK을 냈다. Medium 두 건은 후속 billing/Realtime wrapper가 상담 담당자 서버 정규화를 덮은 문제와 chart:view 검사 전에 encounter 존재를 구분할 수 있던 문제였다. Low 한 건은 문서의 이전 후보 상태였다. 최종 호환 migration, rollback-only rehearsal, 7/7 spec과 두 격리 적용 순서 검증으로 보완한 뒤 exact-file 재심사는 High 0 / Medium 0 / Low 0, LOCAL APPROVE로 닫혔다. 독립 정적 resolver·route 재실행도 27/27, git diff --check도 통과했다. 이후 C1/C2 원격 후보와 rollout packet도 각각 exact-SHA 독립 검토를 통과했고, 특히 최종 rollout packet은 High/Medium/Low 0/0/0 판정 뒤에만 영속 실행했다.

8. 구현 중 발견해 수정한 결함

  1. 임상병리 검체 enum에 조직(tissue)이 없어 세포검사 프로필이 거부되던 문제

  3. 누적 publisher가 payload에서 생략된 기존 lab dependency revision을 null로 덮던 문제
  4. lab adopter가 ON CONFLICT DO NOTHING 이후에도 생성 counter를 증가시키던 문제
  5. 일반 catalog partial edit에서 nullable price를 jsonb_set하면 pricing rule 전체가 SQL null이 되던 문제
  6. 비조제 오더 사용 중지 감사 이벤트가 update로만 기록되던 문제
  7. private publisher/adopter와 내부 chart draft base RPC에 불필요한 execute 권한이 남을 수 있던 문제
  8. live lineage SHA가 잘린 값이었고 실제 510개 집합을 재계산하지 않던 문제
  9. DB required-field 검증이 default 또는 허용 resolver의 완전성을 강제하지 않던 문제
  10. current preset identity를 새 ID/revision 1로 초기화할 수 있던 문제
  11. catalog writer와 master-update resolver가 canonical service_catalog:manage 대신 일부 역할 label 경로에 의존하던 문제
  12. compatibility backfill의 durable audit ledger와 candidate-only idempotency가 부족하던 문제
  13. payload가 임상 검토 증거 없이 clinically_reviewed로 자기 승격할 수 있던 문제
  14. required preset_fixed 필드에 정상 default가 있어도 DB가 거부하던 문제
  15. PR-019 current가 rev2로 전진한 뒤 foundation 재적용 projection 검사가 rev1만 기대하던 문제
  16. publish/adopt 재적용이 이미 보존된 legacy 함수를 다시 rename하던 문제
  17. canonical payload를 wrapper와 cumulative core가 두 번 정규화하던 문제
  18. execution-preset 계약 검증 한 번 안에서 같은 detail schema를 두 번 생성하던 문제
  19. current-main의 후속 billing/Realtime migration이 상담 담당자 서버 정규화 wrapper를 덮던 문제
  20. DB writer가 chart:view를 확인하기 전에 encounter/catalog를 읽어 존재 여부를 구분할 수 있던 문제

각 수정에는 fail-closed 또는 회귀 테스트를 추가했다.

9. 변경 범위

  • 결정론적 프리셋·계통검사·최종 release compiler 3개
  • 동결 fixture와 최종 게시 입력
  • generic execution preset foundation, runtime transport, publish/adopt, system exam, publisher, consultation resolver migration 6개
  • publisher performance migration과 current-main 상담/billing/Realtime 최종 호환 migration, 두 rollback-only rehearsal과 집중 회귀 spec
  • stage-backed set-based publisher migration, local-only ABBA/committed-retry benchmark runner·SQL probe와 강화 rehearsal/spec
  • 병원관리 catalog read/write/UI
  • 차트 초안 prefill·runtime resolver·확정 snapshot transport
  • fulfillment의 system_exam queue 차단
  • 타입·도메인 계약과 집중 테스트
  • 작업 항목, 구현 보고서, 문서 내비게이션

기존 확정 기록과 fulfillment를 바꾸는 DML, Airtable, dependency version은 변경하지 않았다. 승인된 원격 Supabase에는 PR-022 foundation·performance·compatibility와 최종 set-based migration이 적용됐고, release no. 50 게시와 세 대상 workspace adoption·review resolution까지 완료됐다. 과거 timeout 세 건은 모두 완전 rollback 상태로 남고, 이번 성공 release와 workspace 결과만 영속화됐다. npm ci --ignore-scripts는 검증용 로컬 node_modules만 준비했으며 package manifest/lockfile은 수정하지 않았다.

10. 남은 전달 단계와 임상 경계

  1. 최신 origin/main에 후보를 재배치하고 전체 집중 검증을 다시 통과시킨다.
  2. GitHub PR, 고정 staging, production 순서로 애플리케이션 코드를 전달한다.
  3. 배포된 인증 화면에서 병원관리 프리셋 확인·수정·사용 중지와 차트 추가 시 자동입력을 smoke한다.
  4. 조제 108개의 master revision 2 채택은 임상/profile 재검증 뒤 별도 작업으로 진행한다. 현재 정상 rev1 profile-matched 값을 강제로 덮지 않는다.
  5. 모든 합성 프리셋은 계속 synthetic_unreviewed, clinicalUseAllowed=false로 유지한다. 임상 검증과 true 전환은 이번 범위 밖이다.

11. 현재 결론

“마스터에 프리셋 세부값이 있고, 워크스페이스로 함께 복사되며, 병원이 수정·사용 중지하고, 차트 추가 시 자동 입력되고, 확정 후에는 불변으로 남는가?”에 대한 구현과 원격 데이터 답은 예다.

대상 synthetic/demo 워크스페이스 세 곳은 522개 catalog 모두에 비어 있지 않은 프리셋을 보유하고, 사용 중지 설정을 보존하며, 차트 검색에서 활성 행 전부가 prefilled detail을 반환한다. 외부 통제 워크스페이스는 변하지 않았다. 다만 “실제 병원에서 임상 승인된 값으로 바로 사용 가능한가?”에 대한 답은 아니오다. 이번 목표는 기능과 합성 데이터 transport 구현까지이며, 임상 검토·조제 revision 2 재승인·clinicalUseAllowed=true 전환은 별도 단계다.
