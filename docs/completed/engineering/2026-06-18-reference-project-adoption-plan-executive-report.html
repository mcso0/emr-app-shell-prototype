외부 도구 활용 계획 요약 보고서

기준 문서: docs/engineering/architecture/reference-project-adoption-plan.md
작성일: 2026-06-18

결론

CLAiR EMR은 새 SaaS 보일러플레이트로 다시 만들면 안 된다. 이미 Next.js, Supabase, API 경계, seed 데이터, 주요 EMR 화면이 있다.

가장 빠른 길은 기존 구조를 유지하면서 외부 도구를 “참고하거나 일부만 연결”하는 것이다. 목표는 실제 병원 운영이 아니라, DB seed 기반 데모를 안정적으로 보여주는 것이다.

우선순위

  1. Supabase 로그인, 워크스페이스, 권한 경계를 먼저 안정화한다.
  2. seed 데이터를 API로 읽는 화면을 늘린다.
  3. 스케줄, 태스크, 결제는 기존 EMR 흐름을 기준으로 정리한다.
  4. 외부 결제, 이메일, 채팅, 분석은 데모가 안정된 뒤 연결한다.

기능별 활용안

기능 활용할 외부 도구 권장 방향
로그인 / 세션 Supabase, NextBase 참고 Supabase를 유지한다. Clerk/Auth.js로 교체하지 않는다.
멀티테넌시 / 워크스페이스 Supabase RLS, SaaS starter 구조 참고 워크스페이스, 멤버십, 권한은 CLAiR 내부 데이터로 관리한다.
스케줄 Cal.com / Cal.diy 참고 통째 도입하지 않는다. 기준은 “진료 접수-대기-차트-결제” 흐름과 직접 연결되는지다. Cal.com은 외부 예약/가용시간에는 좋지만, CLAiR 내부 진료 상태의 기준 시스템은 아니다.
태스크 관리 Trigger.dev 후보 지금 데모에는 필수 아님. 나중에 예약 알림, 실패 재시도, 정기 작업이 반복되면 검토한다. 진료 태스크 기준은 기존 order_fulfillment_work_items다.
결제 Toss Payments, PortOne, Stripe 참고 구현 계획만 잡는다. DB seed demo에는 실제 결제를 달지 않는다. 한국 결제 후보는 Toss 또는 PortOne이고, Stripe는 흐름 참고용이다.
고객 CRM HubSpot / Attio 후보 현재 단계는 HubSpot 우선. 이유는 무료 시작, 비개발자 사용성, 영업 파이프라인 관리가 쉽기 때문이다. Attio는 나중에 API/맞춤 데이터 모델이 중요해질 때 재검토한다.
유저 소통 / 메신저 Stream Chat, Novu, Resend 후보 데모에는 실제 채팅을 달지 않는다. Slack처럼 빠른 채팅이 필요해지면 Stream Chat을 1순위로 검토한다. Novu는 알림, Resend는 이메일용이다.
분석 / 온보딩 Driver.js 우선 Driver.js로 간다. 무료 오픈소스라 비용 부담이 낮다. 제품 분석이 필요해질 때만 PostHog/Mixpanel을 별도로 검토한다.

주석 반영 결정 기준

항목 결정 근거
스케줄 Cal.com은 참고만 한다. CLAiR 예약은 진료 접수, 대기열, 차트, 결제와 연결된다. Cal.com은 외부 예약, 가용시간, 시간대 처리에 강하다. 그래서 예약 충돌, 시간대, booking 상태만 참고한다.
Trigger.dev 지금은 도입하지 않는다. 현재 DB seed demo에는 백그라운드 작업 플랫폼이 필수는 아니다. 단, “예약 알림”, “실패한 provider 재시도”, “정기 seed reset”, “webhook 후처리”가 생기면 도입 기준을 충족한다.
결제 계획만 만든다. 데모에는 실제 Toss/PortOne 기능을 붙이지 않는다. 지금 필요한 것은 provider-neutral 결제 설계다. 실제 결제는 승인된 별도 작업으로 분리한다.
CRM HubSpot 우선. 지금 필요한 외부 CRM은 환자 관리가 아니라 병원 영업 관리다. 비개발자 사용성, 무료 시작, 학습 자료 기준으로 HubSpot이 더 적합하다. Attio는 커스텀 API 연동이 중요해질 때 후보가 된다.
메신저 나중에 Stream Chat 우선 검토. “코멘트”는 환자/진료/태스크에 붙는 내부 메모를 뜻한다. Slack형 실시간 채팅이 필요하면 React UI가 준비된 Stream Chat이 빠르다. 단, 의료/결제 정보가 오갈 수 있어 데모에는 아직 붙이지 않는다.
온보딩 Driver.js로 결정. 무료 MIT 오픈소스이고, 화면 안내 tour를 빠르게 만들 수 있다. 비용이 거의 없어서 현재 단계에 맞다. 고급 분석/사용자 세그먼트가 필요해질 때만 유료 분석 도구를 검토한다.

지금 바로 하지 말 것

  • SaaS 보일러플레이트로 프로젝트를 갈아엎지 않는다.
  • OpenVPM처럼 라이선스 위험이 있는 프로젝트 코드를 복사하지 않는다.
  • Cal.com을 내부 진료 스케줄 엔진으로 통째 도입하지 않는다.
  • Stripe를 한국 결제 기본안으로 잡지 않는다.
  • 실제 결제, 이메일, 카카오, SMS, 채팅, 분석 연동은 승인 전까지 하지 않는다.

추천 실행 순서

순서 목표 이유
1 Supabase seed 로그인 재현 데모의 출발점이 흔들리면 이후 기능도 불안정하다.
2 API read-state 정리 화면마다 로딩, 실패, 재시도 처리가 달라지는 문제를 줄인다.
3 스케줄 / 접수 안정화 외래 데모의 첫 흐름이다.
4 태스크 / 처치 / 검사 queue 안정화 진료 후속 업무가 seed 데이터와 맞아야 한다.
5 결제 adapter 설계 실제 결제 연결은 하지 않는다. Toss/PortOne을 붙일 수 있는 내부 설계만 준비한다.
6 Driver.js 온보딩 tour 비용 부담이 낮고, 데모 설명 효과가 크다. 실제 환자/결제 데이터와 무관하다.

한 줄 판단

외부 도구는 “대체재”가 아니라 “속도를 내는 부품”으로 써야 한다. 지금은 Supabase 기반 seed 데모를 먼저 안정화하고, 실제 외부 서비스 연결은 그다음 단계로 미루는 것이 안전하다.

참고한 기준

  • Cal.com Embed: 외부 예약 화면을 앱 안에 넣는 용도.
  • Cal.com Schedule API: 가용시간과 시간대 모델 참고.
  • Trigger.dev: 백그라운드 작업, 재시도, 모니터링이 필요할 때 후보.
  • HubSpot Free CRM: 무료 CRM 시작 가능.
  • Attio Pricing: 무료 3 seat 시작, API 중심 CRM 후보.
  • Stream Chat React SDK: Slack형 채팅 UI를 빠르게 만들 때 후보.
  • Driver.js: 무료 MIT 오픈소스 온보딩 tour 후보.

검증

이 보고서는 원본 계획 문서를 비개발자용으로 요약한 것이다. 새 코드, DB, 결제, 이메일, 외부 provider 설정은 추가하지 않았다.
