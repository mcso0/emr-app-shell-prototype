Plan/Order 금융 요약과 오더 청구

2026-08-30 · GitHub PR #673 · 차트가 끝나기 전에도 안전한 중간 정산을 시작할 수 있도록 한 개선

대표 관점 요약

테이블 높이를 거의 늘리지 않으면서 왼쪽에는 오더 상태, 오른쪽에는 금액과 핵심 행동을 한 줄로 배치했다. Order 청구는 차트 완료와 분리했고, 확정된 청구 가능 오더만 서버에서 다시 계산해 수납 화면으로 넘긴다.

화면과 업무 흐름

  • 선택된 행의 Order 확정은 기존 플로팅 액션 바에 유지했다.
  • 하단 요약은 오더 건수·확정 전·확정 후와 발생액·할인·청구 예상 총액을 좌우로 그룹화했다.
  • 금액 상세은 보조 고스트 버튼, Order 청구는 가장 오른쪽의 주 행동으로 구성했다.
  • 금액 상세 패널은 딤·블러·백드롭·포커스 트랩 없이 열려 테이블을 계속 확인하고 조작할 수 있다.
  • 청구 후 encounterId와 invoiceId를 포함해 수납으로 이동하므로 새로고침과 직접 진입에도 같은 청구를 읽는다.

금액·권한 안전장치

경계적용 내용
금액 권위브라우저 합계를 신뢰하지 않고, 확정·미취소·미청구 오더의 frozen candidate를 서버에서 invoice line으로 변환한다.
동시성encounter → orders → candidates 순으로 잠근 뒤 revision을 검증해 동시 금액 정정과 오래된 청구 요청의 충돌을 차단한다.
멱등성같은 사용자·workspace·encounter·command 재요청은 최초 invoice를 반환하며 중복 line과 audit event를 만들지 않는다.
정보 격리차트와 수납의 보호 snapshot을 사용자 session 및 workspace에 묶고, 권한 또는 사용자 변경 시 이전 상태를 다시 표시하지 않는다.
진료 상태청구·수납이 encounter 완료나 fulfillment work status를 변경하지 않는다.

범위와 남은 확인

  • 범위 밖: 임의 금액 부분결제, PG 승인·환불·회계·세금·영수증 외부 연동.
  • 원격 적용은 synthetic/demo production-bound Supabase의 schema와 함수 catalog만 검증하며 실제 환자·보호자·결제 행은 조회하지 않는다.
  • 롤백은 앱 revert와 additive DB rollback SQL을 후보로 보존한다. 이미 생성된 업무 데이터를 파괴하는 자동 rollback은 실행하지 않는다.
