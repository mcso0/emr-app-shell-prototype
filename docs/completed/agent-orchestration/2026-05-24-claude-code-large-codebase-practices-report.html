우리 프로젝트 적용 판단 권장 운영 모델 실행 로드맵 체크리스트 주의점 출처

대형 코드베이스에서 AI 코딩 에이전트를 잘 쓰려면 “모델”보다 “운영 환경”을 먼저 설계해야 한다.

Anthropic 글의 핵심은 Claude Code가 거대한 저장소를 별도 중앙 인덱스에 의존하지 않고 개발자처럼 파일 시스템, 검색, 참조 추적, 로컬 도구를 이용해 탐색한다는 점이다. 그래서 성공 여부는 모델 성능만이 아니라, 시작 컨텍스트, 계층형 지침, 자동화 hooks, task-specific skills, MCP, LSP, subagents, 그리고 이를 관리하는 책임자 체계에 크게 좌우된다.

이 보고서의 결론

원문 요약은 Claude Code 사례를 그대로 다루되, 적용안은 Codex 기준으로 해석한다. 우리 프로젝트는 이미 AGENTS.md, docs/agent-start-here.md, docs/engineering/current-status.md, docs/_meta, docs/work, repo-local skills를 갖고 있다. 다음 개선은 이 구조를 Codex가 더 적은 문맥으로 정확히 쓰게 만들고, 필요한 tool/plugin만 불러오며, 검증과 승인 경계를 놓치지 않게 만드는 것이다.

한국어 번역형 요약

원문 전체를 그대로 옮기지 않고, 핵심 주장과 구조를 한국어로 의역해 정리했다.

1. Claude Code는 큰 코드베이스를 개발자처럼 탐색한다

Claude Code는 전체 저장소를 미리 임베딩해서 서버 인덱스로 올리는 방식에 기대지 않는다. 로컬 개발 환경에서 파일을 읽고, 검색하고, 참조를 따라가며 필요한 문맥을 찾아간다.

이 접근은 최신 워크트리를 직접 본다는 장점이 있다. 반면 시작점이 흐리거나, 저장소 구조가 불분명하거나, 모든 정보를 한 번에 읽게 만들면 컨텍스트 한계에 빠진다. 따라서 큰 저장소일수록 “어디서 시작해야 하는지”를 명확히 알려주는 계층형 안내가 중요하다.

2. 성능은 모델만이 아니라 harness가 결정한다

원문은 Claude Code의 실제 성과가 모델 자체보다 모델을 둘러싼 실행 환경, 즉 harness에 크게 좌우된다고 설명한다. harness는 CLAUDE.md, hooks, skills, plugins, MCP servers 같은 확장 지점으로 구성된다.

핵심은 모든 지식을 한 파일에 넣지 않는 것이다. 매 세션 필요한 공통 규칙은 가볍게 유지하고, 특정 업무에만 필요한 전문 지식은 skill처럼 필요할 때만 불러오게 해야 한다.

3. LSP와 subagents는 큰 저장소에서 특히 유용하다

LSP는 문자열 검색이 아니라 심볼 기준으로 정의와 참조를 찾게 해준다. 이름이 같은 함수나 비슷한 파일이 많은 저장소에서는 잘못된 위치를 여는 비용을 줄인다.

Subagent는 탐색과 편집을 분리하는 데 유용하다. 읽기 전용으로 하위 시스템을 조사한 뒤 핵심 결과만 부모 세션에 넘기면, 메인 세션의 컨텍스트를 실제 수정 작업에 더 많이 쓸 수 있다.

4. 성공한 조직은 설정을 계속 관리한다

성공 사례들은 공통적으로 코드베이스를 탐색 가능하게 만들고, 지침 파일을 주기적으로 정비하며, Claude Code 운영 책임자를 둔다. 모델이 발전하면 예전 지침이 오히려 방해가 될 수 있으므로 3-6개월 단위로 설정을 재검토하는 흐름이 필요하다.

특히 규제 산업이나 민감한 제품에서는 승인된 skills, 리뷰 절차, 제한된 초기 접근, 보안/거버넌스 협업 체계를 먼저 정하는 것이 중요하다.

우리 프로젝트 적용 판단

원문 개념 Codex 기준 대응 판단 우리 프로젝트 적용
CLAUDE.md / root context AGENTS.md, system/developer instructions, docs/agent-start-here.md, docs/engineering/current-status.md 강함 Codex가 매 세션 반드시 읽을 내용은 compact하게 유지하고, 세부 지식은 source docs와 work item으로 내려보낸다.
Layered context docs/_meta/agent-rag-map.md, 영역별 README, work item source docs 진행 중 Codex가 root에서 방황하지 않도록 작업 유형별 “최소 읽기 경로”와 “다음 검증 명령”을 명확히 둔다.
Skills Codex skills, repo-local .agents/skills, emr-docs-sync, manual-linear-ops 기반 있음 반복되는 docs sync, Linear handoff, HTML report, QA 절차는 장문 지시가 아니라 skill로 승격한다.
Hooks Codex에서는 shell 검증, result-review 규칙, CI/check scripts, automation 후보로 해석 후보 docs:check, lint, typecheck, secret scan, result-review 누락 감지는 deterministic gate로 관리한다.
MCP / external tools Codex plugins/connectors, tool_search, GitHub, Linear, Supabase, Vercel, Browser, automation tools 선별 필요 읽기 전용 조사와 실제 변경 도구를 분리하고, Supabase/RLS/deploy/email/payment는 explicit approval gate를 유지한다.
LSP / symbol navigation rg, TypeScript 타입 검사, Next.js 문서 확인, 필요 시 IDE/LSP 기반 심볼 탐색 우선 검토 대규모 리팩터나 cross-feature 변경 전에는 문자열 검색만 믿지 않고 타입/심볼/테스트 근거를 같이 확인한다.
Subagents Codex multi-agent tools, read-only 조사 세션, 병렬 파일 읽기, 독립 QA/review 세션 조건부 편집 권한이 필요한 본작업과 분리해 조사, QA, 보안 리뷰, 디자인 리뷰처럼 독립 가능한 작업에만 우선 적용한다.

권장 운영 모델

1. Codex 시작 컨텍스트는 얇고 강하게 유지

  • AGENTS.md는 절대 규칙과 언어/안전 계약 중심으로 유지한다.
  • docs/agent-start-here.md는 새 세션의 최소 라우팅 문서로 유지한다.
  • 상세 구현 지식은 영역별 README, source docs, work item으로 내려보낸다.

2. Codex는 관련 문서와 도구만 불러오게 한다

  • 문서 작업은 docs/_meta, docs/work, 관련 source doc부터 본다.
  • Next.js 코드는 관련 node_modules/next/dist/docs/ 문서를 먼저 확인한다.
  • 브라우저, GitHub, Linear, Supabase, Vercel 등은 작업 목적이 맞을 때만 tool_search로 불러온다.

3. 반복 업무는 Codex skill 후보로 승격

  • GitBook 문서 동기화 점검
  • Linear Human Review handoff
  • HTML closeout/report 생성
  • Sales Demo 회귀 확인

4. 승인 gate와 운영 책임자를 명확히 둔다

  • 에이전트 운영 DRI는 지침 중복과 오래된 규칙을 정리한다.
  • auth, DB, Supabase, RLS, deploy, real email, payment는 Codex가 임의로 진행하지 않게 승인 조건을 유지한다.
  • 3-6개월 단위로 agent contract, skills, plugins, connector 사용 규칙을 리뷰한다.

실행 로드맵

단계 목표 구체 작업 검증
1주차 Codex 시작 경로 정리 agent-rag-map과 영역별 README에서 Codex task별 최소 읽기 경로를 재점검한다. npm run docs:check
2주차 반복 보고서 Codex skill화 HTML closeout/report 구조를 repo-local skill workflow로 정리한다. 샘플 보고서 1개 생성 후 링크/렌더링 확인
3주차 Codex 검증 gate 정리 docs check, lint, typecheck, secret scan, approval-gated command 감지 항목을 검증 gate 후보로 분류한다. 실행 시간과 false positive 점검
4주차 대형 변경 작업 분리 Codex multi-agent 또는 별도 조사 세션을 읽기 전용 조사와 QA에만 시범 적용하고, 편집 세션과 분리한다. 조사 파일과 최종 diff 비교 리뷰

에이전트 작업 체크리스트

작업 시작 전

  • docs/agent-start-here.md와 docs/engineering/current-status.md를 먼저 읽는다.
  • PR-sized 작업이면 docs/work/index.md에서 기존 item을 찾는다.
  • 작업 유형에 맞는 source doc만 추가로 읽는다.
  • 필요한 plugin/connector는 목적이 명확할 때만 tool_search로 불러온다.
  • Next.js 앱 코드는 관련 Next.js 문서를 먼저 확인한다.

작업 중

  • 기존 dirty worktree 변경을 되돌리지 않는다.
  • mock/live, Supabase, RLS, production deploy 경계는 현재 상태 문서를 따른다.
  • 파일 수정은 수동 편집이면 apply_patch를 우선 사용하고, 기존 패턴을 먼저 읽는다.
  • 반복되는 지식은 긴 root instruction이 아니라 source doc 또는 Codex skill 후보로 기록한다.
  • 검증 명령은 작업 범위에 맞게 좁히되, 보안/권한 경계는 넓게 본다.

작업 종료 전

  • 문서 변경은 npm run docs:check를 우선 실행한다.
  • 구현 변경은 lint, typecheck, build, focused Playwright를 범위에 맞게 실행한다.
  • 프론트엔드/HTML 변경은 가능하면 Browser 또는 정적 HTML 검증으로 렌더링을 확인한다.
  • 의미 있는 작업은 한국어 HTML report를 남긴다.
  • 최종 리뷰는 비개발자도 이해할 수 있게 “무엇이 바뀌었고 왜 중요한지”부터 말한다.

주의점

우리 프로젝트에서 피해야 할 적용 방식

  • 모든 운영 지식을 AGENTS.md나 시작 문서에 계속 추가해 Codex 기본 컨텍스트를 비대하게 만드는 방식
  • 승인 없이 live Supabase, migration push, RLS, production deploy, real email, payment 범위를 에이전트 자동화에 연결하는 방식
  • 읽기 전용 조사와 실제 편집을 같은 세션에서 오래 끌어 컨텍스트를 소모하는 방식
  • 한 번 성공한 수동 노하우를 문서화하지 않아 매번 새 에이전트가 다시 추론하게 만드는 방식
