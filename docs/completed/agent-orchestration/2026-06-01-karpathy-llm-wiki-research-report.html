Karpathy LLM Wiki 조사 및 CLAiR EMR 적용 제안

Karpathy의 LLM Wiki는 새 제품이라기보다 원천 자료를 LLM이 지속 관리하는 Markdown 지식층으로 컴파일하는 작업 패턴이다. CLAiR EMR에서는 기존 docs/ 운영 체계를 대체하지 않고, 에이전트가 현재 상태와 결정 맥락을 더 안정적으로 회수하도록 돕는 파생 지식층으로 쓰는 것이 적합하다.

작성일: 2026-06-01 범위: 웹 조사 + 프로젝트 적용안 상태: 실행 제안, 구현 전

비개발자 요약

일반 RAG는 질문할 때마다 문서 조각을 다시 찾아 답을 만든다. LLM Wiki는 반대로 문서를 한 번 읽을 때마다 중요한 내용을 연결된 위키 페이지로 정리하고, 다음 질문은 그 누적된 위키를 기반으로 답하게 한다. 그래서 반복 설명, 오래된 결정 찾기, 문서 간 모순 탐지가 쉬워진다.

다만 의료 EMR 프로젝트에서는 이 위키를 진짜 보안 경계나 최종 제품 요구사항으로 취급하면 안 된다. 원천 문서와 승인된 work item이 기준이고, LLM Wiki는 그 기준을 더 빨리 찾고 비교하기 위한 보조 레이어로 두는 것이 안전하다.

무엇인가

1. Raw sources

사람이 선별한 원천 자료다. 문서, 회의록, 이슈, 코드 리뷰, 외부 글 등이 들어가며 LLM은 읽기만 하고 수정하지 않는다.

2. Wiki

LLM이 쓰고 관리하는 Markdown 페이지다. 요약, 엔티티, 개념, 비교, 모순, 결정 맥락을 서로 링크한다.

3. Schema

AGENTS.md나 CLAUDE.md처럼 에이전트에게 폴더 구조, 작성 규칙, 인용 규칙, lint 절차를 알려주는 운영 계약이다.

Karpathy 원문은 이를 “아이디어 파일”로 설명한다. 즉 특정 SaaS나 라이브러리보다 원천 자료를 읽고, 누적 가능한 위키로 정리하고, 주기적으로 건강검진하는 방식이 핵심이다.

어떻게 활용하나

작업 실제 행동 산출물
Ingest 새 문서나 이슈를 한 번 읽고 기존 wiki 페이지, index, log, 관련 개념 페이지를 갱신한다. 요약 페이지, 관련 개념 업데이트, 원천 링크, 변경 로그
Query 질문이 들어오면 raw 전체를 뒤지기 전에 wiki index와 관련 페이지를 먼저 읽는다. 출처가 붙은 답변, 비교표, 결정 후보, 후속 질문
Lint 정기적으로 모순, stale claim, orphan page, 끊어진 링크, 출처 없는 주장을 검사한다. 문서 건강 리포트, 수정 후보, Human Review 큐

RAG와의 차이

구분 일반 RAG LLM Wiki
지식 처리 시점 질문 시점에 검색하고 합성한다. 문서 ingest 시점에 합성하고 계속 갱신한다.
축적성 좋은 답변이 채팅 기록에 흩어지기 쉽다. 좋은 답변과 분석을 위키 페이지로 다시 남긴다.
검토 가능성 벡터 인덱스는 사람이 직접 읽고 diff하기 어렵다. Markdown과 Git diff로 사람이 확인할 수 있다.
약점 질문마다 재합성 비용과 retrieval noise가 생긴다. 출처 관리가 약하면 환각과 오래된 요약이 축적될 수 있다.

조사에서 확인한 강점

  • 프로젝트 맥락, 결정, 용어, 모순 같은 장기 지식에 강하다.
  • Markdown/Git 기반이면 도구 종속성이 낮고 사람이 검토하기 쉽다.
  • 반복 질의에서 같은 결론을 다시 만들지 않아 비용과 맥락 손실을 줄일 수 있다.
  • 문서 lint를 기능으로 만들 수 있다. 예: 오래된 상태 문서, 서로 충돌하는 요구사항, 출처 없는 claim 찾기.
  • 작은 팀에서는 문서 담당자가 따로 없어도 위키 정리 비용을 낮출 수 있다.

주의할 점

LLM Wiki는 “정답 저장소”가 아니라 “검토 가능한 합성물”이다. 원천 자료 불변성, 출처 링크, 사람 승인, 주기적 lint가 없으면 잘못된 요약이 계속 증폭될 수 있다.

  • 출처 없는 wiki claim은 CLAiR EMR의 제품/보안/DB 기준으로 사용하면 안 된다.
  • 문서가 수백 개 이상으로 커지면 단순 index.md만으로는 부족하고 검색 또는 MCP 도구가 필요할 수 있다.
  • 의료/개인정보 영역에서는 real patient, guardian, hospital, payment, identity data를 ingest 대상에서 제외해야 한다.
  • remote Supabase, RLS, production deploy, real provider integration 관련 지식은 기존 승인 게이트를 그대로 따라야 한다.
  • 연구/구현 생태계는 빠르게 변하고 있어 특정 오픈소스 구현을 바로 표준으로 채택하기보다 패턴을 먼저 시범 적용하는 편이 안전하다.

CLAiR EMR에 맞는 활용 방식

권장 원칙

  • 기존 docs/가 canonical source다. LLM Wiki는 대체물이 아니라 파생/탐색 레이어다.
  • 작게 시작한다. 전 repo를 자동 ingest하지 말고, agent orchestration, current status, work closeout처럼 맥락 손실이 큰 영역부터 시작한다.
  • 출처가 없는 합성은 반려한다. 각 wiki 페이지는 관련 source doc, work item, closeout, 외부 링크를 명시해야 한다.
  • lint를 첫 번째 가치로 둔다. 답변 자동화보다 오래된 current status, 충돌하는 scope, stale Human Review 상태를 찾는 데 먼저 쓴다.
  • 보안/실데이터는 제외한다. synthetic docs와 승인된 repo 문서만 대상으로 한다.

파일 구조 후보

docs/agent-wiki/
  README.md              # non-canonical generated knowledge layer notice
  index.md               # topic/entity/source map
  log.md                 # append-only ingest/query/lint log
  entities/
  concepts/
  decisions/
  lint/
manifests/
  agent_wiki_sources.csv # source path, hash, last_ingested_at, status

이 구조는 아직 구현하지 않았다. 승인 후 시범 적용한다면 docs/agent-wiki/가 GitBook의 공식 sidebar에 바로 들어가지 않도록 “generated, non-canonical” 표시를 먼저 둬야 한다.

우선순위 높은 사용 사례

사용 사례 왜 유용한가 첫 적용 후보
새 Codex 세션 온보딩 매번 current status, work index, 완료 리포트를 다시 설명하는 비용을 줄인다. docs/agent-start-here.md, docs/engineering/current-status.md, 최근 closeout
문서 충돌 탐지 MVP scope, mock/live boundary, approval gate가 서로 어긋나는 지점을 찾는다. docs/_meta/agent-rag-map.md, docs/work/index.md, auth/security docs
대표 리뷰용 요약 긴 work sequence를 비개발자 관점의 현재 상태와 결정 포인트로 압축한다. docs/completed/** 중 active project closeout
반복 질문 저장 “지금 live Supabase가 어디까지 됐지?” 같은 반복 질문의 답을 계속 업데이트한다. auth/workspace, billing, clinical fulfillment 상태 페이지

추천 실행 순서

  1. 승욱 승인 후 docs/agent-wiki/README.md에 non-canonical 원칙과 금지 범위를 먼저 정의한다.
  2. 시범 대상은 agent orchestration/docs 운영 영역 20개 이하 문서로 제한한다.
  3. 각 source의 path, hash, ingest 날짜를 manifest에 기록한다.
  4. index/log/entities/concepts만 생성하고, canonical source docs는 자동 수정하지 않는다.
  5. 첫 lint 리포트는 “오래된 claim, 충돌 claim, 출처 없는 claim”만 보고한다.
  6. 효과가 있으면 work item 흐름과 closeout 생성 흐름에 query/writeback 절차를 붙인다.

결론

CLAiR EMR은 이미 agent-first 문서 운영 체계가 강한 편이라 LLM Wiki 패턴과 궁합이 좋다. 다만 핵심은 “새 툴 설치”가 아니라 “원천 문서 불변, 출처 있는 합성, 주기적 lint, 사람 승인”이다. 지금 바로 전면 도입하기보다는 agent orchestration/docs 운영 영역에서 작은 pilot으로 검증하는 것이 가장 안전하다.
