DEN-512 Reception Walk-in Readback Hydration Fix

DEN-511 staging replay에서 확인된 “접수 직후에는 보이지만 새로고침 후 Reception/Chart readback에서 같은 synthetic encounter가 사라지는” 문제를 좁혀 수정했다. 핵심은 live workspace에서 새로 등록한 환자/보호자가 mock fixture에 없기 때문에, persisted queue/calendar readback 직후 프로필을 다시 hydrate하지 않으면 카드와 대기열 projection이 끊기는 점이었다.

비개발자용 요약

  • 접수 자체는 저장됐지만, 새로고침 후 화면이 새 환자와 보호자 정보를 다시 붙이지 못해 접수 카드와 진료 대기열이 흔들리는 문제가 있었다.
  • 이번 수정은 저장된 접수를 다시 읽을 때 환자, 보호자, 담당 수의사, 방문 목적 정보를 함께 복원하게 만든 것이다.
  • 그래서 같은 synthetic 접수가 Reception 화면과 Chart 대기열에서 계속 같은 정보로 보이는지가 핵심 확인 포인트다.
  • 실제 환자, 보호자, 병원 운영 데이터, 결제, 외부 알림은 사용하지 않고 synthetic QA 범위 안에서만 확인한다.

변경 요약

  • Reception queue/calendar read record에 optional patient, primaryGuardian payload를 받을 수 있도록 타입과 mapper를 확장했다.
  • Supabase RPC 응답이 camelCase 또는 snake_case로 들어와도 encounter, queue entry, patient, guardian을 같은 도메인 타입으로 복원하도록 서버 mapper를 보강했다.
  • Reception refresh read flow에서 persisted readback record를 받은 뒤, embedded profile을 먼저 patient profile store에 반영하고, 부족한 live profile은 lookup reader로 보강하도록 했다.
  • walk-in writer SQL contract에서 consultation queue의 entered_at이 now()가 아니라 접수 planned/checked-in event time을 따르도록 맞췄다.

검증 포인트

  • Cheongdam workspace에서 queue/calendar readback만으로 live 환자/보호자 프로필을 hydrate하고, 새로고침 후에도 Reception side card와 calendar card가 같은 환자, 보호자, 담당 수의사, 방문 목적을 유지하는 회귀 테스트를 추가했다.
  • queue/calendar/lookup/walk-in mapper가 snake_case DB payload를 받아도 기존 camelCase client contract로 복원되는지 서버 테스트로 고정했다.

범위 제외

  • staging DB reset/delete처럼 되돌리기 어려운 데이터 초기화 작업은 수행하지 않는다.
  • 실제 환자/보호자/병원/결제/provider/external notification side effect는 사용하지 않았다.
  • DEN-511 staging replay는 고정 staging 배포와 필요한 Supabase 함수 적용 후 다시 확인한다.
현재 상태: 로컬 구현과 focused verification은 완료됐다. 이번 요청으로 고정 staging 배포와 필요한 Supabase 함수 적용 여부 확인을 진행한다.
