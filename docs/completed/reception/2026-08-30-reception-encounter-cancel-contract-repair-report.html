RECEPTION-LIVE-PR-018 · 2026-08-30

접수 취소 계약 복구 결과

화면은 취소 사유를 포함한 새 DB 함수를 호출하고 있었지만 원격 DB에는 이전 함수만 남아 모든 요청이 500으로 실패했다. 애플리케이션과 DB 계약을 맞추고, 접수와 진료 대기열이 함께 취소되도록 복구했다.

원인

  • 애플리케이션은 취소 사유를 포함한 4개 인자 RPC를 호출했다.
  • 원격 DB에는 3개 인자 RPC만 있고 접수 취소 사유 컬럼도 없었다.
  • PostgREST가 일치하는 함수를 찾지 못해 요청이 HTTP 500으로 종료됐다.
  • 실패한 요청은 접수와 대기열 어느 쪽도 부분 변경하지 않았다.

변경 내용

  • encounters.cancellation_reason을 추가하고 취소 상태에는 빈 사유를 허용하지 않았다.
  • 앱이 사용하는 4개 인자 취소 RPC를 추가했다.
  • 세션 사용자와 요청 actor 일치, 활성 워크스페이스 소속, reception:update 권한을 DB에서 재확인한다.
  • 접수 행과 consultation 대기열 행을 잠근 뒤 한 트랜잭션에서 함께 취소한다.
  • 취소 감사 이벤트도 같은 트랜잭션에 기록해 감사 실패 시 상태 변경까지 롤백한다.
  • 안전한 형식과 길이의 요청 ID만 DB 감사에 전달하고, 감사 이벤트 ID까지 확인된 경우에만 서버 감사 중복 기록을 생략한다.
  • 인증 사용자의 기존 3개 인자 RPC 실행 권한을 제거했다.
  • DB 권한 거부를 일반 500이 아니라 HTTP 403으로 전달하고, 500 로그에는 진료정보나 식별자를 남기지 않는다.

검증

  • 접수 취소 서버 계약 테스트 11개와 TypeScript 검사를 통과했다.
  • 새 마이그레이션을 로컬 DB에 적용했다.
  • 전용 합성 접수건으로 actor·권한·비활성·교차 워크스페이스 거부, 접수·대기열·감사 동시 반영을 확인했다.
  • 감사 저장을 의도적으로 실패시켜 접수와 대기열 변경이 함께 롤백되는 것도 확인했다.
  • DB 감사 완료 표식이 없으면 서버 감사 경로를 사용하는 드리프트 안전망도 확인했다.
  • DB lint에서 새 함수 오류는 없었다. 기존 복구 함수 오류와 기존 경고는 이번 범위 밖으로 남겼다.
  • 대기열 UI 취소 회귀 시나리오는 첫 실행의 탐색 경합 후 재실행에서 통과했으며 후보 검증에서 다시 확인한다.
  • 전체 로컬 DB reset은 기존 임상 마스터 서비스 검토 마이그레이션의 seed 순서 오류로 새 마이그레이션 전에 중단됐다.

범위와 안전성

  • 예약 취소, 대기열 UI, 사용자가 직접 입력하는 취소 사유는 변경하지 않았다.
  • 현재 화면에 보이는 기존 접수건은 테스트 데이터로 사용하지 않는다.
  • 원격 적용은 컬럼·함수·권한 카탈로그 확인과 롤백 전용 합성 재생이 모두 통과할 때만 완료로 본다.
  • 롤백 시 사유 컬럼과 기록 데이터는 보존하며, 사유를 쓰지 못하는 기존 3인자 함수는 다시 켜지 않는다.
  • DB 계약 문제는 취소 요청을 차단한 뒤 전진 수정하고, 앱 문제는 이전 프로덕션 배포로 되돌린다.

다음 게이트

  • 승인 후 합성/demo Supabase에 마이그레이션을 적용하고 롤백 전용 재생을 실행한다.
  • 같은 후보를 production에 반영하고 전용 합성 접수건으로 최종 스모크한다.
