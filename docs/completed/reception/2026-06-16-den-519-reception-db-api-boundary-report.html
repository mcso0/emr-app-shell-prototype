DEN-519 접수/예약 DB/API 경계 검토 보고

접수/예약 QA 구현에 들어가기 전에, 어떤 화면 동작이 실제 API와 synthetic/demo DB를 타야 하는지 검토하고 다음 PR의 수용 기준을 고정했다.

핵심 결론

현재 접수 화면에는 API 기반 read/write 경로가 이미 있지만, 체중, 예약 생성, 접수 상세 수정은 아직 실제 DB 계약이 부족하다. 특히 체중은 UI 입력만 고치면 안 되고, 접수 생성 후 환자 프로필의 weight_kg가 DB에 저장되고 재조회로 확인되어야 한다.

확인한 현재 상태

  • 대기열, 일자 캘린더, 환자/보호자 검색은 API read 경로가 있다.
  • walk-in 접수 생성, 예약 체크인, 접수 취소는 API write 경로가 있다.
  • UI에는 아직 session draft 기반 우회 경로가 남아 있어 QA 통과 기준에서 제외해야 한다.
  • 환자 체중은 접수 화면에서 하드코딩 fallback으로 읽고 있으며, 접수 생성 입력과 RPC에는 체중 저장 계약이 없다.
  • Supabase RPC 직접 호출 경계는 서버 권한 체크보다 약하므로 follow-up DB 작업에서 denial/readback 테스트가 필요하다.

다음 구현 이슈에 적용할 기준

  • 성공 기준은 API write와 API readback이다. UI local overlay만으로는 완료 처리하지 않는다.
  • mock/fallback은 Sales Demo 호환 목적을 제외하고 QA acceptance에 사용하지 않는다.
  • 예약 생성과 접수 상세 수정은 typed server contract, permission check, DB/API persistence, readback test가 필요하다.
  • 체중 저장은 환자 프로필 source of truth를 갱신하고 reload 후에도 유지되어야 한다.
  • 과한 기능 개발을 피하고, DEN-514~DEN-517의 QA 범위에 필요한 최소 계약만 구현한다.
