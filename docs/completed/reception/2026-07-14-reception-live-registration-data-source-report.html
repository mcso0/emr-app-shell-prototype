접수 보호자·환자 등록 원격 데이터 연결 수정

2026-07-14 · RECEPTION-LIVE-PR-005 follow-up · Human Review

결론

신규 보호자·환자 등록과 기존 보호자에 환자 추가가 동일한 등록 API를 사용하도록 유지하면서, 기존 보호자 선택의 데이터 소스를 현재 워크스페이스의 원격 조회 API로 통일했다. 운영 워크스페이스에서 번들 데모 보호자 ID나 데모 중복값이 등록을 방해하거나 Supabase RPC로 전달되지 않는다.

원인

  • 등록 모달이 워크스페이스와 무관하게 번들 데모 데이터로 초기화되는 전역 client store를 조회했다.
  • 기존 보호자 선택 시 guardian-lee-jieun 같은 문자열 demo ID가 UUID 컬럼을 사용하는 RPC로 전달됐다.
  • API와 Supabase writer 연결은 정상이며, 원격 PostgreSQL 로그에서 잘못된 UUID 입력 오류가 확인됐다.
  • 공용 조회의 staging 합성 별칭도 등록용 신원 조회에는 사용하면 안 되는 보조 demo 동작이었다.

주요 변경

  • 기존 보호자 목록·검색·연결 환자·동명이름 안내를 workspace-scoped lookup 응답에서만 계산한다.
  • 등록용 조회는 syntheticAliases=false를 보내 정확한 원격 검색만 수행한다.
  • 신규 등록의 전화번호·마이크로칩 중복 판정은 API/DB 응답을 최종 기준으로 사용한다.
  • 조회 중·빈 결과·조회 실패·재시도 상태를 제공하고, 서버 충돌 시 작성 중인 초안을 유지한다.
  • Supabase gateway가 비 UUID 기존 보호자 ID를 RPC 호출 전에 거부한다.
  • 등록 성공 후에만 응답 레코드를 client store에 반영해 현재 화면을 즉시 갱신한다.

검증

  • Supabase 등록 및 조회 서버 테스트 15건 통과
  • 신규/기존 등록, 원격 UUID payload, demo 데이터 격리, 서버 중복 오류 초안 유지, 조회 오류 재시도 테스트 통과
  • 변경 파일 ESLint, TypeScript typecheck, production build 통과
  • 원격 staging DB aggregate 재확인: QA 패턴 보호자 0건, 환자 0건, 당일 생성 보호자 0건, 환자 0건
  • DB 스키마 변경이나 신규 dependency 없이 기존 lookup API와 registration API를 재사용

알려진 기존 항목

등록 다이얼로그 제목 픽셀 테스트 1건은 정확한 origin/main에서도 동일하게 실패한다. 공유 토큰이 18px을 렌더링하지만 오래된 테스트는 16px을 기대하는 문제이며, 이번 기능 수정에서는 사용자가 확인한 모달 UI와 공유 다이얼로그 타이포그래피를 변경하지 않았다.
