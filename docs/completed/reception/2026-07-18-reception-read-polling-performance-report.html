결론

접수 화면이 9초마다 큐와 캘린더를 따로 요청하던 구조를 줄였다. 실제 Supabase 환경에서는 한 번의 스냅샷 요청으로 두 데이터를 동시에 읽고, 사용자 권한도 한 번만 준비한다. 자동 확인 주기는 60초 fallback으로 낮추고 숨겨진 탭과 중복 요청을 차단했다.

사용자와 운영에 미치는 영향

  • 접수 화면을 오래 열어둬도 아무 변화가 없을 때 발생하는 원격 DB 요청이 크게 줄어든다.
  • 화면 포커스와 가시성 복귀 시에는 최신 데이터를 다시 확인한다.
  • 같은 병원·날짜의 이전 요청이 진행 중이면 새 요청을 추가로 만들지 않는다.
  • 권한, 워크스페이스 범위, 큐·캘린더 응답 형식, 데모 fallback은 유지한다.

배포 후 확인 결과

스냅샷 구현을 포함한 origin/main은 프로덕션에 배포됐다. 원격 10분 관찰과 인증된 청담 접수 화면의 통제 측정을 모두 완료했다. 현재 접수 새로고침 1회는 큐·캘린더·멤버십·권한 관련 조회를 각각 1회만 실행한다. Realtime 변경 알림, 단일 권한 스냅샷 RPC, 검사·조제 상태변경 최적화는 이번 범위에 포함하지 않았다.

최신 프로덕션 배포는 스냅샷 구현을 포함한 origin/main과 일치한다. 인증된 청담 접수 탭을 최신 번들로 다시 불러온 뒤, 같은 길이의 무동작 구간과 수동 새로고침 구간을 세 번 비교했다. 두 번은 관련 조회가 각각 정확히 1회 증가했고, 한 번은 다른 클라이언트의 동시 트래픽이 섞였다. 세 번의 중앙값은 모두 1회였으므로 접수 화면 자체의 중복 권한 조회는 재현되지 않았다. 브라우저 연결이 요청 waterfall을 제공하지 않아, 실시간 증거는 브라우저 동작과 같은 구간의 DB 증가량을 맞춘 결과다. 수동 관찰에서 보인 추가 권한 호출은 staff 경로, 호환 경로, 기존 열린 클라이언트를 구분하는 별도 호출원 추적 대상으로 남긴다.

추가 권한 조회의 출처

호출원언제 실행되는가판단
접수 스냅샷화면 진입, 60초 갱신, 포커스 복귀, 수동 새로고침큐·캘린더를 위한 정상 조회
직원 목록본문에서 60초마다, 사이드패널 진입 시, 상세 패널이 열릴 때장기적으로 권한 조회 비율을 약 2배로 만드는 주된 호출
알림앱 시작 시 활성·보관 목록을 각각 요청시작 시 같은 권한 준비가 2회 발생
워크스페이스 탭앱 시작과 탭 상태 저장 시시작·탐색 과정의 추가 권한 조회

179초 원격 표본에서는 권한 조회 묶음 13회, 접수 큐 4회, 캘린더 5회, 직원 상태·프로필 조회 4회가 확인됐다. 접수 화면은 큐·캘린더와 직원 정보를 각각 60초마다 갱신하므로 권한 조회가 접수 스냅샷의 약 2배가 되는 것이 현재 구조와 일치한다. 여기에 앱 시작 시 알림과 탭 복원, 사이드패널의 별도 직원 조회가 더해진다. 따라서 새로고침 한 번의 N+1 문제가 아니라 여러 화면 영역이 같은 권한 준비를 따로 실행하는 구조다.

다음 수정 우선순위

  1. 접수 본문·사이드패널·상세 패널이 직원 목록 결과 하나를 공유하게 만든다.
  2. 앱 시작 시 활성 알림과 보관 알림을 한 요청으로 받을 수 있는지 검토한다.
  3. 두 개선 후에도 트래픽이 크면 접수 스냅샷과 직원 갱신의 서버 요청 통합을 검토한다.

현재 개별 DB 실행시간은 약 1~3ms라 긴급한 서버 증설이나 대규모 인덱스 추가는 필요하지 않다. Vercel 경로별 런타임 로그 집계는 현재 MCP 권한에서 403 Forbidden으로 확인할 수 없었으며, Supabase 로그와 실제 호출 코드의 빈도·구조를 대조해 출처를 판정했다.

직원 목록 공유 개선 완료

접수 본문이 직원 목록 조회와 60초 갱신을 한 번만 담당하도록 변경했다. 왼쪽 사이드패널과 열린 접수 상세 패널은 같은 병원·같은 날짜의 결과를 공유한다. 서버 권한 확인과 화면 디자인은 그대로 유지된다.

새 성능 회귀 테스트는 접수 본문, 왼쪽 사이드패널, 접수 상세 패널이 함께 있는 상태에서 직원 API 1회와 동일한 직원 표시를 확인했다. 성능 집중 테스트 5개, TypeScript, 변경 파일 ESLint, 프로덕션 빌드, 문서·시크릿 검사가 통과했다. 기존 접수 UI 테스트 5개는 이번 변경과 무관하게 테스트 응답에서 영업시간을 생략해 기존 코드가 중단되는 문제와 기존 hover 색상 기대값 차이로 완료되지 않았다.

알려진 별도 회귀

기존 접수 UI 날짜 테스트 4건은 현재 브랜치가 렌더하는 접근성 문구 26년 5월 8일(금) 표시 중과 테스트의 이전 기대값 26.05.08 (금) 표시 중이 달라 실패했다. 이번 성능 변경은 해당 문구를 수정하지 않았으며 별도 UI 회귀 정리가 필요하다.

합성/데모 경계만 사용했으며 DB 스키마, RLS, 원격 데이터는 변경하지 않았다.
