# Reception / Appointment Users / Roles

이 문서는 접수 / 예약 패키지의 사용자와 권한 경계를 정의한다. 상세 기능 동작은 [Feature Spec](../reception-appointment-spec.md)을 기준으로 한다.

## Primary Users

| 사용자 | 주요 목적 | 대표 작업 |
|---|---|---|
| 데스크 직원 | 보호자 응대와 당일 운영 시작 | 예약 등록, 예약 변경/취소, 현장 접수, 예약 환자 접수 처리, 지연/노쇼 처리 |
| 수의사 | 작은 병원에서 데스크 역할을 일부 대체하거나 본인 진료 흐름을 확인 | 예약 환자 접수 처리, 본인/미지정 대기 확인, 진료 차트 진입 |
| 수의테크니션 | 접수 이후 후속 업무 맥락 확인 | 진료 대기와 후속 검사/조제/처치 흐름 확인 |
| 병원 관리자 | 운영 기준과 권한 관리 | 접수/예약 정책 확인, 직원 권한 관리, 운영 이슈 검토 |

## Permission V1

| 작업 | 데스크 | 수의사 | 수의테크니션 | 병원 관리자 |
|---|---:|---:|---:|---:|
| 예약 조회 | 가능 | 가능 | 가능 | 가능 |
| 예약 생성/변경/취소 | 가능 | 가능 | 제한 | 가능 |
| 현장 접수 | 가능 | 가능 | 제한 | 가능 |
| 예약 환자 접수 처리 | 가능 | 가능 | 제한 | 가능 |
| 노쇼/지연 처리 | 가능 | 가능 | 제한 | 가능 |
| 접수/예약 정책 변경 | 불가 | 불가 | 불가 | 가능 |

## Product Rationale

- 수의사도 일부 접수/예약 작업을 할 수 있어야 한다. 작은 병원에서는 데스크 인력이 없거나, 수의사가 접수 업무를 대신 수행하는 경우가 있기 때문이다.
- 수의테크니션은 접수 이후 업무 흐름을 확인할 수 있지만, 접수/예약을 최종 변경하는 권한은 기본값으로 제한한다.
- 병원 관리자는 MVP에서 전체 권한에 가까운 최고 권한으로 둔다.

## UX Copy Rule

서비스 UI는 사용자에게 반말하지 않는다. 예를 들어 실패 메시지는 `접수 정보를 불러오지 못했습니다.`처럼 정중하고 운영적인 문장으로 작성한다.
