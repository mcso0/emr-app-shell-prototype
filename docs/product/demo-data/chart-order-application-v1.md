# Chart Order Application V1

This document defines the synthetic data shape for the expanded chart Order section where staff add, edit, bill, and confirm orders during an encounter.

It describes applied chart workflow data only. It is not a real clinical recommendation, fee schedule, prescription rule, or medical safety engine.

## Why This Is Separate

Hospital admin preset docs define master data. The expanded chart Order section uses applied data.

When a user adds an order to a chart, the system should create `chartOrderLine` records from the catalog or set preset. These rows can then be edited, billed, confirmed, and routed without mutating the original preset.

## Applied Row Lifecycle

Chart order rows should be easy to replay in a portfolio scenario.

| Step | Data Change |
| --- | --- |
| Add from catalog | Create `chartOrderLine` with `orderStatus = draft`, preset snapshot, pricing snapshot, and no generated task |
| Add from set | Create parent set row plus child rows with `sourceSetId`, `parentChartOrderLineId`, `setItemId`, and sort order |
| Order 청구 | Create or update `billingCandidateId` for selected rows where `billingReflectionEnabled = true` |
| Order 확정 | Set `orderStatus = confirmed`; create `generatedTaskId` for rows with `taskRequired = true` |
| Billing accepted | Link accepted candidates to `invoiceLineId` while preserving chart row pricing and adjustment source |
| Cancel before confirmation | Mark row cancelled without creating downstream task or invoice line |
| Cancel after confirmation | Preserve task/invoice links and add cancellation state instead of deleting the row |

`Order 청구` and `Order 확정` can happen in different order during the demo, so billing candidate state and task confirmation state should be stored separately.

## Order Name And Label Data Notes

- Order names should display up to 20 characters and show the full name in a hover tooltip when truncated.
- Clinical pathology rows no longer show a separate equipment/device label beside the order name.
- Narcotic and psychotropic rows use compact badges beside the order name: `마약` becomes `마`, and `향정` becomes `향`.
- Set names follow the same 20-character truncation and tooltip rule.
- In the expanded Order modal, a set row can expose the add button regardless of depth.
- A two-depth set button in the compact chart view should open the expanded Order modal rather than editing deeply in place.
- When adding under a set, the search field belongs under that set and should preserve parent set metadata.

## Quantity And Amount Derivation

| Source Case | Quantity Rule |
| --- | --- |
| Medication, per day | Use `days` as billing quantity |
| Medication, per frequency | Use `totalCount` as billing quantity |
| Medication, per each with EA-style dispense unit | Use actual dispense quantity as billing quantity |
| Medication, per mL | Use actual dispense quantity as billing quantity |
| Medication, per order | Quantity remains manually or preset-defined; default can be one |
| Medication, per kg | Quantity does not automatically change except where the preset's kg pricing rule defines a weight bracket |
| Non-medication, per order | Quantity remains manually or preset-defined; default can be one |
| Non-medication, per kg | Quantity follows the pricing rule snapshot rather than medicine dose metadata |
| Order set, set fixed price | Quantity unit is 건 and child rows do not determine set price |
| Order set, included order sum | Amount is derived from included child order billing rows |
| Order set, range price | Amount is derived from range price rows |

Keep computed values and their sources separate. For example, `billingAmountKrw` can be derived while `quantitySource` explains why the quantity is `days`, `total_count`, or `actual_dispense_quantity`.

Frequency aliases should be normalized before calculating totals:

| Alias | Canonical Code |
| --- | --- |
| `e3d` | `q3d` |
| `e4d` | `q4d` |
| `e5d` | `q5d` |

For chart fixtures, `totalCount = days * frequencyDailyCount`. This is workflow math only and is not medication safety validation.

## Hierarchy Rules

- Set rows and individual rows can appear in the same table.
- A set can contain nested set rows and individual order rows.
- Expanded child rows should keep `sourceSetId` and `parentChartOrderLineId`.
- Tree indentation, row depth, and category badges are display data, not clinical meaning.
- Reordering inside a chart should affect that encounter only.
- Editing a catalog preset later should not mutate chart order rows already added to an encounter.

## Billing And Confirmation Rules

| Rule | Demo Meaning |
| --- | --- |
| `Order 청구` | Creates or updates billing candidates from selected billing-reflected rows |
| `Order 확정` | Confirms selected rows and creates downstream queue work where needed |
| Pending rows | Can show as highlighted draft/applied rows before final confirmation |
| Confirmed rows | Should remain readable and traceable after billing changes |
| Billing reflection off | Row can remain operational but contribute zero or no billing line |
| Batch discount/adjustment | Applies to selected rows and should be stored separately from preset price |
| Footer totals | Derived from current applied rows, not from the master catalog alone |

## Deferred Screen-Implementation Notes

- The expanded modal should keep the large table usable without hiding the footer actions.
- Category tabs filter the table but should not destroy selected row state.
- `총괄지시사항` is encounter/order-batch instruction data, not an individual preset field.
- `Order 스케줄러` handles schedule review for applied order rows.
- Inline checkmarks and icons should be stored as statuses or linked note flags, not only visual state.
- Row color can show applied/pending grouping, but persistence should use explicit status fields.
- Batch billing and confirmation should operate on selected rows only.

## Out Of Scope For V1

- Real prescription safety.
- Real medication dose validation.
- Real tax compliance.
- Payment provider integration.
- Server-side billing finalization.
- External device or pharmacy integration.
